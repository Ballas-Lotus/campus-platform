# 阶段 20：选课名额实时同步（只改读侧）

> ⚠️ **后续演进提示（2026-10-17）**：阶段 21 已把本文的 `campus:stock` 结构从"展示读模型"升级为"**受理真相**"
> （ACCEPT 原子受理 + MQ 异步落库 + 补偿 + 台账口径对账）——本文第 1 节"写入量只有闸门放行后…""按真值纠偏永远安全"
> 等结论仅适用于本文的**只改读范围**；现状以 [docs/18-受理制异步落库（阶段 21）](18-受理制异步落库（阶段 21）.md) 为准
> （读侧三层、信号三字段、SSE、前端管线**均未变**，仍然有效）。

> 目标：学生**在选课/退课瞬间就感知到名额变化**（读体验优先），同时数据库连接池不为查询流量服务。
> 范围决策：**写路径零改动**——保留"闸门预扣 → 同步事务落库 → 恰好正确"的语义；信号在**每条写确实落库之后**（既有 `afterCommit` 钩子）推送。异步落库 / pending 台账 / op_id 等方案全部不需要（同步模型下 Redis 与 DB 之间不存在在途窗口）。

## 1. 设计总览

```
写（语义未变）：CourseService.select/drop（同步事务，锁/条件更新/唯一索引原样）
    └─ afterCommit（既有 afterStockDelta 钩子）追加两步：
         ① PUSH 脚本：campus:stock:{courseId} Hash 内  c:{classId}="remain:ver"（比值与版本同一脚本原子写入）
                      + HINCRBY @cver（课程版本）+ 刷新 TTL + 维护 c2c 反查表
         ② PUBLISH campus:stock:signal  {"id":<classId>,"v":<ver>,"remain":<remain>}   ← 严格三字段
             失败只记日志：不影响选课结果，客户端由查询/轮询兜底

信号通道（多实例广播）：每个实例订阅 Redis Pub/Sub → 实例内 50ms 合并（同班只推最新版本）
    → 独立线程池扇出到本机 SseEmitter（慢连接写失败即摘除）

读（新增三层）：
  GET /api/course/{courseId}/stock?version=V
      L1 进程内快照缓存（键含版本；TTL 2s；收到该课信号即失效；上限 2000 条）
           V == 本地已知 cver 且未过期 → 0 网络调用直返
      L2 一次 HGETALL campus:stock:{courseId}（(remain,ver,cver) 原子快照）
      L3 分布式锁 + 双检 → 按 DB 真值重建（抢不到锁/超时 → 直接返回 DB 真值，degraded=true，不堆积）

前端管线（SSE 与降级轮询共用同一套）：
  收到信号 → ① 乐观渲染（只接受更大版本号，乱序丢弃）② 防抖 150ms 合并 + 最大等待 500ms ③ 窗口结束查询校准
  建连/重连成功 → 无条件查询拉齐；长连接不可用 → 15s±抖动轮询接管（已连时 60s 校准）
  纠正平滑：差值 ≥3 走一次 1.2s 高亮动画，≤2 直接赋值
```

**正确性说明**：本结构只是"展示读模型"。能不能选上仍由**闸门 Lua + 数据库条件更新**裁决；remain 允许毫秒级滞后，客户端以服务端查询为准。对账器（30s）按 DB 真值纠偏——写是同步的，按真值纠偏永远安全（不存在"把在途名额还回去"的超卖窗口）。

## 2. Redis 结构（新增 2 项 + 1 频道；老结构零改动）

| key | 类型 | 内容 | TTL |
|---|---|---|---|
| `campus:stock:{courseId}` | Hash | `m:{classId}`=容量、`c:{classId}`=`"remain:ver"`、`@cver`=课程版本 | 6h（写时刷新） |
| `campus:stock:c2c` | Hash | classId → courseId（信号反查） | 24h |
| 频道 `campus:stock:signal` | Pub/Sub | 信号 JSON（即 SSE data 原文） | — |

复用未改：`campus:cache:class_stock:{courseId}`（阶段 19 展示模型，兼容旧页面）、幂等键、闸门计数器、班级静态信息缓存。
Lua 脚本：`PUSH_SCRIPT`（比值+版本原子写+EXPIRE+维护 c2c）、`FIX_SCRIPT`（对账按绝对真值回写+版本递增）。

| 验证项 | 结果 |

| 信号体 | `data:{"id":7221,"v":1,"remain":252}` 严格三字段；`event:ready` / `:hb` 心跳 25s 正常 |
| 实例内 50ms 合并 | 12 条紧凑连发（间隔 ~5ms）→ 客户端只收到 **1 帧**（最新版本 v=82） |

## 5. 验收对照（任务提示词 8 条 → 本方案口径）

| # | 标准 | 本方案证据 |

| 1 | 写落库后毫秒级推送、信号极小 | 上表实测 1ms；三字段（禁止扩展，`CourseStockKeys.signalJson`） |

| 4 | 乱序不回退 | 代码：`if (sig.v <= cur.v) return`；查询结果 `cl.v >= cur.v` 才应用 |

## 7. 诚实边界

- **列表聚合的实时性（阶段 21.2 已增强）**：课程列表页现在会对**当前页可见课程**按需加载一次班级名单并纳入实时订阅——「名额情况」列随信号实时更新（每门课仅首次加载一次，订阅集合 = 当前页课程 + 抽屉课程）。
  更早的行为（仅"打开过抽屉"的课程才实时）已被替换；翻页/筛选会切换订阅集合；单连接仍受 200 个教学班上限约束；

- **L1 的陈旧上界 = 2s**：Pub/Sub 是尽力而为，漏信号时 L1 靠 TTL 兜底（查询/轮询会收敛）;
- **SSE 上限**：单实例 5000 连接 / 单用户 3 条 / 单连接 200 个班级；超限返回业务错误 → 前端自动降级轮询；
- **多实例验证**：本机以单实例运行验证（Pub/Sub 扇出结构支持多实例；如需双实例可 `--server.port=9083` 起第二个验证）；
- 信号只驱动**展示**；判定始终在闸门 Lua 与数据库条件更新。
