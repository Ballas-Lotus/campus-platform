1架构全景：谁和谁说话

四层：客户端 → 网关 → 服务 → 中间件。所有业务请求都走同一条主干道，没有任何"绕道直连数据库"的特殊路径。

2业务全流程：一名学生的一天

四个阶段：会话启动 → 浏览（读）→ 提交（写）→ 事后（异步与撤销）。每个阶段标注了它背后的机制，热路径（写）全部指向第 3 节的大图。

📚 图书馆座位

选时段 → 预扣闸门 → 位图冲突检测（同一用户同一时段只能占一处）→ 条件更新占片 → 签到 / 超时释放。

🏸 体育场馆

按时段预约，链路与图书馆一致（同一套 Reservation 核心），并发下同样先 Redis 预扣再进事务。

🎤 讲座

名额制报名 /signup：名额即容量，走闸门挡量；成功后 MQ 异步送站内信。

📖 选课

本项目压力最大的一条线：读模型（静态+余量分离）+ 合并 Lua 闸门 + 8 分片落单 + 位图/唯一索引兜底。

这是全文的核心图。自上而下是一次"齐射"的完整旅程：入口三道闸 → 读写分叉 → 真相层 → 异步 → 观测。每个分叉点都标了实测数字。

📉 读侧收益

读模型拆分让"写后可见"从 21.4ms / 40 次回源 降到 3.05ms / 0 次回源；读容量 ~4.2k QPS。

⚡ 写侧收益

合并 Lua 把成功路径从 4 次 Redis 往返压到 2 次（≈1.85×）；写入口吸收 ~3.3k req/s。

🛡 挡量效果

10,000 人 → 9,887 在 Redis 被挡（40052），只有 10 个占用数据库连接。

✅ 正确性

恰好 10 成交、余票 -10 分毫不差、0 异常、0 回补、0 降级；端到端 P95 469ms。

4返回码速查：每个拒绝发生在哪一层

用户看到的是一句提示，系统里对应的是"在哪一层、被谁、为什么拦下"。

返回码含义拦截位置成本
40100未登录 / token 失效网关 JWT 验签最低（不进服务）
40055触发限流Sentinel（服务入口）极低（内存判定）
40060重复提交 / 正在处理中合并 Lua 快路径 或 幂等切面1 次 Redis 往返
40052余量不足 / 名额已满预扣闸门（Redis Lua）1~2 次 Redis 往返，不借数据库连接
0成功事务提交 + 提交后增量 + MQ走完全链路
齐射实测的分布：40052 × 9,887，0（成功）× 10，其余码为 0 —— 说明"挡量"这件事完整发生在 Redis 层，数据库只处理了它必须处理的 10 个请求。

5五个设计取舍（为什么这么做）

这些不是"最佳实践"清单，而是本项目在真实约束下的选择，每条都有实测支撑。

取舍选择为什么
Redis 与 MySQL 谁是真相MySQL 是真相，Redis 是预计数Redis 挂了降级直通、计数器漂移 30s 对账纠回；正确性从不押在缓存上（与"Redis 即真相"的 12306 学习版相反，因为抢课要求"恰好"，且单机可承受）
闸门放在事务前还是事务内事务之外@Transactional 一进就借连接；挡在事务外，9,887 个被拒请求从不占连接池 → 连接池 128 全程安全
超载时排队还是快速拒绝快速拒绝（40052）选课可重试，"告诉你没戏"比"让所有人一起死"更负责；对比 12306 学习版 V1 的"整列车锁排队"（30 并发 → 4.2 单/s、P99 7.2s）
展示与判定能不能用同一份数据可以，但标准不同展示（余量列）允许旧 100ms 级、允许 ±1 偏差；判定（放不放行）必须新鲜原子唯一 —— 所以余量走读模型，闸门走 Lua
某层挂了怎么办每层可降级，真相层不可绕过限流/幂等/缓存/闸门全失效时，MySQL 条件更新 + 唯一索引仍保证不超卖（最坏情况是多打数据库，不是错卖）
