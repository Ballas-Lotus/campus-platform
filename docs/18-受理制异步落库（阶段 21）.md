# 阶段 21：受理制——真相在 Redis，MQ 异步落库

> 目标（用户定调）：**推送不及时的根源是"等 MySQL 落库"**——高并发下事务排队几百毫秒，信号再快也白搭。
> 本阶段把裁决点前移到 Redis：**受理即裁决、Redis 一变就推、落库走 MQ 异步**，数据库退居"迟到的记录者"。
> 一句话对仗：阶段 20 是"落库后通知"，阶段 21 是"受理即真相"（12306 V2 同款思路）。
>
> **两条链路一份代码**：`campus.stock.async-select-enabled=true`（默认受理制）/ `false`（一键回退阶段 19/20 同步链路）。

## 1. 设计总览

```
【受理链路（默认）】
 用户请求
  → classId→courseId：c2c 反查（热命中 1 次 HGET；miss 回查 DB 一次）
  → ACCEPT Lua（一次原子，1 次 Redis 往返）：
       ① 幂等两态（CONSUMED→40060 / CONSUMING→40060）
       ② 快速已选检查（SISMEMBER campus:sel:{userId}；集合缺失→-6，先按 DB 惰性初始化再重试）
       ③ 结构检查（campus:stock:{courseId} 的 c:{classId}；缺失→-2，先按受理制口径重建再重试）
       ④ 边界检查：remain<1 → {-1}（满员，不改任何状态）
       ⑤ 通过：c:{classId}="remain-1:ver+1" ┐
               HINCRBY @cver                 │ 同一脚本原子
               HSET pend {classId}:{opId}    │
               SET idem CONSUMING + SADD sel ┘
  → 发落库消息（MQ syncSend 300ms 超时；失败 → 补偿回滚 → 40056"未被受理"）★
  → PUBLISH 名额信号（严格三字段 {"id","v","remain"}）★ 先 MQ 后 PUBLISH：推出去的每帧都有消息在路上
  → 置已消费（5s 幂等窗口）→ 返回 {accepted:true, remain, version, opId}

【落库消费者（campus_course_select_topic，批量 20/批）】判定树（顺序即正确性）：
  ① 台账不存在？ → 已解决（清账过/补偿过/裁决过）→ 只置"已消费"，绝不落库 ★
  ② 落库行 op_id == 本受理？→ 已生效（重放/清账前崩溃）→ 只清账，绝不补偿 ★
  ③ CourseService.select(userId, classId, opId)（四道防线原样：锁用户行/唯一索引/冲突检测/条件更新）
       成功 → 清账 + settled(ok) 回执（"选课成功"站内信由落库事务 afterCommit 发出）
  ④ 业务拒绝（重复/真满/冲突/班级不存在）：
       复查 op_id 命中 → 竞态内已生效 → 清账收尾
       否则 → 补偿（台账存在为原子闸门）：+1（钳制≤容量）+ 版本+1 + 修正信号 ★
              + 非"已选过"再清已选集合 + settled(false) 回执 + 失败站内信
  系统异常 → 整批 RECONSUME_LATER（不清账、不补偿——受理依然有效，等重试）

【读路径】阶段 20 三层不变（L1 进程内/L2 HGETALL/L3 锁+双检）；只是它读的结构从"展示模型"升级为"真相"。

【退课】保持同步落库（非热点；"失败即未退"语义最清晰）：DB 成功 → 结构 +1 + 信号 + 已选集合 SREM。
```

## 2. Redis 结构增量（阶段 20 结构语义升级）

| key | 类型 | 内容 | TTL |
|---|---|---|---|
| `campus:stock:{courseId}` | Hash | `m:{classId}`=容量、`c:{classId}`=`"可受理余量:版本"`、`@cver`（语义升级：受理真相） | 6h（写时刷新） |
| **`campus:stock:pend:{courseId}`** | Hash | 受理台账：field=`{classId}:{opId}` → `"-1\|受理时刻\|userId"` | 24h |
| **`campus:sel:{userId}`** | Set | 已选集合（快速已选检查；`-1` 为"空集合哨兵"，保证 EXISTS 判定"已初始化"成立） | 24h（惰性按 DB 重建） |
| `campus:stock:c2c` | Hash | classId → courseId（受理/推送/重建顺带维护） | 24h |
| 频道 `campus:stock:signal` | Pub/Sub | 名额信号（严格三字段） | — |

**不变量（受理制的算术核心）**：`结构余量 ≡ capacity − selected(DB) − Σ未决受理(pending)`。
受理（余量 −1 与 pending +1 同时发生）与落库成功（DB selected +1 与 pending −1 同时发生）**都不改变该真值**——
因此对账按此口径天然免疫在途噪音（不需要"pending 非空就跳过"之类特判）。

**DDL**：`resources/database/migrate-course-select-opid.sql` —— 8 分片 `t_course_selection` 加 `op_id VARCHAR(64)`
（重放判定"已生效"的唯一依据；同步老链路写 NULL）。schema.sql 已同步更新（新装环境自动带列）。

## 3. 正确性：每个"必须"及其反例

| # | 规则 | 违反后会怎样 |
|---|---|---|
| 1 | **先 MQ 后 PUBLISH**（受理顺序） | 反过来：MQ 失败回滚时，客户端已收到"名额 −1"的假信号（掉一下又弹回） |
| 2 | **满员拒绝不改任何状态**（不扣减/不加版本/不推信号） | 给抢课风暴中的每个失败者加版本 → 版本空转 + 信号洪峰（纯浪费） |
| 3 | **消费端"台账不在即跳过"** | 超时裁决补偿过的受理，其迟到消息会把名额再落库一次 → 结构少扣 1 → **超卖** |
| 4 | **op_id 判定"已生效"绝不补偿** | 崩溃重放把已提交的选课当失败回滚（+1）→ **超卖** |
| 5 | **补偿以台账 HEXISTS 为原子闸门**（COMPENSATE Lua） | 消费端与超时裁决并发补偿同一笔 → 名额加回两次 → 少卖（纠偏可治，但没必要） |
| 6 | **对账口径含 pending**（capacity−selected−Σpending）+ 版本 CAS | 按 DB 真值纠偏会把在途名额"还回去" → **超卖**；无 CAS 会覆盖并发原子扣减 |
| 7 | **超时裁决（5min）按 op_id 查库** | 消息丢失/进程死亡的在途受理永远占着名额（少卖）+ 台账泄漏 |
| 8 | **冷启动恢复小循环**（-6 集合初始化 与 -2 结构重建会连续出现） | 写成两个"一次性 if"时：集合初始化后的重试暴露 -2 却再没人重建 → 全量降级老链路（实测踩中，见 §6 缺陷复现） |
| 9 | **生产者路由预热 + topic 预建** | 首笔向新 topic 的发送需要拉路由，300ms 超时必然失败 → 首笔受理被补偿（现象正确但体验差） |
| 10 | **已选集合的维护点齐全**：accept SADD / 退课 SREM / 补偿 SREM（"已选过"除外）/ 登录重置清空 / 压测夹具剔除压测班 | 残留条目 → 后续选课被"快速已选检查"误拦（40051）；清多了 → 无效受理+补偿抖动 |

## 6. 开发中实测踩中的缺陷（已修复，留作素材）

1. **首笔发送必败**：向新 topic 的首次 `syncSend` 需要从 NameServer 拉路由 + broker 自动建 topic，
   300ms 超时必然打满 → 首笔受理被"正确地"补偿成 40056。修复：启动时 3s 超时探针预热路由 + `mqadmin updateTopic` 预建 topic。
2. **冷启动双缺只修一半**：ACCEPT 脚本先查集合后查结构——两者都冷时先得 -6，初始化集合后重试才暴露 -2，
   而恢复逻辑是"两个顺序 if"→ 结构永远没被重建 → 全量降级老链路（现象：`结构/集合未就绪，回落同步老链路 code=-2`）。
   修复：恢复改为小循环（-6/-2 各至多处理一次，最多 3 轮）。**这类"恢复路径的状态机"正是受理制最容易被测出的角落。**
3. **补偿漏清集合**：MQ 发送失败路径回滚了名额与台账，却没 SREM 受理时 SADD 的条目 → 用户下次选同一班被 40051 误拦。
   修复：闸门补偿分支补 SREM（消费端业务拒绝分支同款处理，"已选过"除外）。
4. **压测夹具把热态测没了**：夹具清理曾整组删除已选集合 → 每轮齐射都是冷启动（P50 133ms）。
   修复：只 SREM"压测班"这一条 → 复跑呈现真实热态（P50 14ms）。
5. **版本回退卡死客户端（阶段 20 潜在边界，本轮修复）**：结构被 evict 重建后版本从 0 重新计数，
   而客户端按"版本只增不减"丢弃查询结果 → 持有高版本的页面会**长期显示旧数据**（演示时"登录重置触发的 evict"必现）。
   修复：客户端**查询=权威快照永远采纳数值**、版本只升高做高水位；信号仍严格按版本去重（洪峰乱序保护不受影响）。

## 7. 风险与边界（诚实说明）

- **Redis 从"加速器"变"命门"（P1）**：受理链路 Redis 异常 → 自动降级同步老链路（其内还有一层"Redis 异常直通数据库"）；
  但若 Redis 长时间不可用，系统实际回到阶段 16 以前的形态（能选，但慢）。建议生产开 AOF + 主从。
- **低并发收益小**：单笔受理的绝对值（热态 ~10ms）与同步链路（热态 SQL 单笔 ~10-30ms）差距在低并发下不显著；
  收益在高并发排队场景（省掉事务排队几百 ms）。
- **退课仍是同步落库**：刚受理未落库时退课会短暂 40054（前端任务未落定前按钮显示"选课中…"，正常点不到）。
- **已选集合是加速器**：允许过期/丢失（惰性重建）；极端情况下"集合说没选、DB 说选了"会走一次"无效受理→补偿"抖动，正确性不受影响。
- **超时裁决窗口（5min）**：消息长时间滞留且超过裁决时限时，会先补偿、迟到消息被"台账不在"规则拦下——用户收到"未成功"通知但名额已退回，语义自洽。
- **对账器新口径是全局约束**：任何未来新增的"按 DB 真值写回"逻辑都必须换成 `capacity − selected − Σpending`（代码即文档：`CourseStockService.dbTruthWithPending`）。

**浏览器手测清单**（前端 `http://localhost:5173` → 课程列表 → 查看教学班）：
1. 点"选课" → 提示"已加入选课任务" → 右下角出现**「🧾 选课任务」面板**（排队中 → 提交中 → 已受理，等待确认…）；班级卡片只出现**"选课中…"**（蓝色中性标签），**不会提前变"已选"**；
2. 回执到达（0.1~1s）→ 任务面板变 **"✅ 已选上"**，卡片此时才变"已选"（以数据库为准），"我的课表"同步出现该课；成功任务约 8 秒后自动收起；
3. 选一个与已选课冲突的班 → 任务面板变 **"❌ 未选上：冲突原因"**；卡片自始至终没有变成"已选"，因此**无需回滚**；站内信收到"选课未成功"；
4. 快速连选两门（如语文+英语）→ 任务面板出现两条：前一条"已受理"时后一条显示"排队中…"，前一条落定后才提交后一条（串行）；同班/同课程重复提交会被直接拦下；
5. 断网 10s 再恢复 → 状态标签"轮询校准中"→自动回连拉齐；任务超 4s 无回执显示"结果确认中，请稍后刷新"，并以刷新后的数据库状态收敛；
6. 选课 → 立刻退课：退课按钮在"选课中"期间不可点（防 40054 窗口）。

## 10. 阶段 21.1：前端改为"选课任务队列"（回执确认制）

**动因（用户验收意见）**：受理制下"提交 → 确认"之间有一段异步窗口（落库校验：时间冲突等）。
旧前端在窗口内就把班级标成"已选（处理中）"、被拒时再回滚——**回滚观感差、且容易让人误以为系统先给后收**。
真实数据部分没有问题：POST 返回的 remain/version 是 ACCEPT 在 Redis 当场查余量并扣减后的真实值；
要改掉的只是"提前宣称用户已选上"这一层 UI。

**新模型（仅前端改动，后端契约不变）**：

```
用户确认 → 加入「选课任务」队列（本端，Pinia）
  → 串行提交：同一时刻只有一个任务在途，前一个拿到回执（或 4s 超时）后才提交下一个
  → 任务状态：排队中 → 提交中 → 已受理等待确认 → ✅ 已选上 / ❌ 未选上（原因）
  → 班级卡片只显示中性标签「选课中…」，**不提前标"已选"**；"我的课表"不提前变化
  → settled 回执到达：落定任务 + 提示 + 刷新（此刻才以数据库为准显示"已选"）
  → 4s 无回执：标记"结果确认中，请稍后刷新"，刷新后按数据库真相收敛
去重：同一教学班、或同一课程（任一教学班）存在未终结任务时，拒绝再次入队。
```

**为什么串行**：①第二个任务的时间冲突判定能基于第一个已落库的结果；②结果顺序符合直觉；
③避免用户在同一瞬间对两门冲突课程各发一次请求（虽然数据库最终也会拒绝其一，但串行让体验可预期）。

**边界**：任务队列只存在于当前页面会话（刷新/离开页面后任务面板清空，但已提交的请求仍由服务端继续处理，
页面以数据库为准显示）；多标签页各自维护队列，settled 经 BroadcastChannel 同步、刷新兜底。

**验证**：任务队列纯逻辑 14 项单测全绿（入队/去重/串行取队首/回执落定/失败可重试/
"回执先于响应"竞态不被回写/unknown 可收敛/清理）；`vite` 编译通过（`stores/selectTasks.js`、`views/CourseView.vue`）。
