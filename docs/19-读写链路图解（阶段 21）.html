1写链路全景 —— 受理制（默认开启，可一键回退）

一条选课请求：入口同步 → ACCEPT 原子受理（Redis 即真相）→ 先 MQ 后 PUBLISH → 立即返回；数据库在后台异步落库，拒绝则自动补偿并回执。

Redis 受理（真相） MQ 异步落库 补偿 / 修正 同步入口 / 响应 数据库 / 降级

2ACCEPT Lua —— 受理即裁决（一笔原子，1 次往返）

顺序刻意固定：幂等 → 已选 → 结构 → 边界 → 原子写五项。拒绝分支全部"不占状态"，只有通过分支才产生任何写入。

3落库消费者 —— 四分支判定树（顺序即正确性，缺一即超卖）

这是受理制最关键的 40 行：台账与 op_id 两层保护回答两个问题——"这笔受理解决了吗""这个重放真的落过库吗"。

4读链路 —— 三层查询 + 信号/回执管线

读的骨架与阶段 20 完全一致；变化在于它读的 campus:stock 结构现在是"受理真相"，且新增了按用户定向的 settled 回执。

5对账不变量与超时裁决 —— 兜住"消息丢失 / 进程崩溃"

受理制的算术核心：受理与落库成功都不改变"真值"，所以对账可以放心地按同一个公式比对；版本 CAS 保证不覆盖并发写者。

读这一页的顺序建议：图 1看全局节奏 → 图 2/3看写路径的"每个必须及反例" → 图 4看读为什么不会打穿数据库 → 图 5看兜底层。 面试讲法：先讲"为什么等 MySQL 落库会慢"（阶段 20 的天花板），再讲"受理制怎么把等待移出用户路径"，最后主动说风险（Redis 变命门 + 补偿/超时裁决 + 一键回退）。
诚实边界：受理制下 code=0 的语义是"已受理"而非"已落库"——前端以「选课任务队列」显示处理中与结果（不提前标"已选"，也就没有回滚）； 低并发场景与同步链路差距不显著（收益集中在高并发排队）；退课仍是同步落库（刚受理未落库时短暂不可退）。
