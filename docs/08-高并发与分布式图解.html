高并发：不用分布式锁，把裁决交给数据库单条语句

预约/选课的并发正确性 = 四条防线。它们都能被压测的「恰好 N 成功」断言证伪，做不了假。

四道防线（从入口到终局）

① 原子条件更新 · 防超卖判断写进 UPDATE 的 WHERE：
SET booked=booked+1 WHERE id=? AND booked<capacity
0 行受影响 = 抢满了。选课同理 selected<capacity
② 用户行锁 · 串行化同类操作SELECT id FROM t_user WHERE id=? FOR UPDATE
同一用户的"读-判-写"串行；消除并发首约的间隙锁死锁（阶段 9 压测发现并修复）
③ 唯一索引 · 终局兜底uk_reserved(slot_id,user_id,active_key)
uk_user_class_semester · uk_reservation_no
④ 位图冲突检测 · 跨资源96 格 BigInteger 位图（24 hex），行级 FOR UPDATE + OR/AND-NOT 合并；同一用户并发抢多座位同时段只成功 1 个

防超卖关键 SQL（分片后仍是单分片原子操作）

-- 资源时间片扣减（图书馆/场馆/讲座）：数据库原子防超卖 = 唯一裁决者
UPDATE t_resource_slot SET booked = booked + 1, version = version + 1
WHERE id = ? AND resource_id = ?        -- 阶段 14：补分片键 → 单分片命中
  AND booked < capacity;              -- 0 行 = 已被抢满 → 业务拒绝(40024)

-- 选课名额扣减（广播表，两库副本同事务内双写）
UPDATE t_course_class SET selected = selected + 1
WHERE id = ? AND deleted = 0 AND selected < capacity;
为什么不用 Redis 分布式锁？锁只能保证"同一时刻谁来执行"，释放后重复请求照样能再进来——它不是幂等； 而"把判断写进 WHERE"的单条语句在数据库里原子执行，天然同时解决互斥 + 幂等 + 正确性，还少一个组件的故障面 （小林原文同款观点：「数据库业务一般优先依靠数据库事务，Redis 可以作为辅助防重」）。

幂等的三种典型方案

① 插入类业务：唯一约束挡住重复插入；

② 状态流转：UPDATE ... WHERE status='待支付'，重复执行影响行数为 0；

③ 累加类业务：用「业务流水 + 唯一索引」去重，而不能单纯乐观锁；

并提醒：Redis SETNX / 分布式锁有「记录与执行」两个窗口，不能单独代替幂等记录。

分片带来的新并发问题（已实测解决）

热点分片连接放大：100 人抢同一个场地 → 事务全部路由到同一分片，排队等行锁期间每条事务占着一条物理连接， 连接池 20 直接打爆（先 CannotCreateTransactionException，后 Hikari timeout）。 解法：外层 128 + 内层 2×128 + MySQL max_connections=500；容量规划按单分片峰值并发而非总并发。

分布式：服务拆分 + 分库分表 + 全局唯一 ID

三件事：拆进程（故障隔离）、拆数据（水平扩展）、拆号段（全局唯一且可路由）。

4.1 服务拆分与无状态化（阶段 12）

拆成三个进程网关 :9080 / 用户服务 :9081 / 业务服务 :9082，注册到 Nacos；网关按路径分流。
状态外置到 RedisJWT 本体只做签名校验（无状态）；登录态的真身在 Redis 副本 —— 服务可随意重启/扩容，登出=删副本（旧 token 立即失效）。
两级校验 + 纵深防御网关做 JWT + Redis 副本校验（40100/40101）；服务内过滤器保留第二道，直连调试行为一致。
实测停用户服务 → 预约/选课照常（故障隔离）；业务服务双实例杀一存一（横向扩容）。

4.3 分库分表：哈希的思想，与小林的 Redis 哈希槽同源

小林 · 知识点

Redis Cluster 怎么找分片

"对 key 做哈希，并对总分片数取模……确定性哈希函数，给定 key 永远映射到同一个分片。"

为解决扩容重分片，引入 16384 个哈希槽：CRC16(key) % 16384，扩容时只搬槽不重算 key。

——《什么是 Redis？》·「Redis 集群」
➜
本项目 · 落地

数据库分片 = 同一套确定性哈希

shard = MOD(分片键, 8)；库 = shard/4，表 = shard%4；同一 user_id 的数据永远落在同一分片。

更进一步：基因法把"路由指纹"编进业务单号（尾 6 位 = user_id % 1,000,000）， 于是"按单号查"也能直接算出分片 —— 无需索引表、无需广播扫描（相当于 Redis 的 hash tag 思想：让 key 自带路由信息）。

图 3 · 基因法：一次哈希设计，让「按人查」和「按单号查」走同一条路

4.4 分布式 ID：雪花 + Redis 分配机器号

为什么必须换掉自增 ID8 个物理分片各自 AUTO_INCREMENT 会撞号；分片表主键统一雪花（MyBatis-Plus ASSIGN_ID）。
机器号怎么来INCR campus:snowflake:worker，多实例自动错开（1024 取模）；Redis 不可用回退随机并告警。
和基因的分工雪花段保证全局唯一；基因段保证可路由；单号 = RES + 雪花 + 6 位基因（28 字符）。

小林 · 知识点

Redis 的定位与能力

"Redis 是一个内存数据库，用作另一个真实数据库前面的缓存，以帮助提高应用程序性能……"

"命令执行仍为单线程"（6.0 起多线程仅 IO）；支持 Lua 脚本、发布订阅、复制、事务等。

单实例简单但"一旦失败，所有客户端调用都失败"；高可用靠复制/哨兵/集群；持久化 RDB/AOF 按容忍度选。

——《什么是 Redis？》
➜
本项目 · 落地

五类状态，全部"自带 TTL 或原子诉求"

🔑 登录态副本 — TTL 30min 滑动续期（可主动失效的开关）

⛔ 惩罚键 campus:penalty:{userId} — TTL 到期自动解禁，免定时任务

⑤ 单线程 = Lua 的原子性来源（与 MQ 幂等直接相关）

小林 · 知识点

"Redis 6.0 起支持多线程 I/O（命令执行仍为单线程）"——一条命令/一段脚本在执行期间不被其他命令插入， 这是"查-判-改"可以写成原子脚本的前提。

➜

MQ 消费幂等就吃这口饭：两态 Lua「没有键→写入 CONSUMING；已是 CONSUMED→跳过」一步完成， 两个消费者同时抢同一条消息也只有一个能进入处理。不需要 SETNX+SET 两步（两步之间就有窗口）。

-- @MQIdempotent 消费幂等（两态 Lua；键：campus:mq:idem:{prefix}:{messageKey}，TTL 24h）
if redis.call('EXISTS', KEYS[1]) == 0 then
    redis.call('SET', KEYS[1], 'CONSUMING', 'EX', ARGV[1])
    return 1          -- 抢到执行权
elseif redis.call('GET', KEYS[1]) == 'CONSUMED' then
    return 0          -- 已处理过 → 直接 ACK
else
    return 2          -- 处理中/上次异常残留 → 按策略等待
end
-- 业务成功后置 CONSUMED；业务抛异常则删除键（让 MQ 重试能重新进入）

高可用与持久化：单实例 + 可容忍降级的诚实答案

小林知识点本项目的选择理由（降级剧本）
单实例挂了 → 所有调用失败本机单实例（演示规模）Redis 挂：登录态失效→重新登录；惩罚键丢失→惩罚提前解除；幂等键丢失→消费端还有业务状态二次校验兜底。故障被三层设计吸收，不会伤数据
复制 / 哨兵（Quorum 法定票）/ 故障转移未启用；升级路径已文档化生产化第一步：1主2从 + 3 哨兵（"至少 3 节点、Quorum=2"）
RDB：快照间隔之间可能丢数据；AOF：更完整但更重按默认，不做持久化调优存的全是可重建状态——与小林的判断句同一逻辑："用作缓存的场景，丢数据并非世界末日"（我们连"世界末日"的数据都在 MySQL 与 MQ 里）
集群：CRC16 % 16384 哈希槽水平扩展数据扩展落在数据库分片（§4.3）本项目的"大"在 95.8 万行预约表，而非 Redis 内存

MQ 篇对照：三条主线的逐条落实

为什么用 MQ → 重复消费怎么办 → 消息丢了怎么办 → 延时消息与状态机 → 恰好一次的真身。

6.1 为什么需要 MQ：解耦 / 异步 / 削峰（项目版本）

小林三大价值本项目对应具体机制
解耦：订单系统不再逐个 RPC 通知下游预约成功 → 发 campus_notification_topic，站内信消费者订阅预约引擎不认识"站内信"；以后加"短信通知"只需新消费组，主流程零改动
异步：非核心流程后台执行，前台快速响应通知落库异步（顶栏 🔔 轮询未读数）预约接口只做"发消息"（同步发送拿 ACK），不等待写通知表
削峰：流量先入蓄水池，后端按能力消费抢课/抢座入口 Sentinel 限流（40055） + 原子扣减真正瞬时打库的写请求在入口切面就被快速失败（120 并发实测拦 99），不产生 DB 动作
诚实边界：本项目没有把预约/选课主干"搬进 MQ"（强一致写路径同步完成，靠四道防线保证正确性）； MQ 用在旁路：通知（异步）与超时判定（延时）。这符合小林的判断句："要不要用，看业务收益是否值得额外的复杂性。"

MQ 的三大挑战在本项目的真实应对

挑战（小林）本项目应对
多一个要保障可用性的组件MQ 挂了：站内信不落库（可补）、超时判定退回 Scheduler 每 60 秒兜底——降级路径常备（正是小林说的"本地消息表等补偿方案"的广义形态）
开发排查复杂度：重复/丢失@MQIdempotent + 状态机二次校验 + 幂等键日志（每条消息带 messageKey）
数据一致性：只成功一半见 §6.3 与 §8（本项目用"业务状态即 outbox"保证收敛）

6.2 重复消费怎么解决：「MQ 负责重投，业务负责幂等」

第一层：稳定幂等键messageKey = timeout:{预约ID}:{hop} / RESERVATION:{单号}:{userId} —— 重发时键不变（不重新生成 UUID），这正是小林强调的"稳定的业务幂等键"。
第二层：两态 Lua 快速挡重见 §5 的 Lua：重复消息在 Redis 一步被识别（实测：同 key 发 2 条 → 落库恰好 1 条）。
第三层：业务状态机终审判爽约前先重查：预约不存在 / 已签到 / 已非 APPROVED → 直接跳过。就算 Redis 幂等键整个丢了，错误判定也不会发生。
特殊设计：hop 链"延时不够（被截断/时钟偏差）"时消费者按剩余时长重投递，hop+1 生成新幂等键——每一跳独立幂等，而不是被旧键挡死（这是 12306 的链式思路）。

6.3 消息丢失怎么解决：生产者 / Broker / 消费者三环节对照

环节（小林的三段检查）本项目落地缺口与兜底
生产者："确认消息真的发出去了；订单已写库但发消息前宕机 → 要有记录可补发" 同步发送（syncSend 拿 Broker ACK）；发送失败自动降级（5.x 定时消息失败 → 延迟等级回退重发；再失败仅告警不阻断主流程） "已写库、未发出"的窗口 → Scheduler 兜底扫描（§8 的 outbox 思想）
Broker："持久化 + 副本；不能只说部署了集群" RocketMQ CommitLog 持久化（本机单主）；topic/消费组前缀 campus_* 隔离 单主是演示环境取舍；生产按"2主2从 + SYNC_FLUSH"规划（文档记录）
消费者："先业务成功，再确认消息；失败进重试，超限进死信" 业务成功才 ACK；抛异常 → 幂等键删除 → MQ 原生重试（RocketMQ 默认 16 次、间隔递增）→ 进 %DLQ% 死信 重试消费者同时被 Scheduler 兜底，不依赖单一通道

6.4 延时消息：底层原理 +「判爽约」就是校园版的「延迟关单」

小林 · 知识点

RocketMQ 延迟消息原理 & 关单的正确姿势

4.x：固定延迟等级，消息转存 SCHEDULE_TOPIC_XXXX，到点回写正常投递路径； 5.x：可指定投递时间戳（时间轮组织到期消息）。

"到期代表可投递，不代表业务必然在那一毫秒完成"——所以关单要以数据库状态为准：

UPDATE orders SET status='CLOSED' WHERE order_id=? AND status='UNPAID' AND expire_time<=now

"保留定时扫描作为兜底，处理延迟消息漏发、投递延后等异常。"

——《消息队列面试题》· RocketMQ 延迟章节

6.5 恰好一次的真身：「至少一次投递 + 消费幂等」（小林的标准答案）

语义含义（小林）本项目
最多一次允许漏，不重试未选（不能容忍漏判爽约）
至少一次失败重试，可能重复✅ 选择（RocketMQ 重试 + hop 重投）
恰好一次"在明确范围内只生效一次"✅ 业务效果达成：至少一次 + 幂等（实测发2落1；压测"成功数=名额数"严丝合缝）

一致性重点：本地消息表 —— 本项目的"业务表即 outbox"

用户指定的对照锚点：「本地消息表怎么保证数据库和 MQ 的一致性？」逐句对齐。

小林 · 知识点（逐句）

本地消息表（Outbox）

① "在同一个数据库事务里做两件事：插入订单，插入一条待发送事件"——事务成功两条一起在，失败一起回滚；

② "事务提交后，由后台任务扫描待发送记录，发送到 MQ；收到确认后标记已发送"；

③ "发送成功但标记前宕机 → 下次扫描再发一次 → 消费者仍然要幂等，事件 ID 重发时不能变"；

④ "待发送记录超时告警，失败重试，成功记录定期归档"。

——《消息队列面试题》·「本地消息表怎么保证数据库和 MQ 的一致性？」
➜
本项目 · 落地

不建消息表：预约表本身就是 outbox

① 预约与"超时判定"在同一个 MyBatis 事务里落库（预约行 + 位图 + 库存扣减）——提交后"待办"自然存在；

② 生产者首选同步发延时消息；兜底扫描器 = Scheduler（每 60s 扫 status='APPROVED'）；

③ "待发送记录"不是一条消息行，而是 可推导的状态条件："APPROVED 且已过开始+15min 且未签到"。 没有"标记已发送"字段——因为状态流转（NO_SHOW/COMPLETED）天然把它从扫描集合里移走；

④ 消费端幂等三层（§6.2）保证任意次重发只生效一次。

图 5 · 两种 outbox：一个是"写一条要发什么"，一个是"数据本身说明了要发什么"
维度本地消息表（小林版）业务表即 outbox（本项目）
原子性业务 + 事件记录同事务 ✅业务落库即"待办已存在"✅（无第二条记录要同步）
补发来源扫 t_local_message扫预约表状态条件（Scheduler）
重复投递消费端幂等 + 事件 ID 不变 ✅消费端幂等（两态 Lua + 状态终审）✅
时效取决于扫描间隔首选精确延时消息（实测 8.6s）；兜底窗口 ≤60s
代价额外表 + 标记字段 + 归档 + 多扫描者要租约仅当"待办条件"可从业务状态推导时成立（本项目成立：到点+未签到）；否则仍需消息表
为什么不用事务消息（半消息/回查）？小林讲过它解决的问题是"本地事务结果与消息可投递性一致"。 本项目评估后不引入：消息发送在事务提交前后都无害——早发（事务未提交）→ 消费端查库状态不符会跳过； 漏发 → Scheduler 兜底。既然不存在"必须原子"的绑定，就省掉 half-message + 回查的复杂度（若未来有"强一致投递"诉求， 现成的 RocketMQ 事务消息即可接入）。
