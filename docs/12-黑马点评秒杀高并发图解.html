黑马点评是什么？为什么秒杀是它的"含金量重点"

一句话：一个拿 Redis 全家桶当主角的实战项目，而秒杀章节是唯一把"高并发 + 分布式"完整串起来的地方。

💬 说人话 黑马点评整个项目像一座"Redis 兵器库"：短信登录用 Redis 代替 Session（共享登录态）、查商户先过缓存（缓存三兄弟）、 签到用 BitMap、UV 统计用 HyperLogLog、附近商户用 GEO……但这些都是读多写少的"兵器展示"。 只有优惠券秒杀是真刀真枪的高并发写——有限库存、瞬时流量、一个人只能买一份、还不能超卖。 所以面试官问黑马点评，八成先问秒杀。

2

秒杀难在哪：三座大山

先想清楚敌人是谁，再看每一代方案在打哪一个。

💬 说人话 把秒杀想象成"食堂 12:00 开抢限量 100 份的半价鸡腿饭"：
① 超卖——最后 1 份鸡腿，两个人同时看到"还有"，都付了钱 → 卖出 101 份；
② 一人多单——同一个同学拿两份（自己排完又替"另一个自己"排）；
③ 数据库被冲垮——1 万人同时挤在窗口（数据库）前，窗口直接瘫痪。
大山怎么产生的课程的解法（后文各一节）
超卖"先查库存、再扣库存"两步之间有缝隙：两个线程都查到 stock=1，都扣成 0 → 实际卖了 2 份乐观锁 CAS 条件更新（§5）
一人多单"先查订单、再插订单"之间同样有缝隙：都查不到 → 都插入synchronized → 分布式锁 → Lua 原子判定（§5/§6/§7）
数据库压力开抢瞬间的无效请求（没库存、已买过）也要"查一圈数据库"才被拒Redis+Lua 预检挡量（§7）→ 异步落库（§8）
提炼成一句话（面试可直接用）：秒杀的所有优化，本质是把"判断资格"和"真正下单"拆开—— 判断资格放到 Redis 内存里做（快、原子），真正下单交给数据库异步完成（稳、限速）。

这张时间线就是面试标准答案的骨架——"为什么这么设计"全藏在每代的"遗留"里。

图 1 · 六代演进：V1→V2 防超卖、V3→V4 跨集群防重复、V5→V6 从"挡量"到"异步"。每一步都保留前一步的成果。
4

前置武器：全局唯一 ID（Redis INCR 版雪花）

订单 ID 不能再用数据库自增——分库分表会撞号，而且规律 ID 会泄露"今天卖了多少单"。

ID 的位布局（课程方案）

0
符号位 1bit
恒为 0
时间戳 31bit
秒级，自定义起始纪元
（约可用 69 年）
序列号 32bit
同一秒内的自增计数
（每秒可容 2³² 个）
// 每天一个 key，用 Redis 自增做"秒内序列号"；其余位由位运算拼装
String date = LocalDate.now().format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
long seq = redisTemplate.opsForValue().increment("icr:" + date);   // 原子自增
long orderId = (timestamp << 32) | seq;   // 时间戳左移 32 位 拼 序列号
💬 说人话 ID = 「今天第几个 1/3 秒」拼「这一秒里的第几单」：日期保证每天从头数且不重复， Redis 的 INCR 保证"这一秒里的第几单"绝不会有两个人拿到同一个号（单线程原子自增）。 分库分表后各表 ID 依然全局唯一、趋势递增（对索引友好），还不会暴露具体销量。
面试顺带提一句加分：同类方案还有雪花算法（Snowflake）——机器位替代 Redis 自增；本项目的分库分表 ID 用的是基因法（把分片基因写进 ID）， 目标是"分片键可从 ID 反推"，与本页 §10 对照表呼应。
5

第一战：超卖（乐观锁）与一人一单（先查后插的竞态）

两座山共用同一个成因：检查与修改之间存在时间缝隙。

图 2 · 超卖的成因是"检查"与"修改"两步之间的缝隙；把检查塞进 UPDATE 的条件里，缝隙就没了。

一人一单：同一道缝隙，换个战场

"先查有没有订单、再插入订单"——并发下两个线程都查不到，就都会插入。课程的修法分两级：

阶段做法为什么 / 坑
单机版 synchronized (userId.toString().intern()) 包住下单方法 intern() 复用字符串常量池，避免每个请求都新建锁对象；只对同一个用户串行（不同用户互不影响）
关键细节 锁必须包住整个事务（通过 AopContext.currentProxy() 调代理对象） 若锁在事务提交前就释放：后一个线程查不到"还没提交的订单"→ 还是重复下单（面试高频追问）
集群版 换分布式锁（下一节） synchronized 只在单个 JVM 内生效——部署两台机器，锁就"各锁各的"了
💬 说人话 synchronized = 宿舍楼下只有一个门卫（单机有效）；但你们楼有两个门（两台服务器）时， 就需要一张全楼共享的门禁系统——这就是分布式锁。
6

第二战：分布式锁的三代进化（SETNX → Lua → Redisson）

课程先手写一版锁、亲手踩四个坑，再引出 Redisson——"为什么用 Redisson"的答案全在这四个坑里。

图 3 · Redisson tryLock：抢到就启动看门狗续期；抢不到就订阅等待。右下四道坎就是"为什么不用手写锁"的标准答案。

自研锁的两版代码——错在哪，Lua 怎么救

// ❌ 版本一：两条命令分开执行 —— 没设过期就宕机 → 死锁
Boolean ok = redisTemplate.opsForValue().setIfAbsent("lock:order:" + userId, "1");
redisTemplate.expire("lock:order:" + userId, 10, TimeUnit.SECONDS);
// ✅ 改成一条原子命令：SET key value NX EX 10

// ❌ 版本二：释放锁"先判断再删"两步走 —— 判断完可能超时换了锁主 → 删了别人的锁
if (redisTemplate.opsForValue().get(key).equals(token)) { redisTemplate.delete(key); }
// ✅ 用 Lua 把"判断 + 删除"合成一次原子执行（让 Redis 单线程来保证中间不被打断）
💬 说人话 为什么释放锁要用 Lua？——"看一眼牌子是不是我的、再摘牌"这两步之间， 牌子可能已经超时换成别人的了，你这一摘就摘错了。Lua = 把这两步焊成一瞬间，神都插不进来。 （这一条与本项目 §8 的"Lua 预检"是同一个原理：Redis 单线程执行脚本，中间不插队。）
7

第三战（★核心）：Redis + Lua 预检——三道判断压缩成一次原子

到这里，课程把"库存判断 + 一人一单 + 扣减"从数据库整体搬进了 Redis 内存，一次往返完成。

图 4 · V5 的核心：三道判断 + 两次修改 = 一次网络往返、一次原子执行。被拒的请求（1/2）连数据库的影子都摸不到。

Lua 脚本原文（课程版，返回值 0/1/2）

-- 参数：ARGV[1]=voucherId  ARGV[2]=userId
local stockKey = 'seckill:stock:' .. ARGV[1]
local orderKey = 'seckill:order:' .. ARGV[1]
if (tonumber(redis.call('get', stockKey)) <= 0) then return 1 end          -- 库存不足
if (redis.call('sismember', orderKey, ARGV[2]) == 1) then return 2 end  -- 重复下单
redis.call('incrby', stockKey, -1)                                -- 扣库存
redis.call('sadd', orderKey, ARGV[2])                              -- 记名（一人一单）
return 0                                                          -- 成功
💬 说人话 这就像把四个动作焊成一个动作：看库存 → 看名单 → 扣一份 → 写名字， 由 Redis 单线程一气呵成。中间任何人想插队都没门——超卖和重复下单从"要防的 bug"变成"不可能发生的物理事实"。
V5 的遗留（也就是 V6 的动机）：Lua 预检之后，通过的请求仍然要同步走一遍数据库（扣库存 + 写订单）。 数据库这个"慢动作"还在用户的等待链路里——挡掉了无效请求，但"有效的那些"依旧慢。所以要异步。
8

终战（★核心）：异步秒杀——Lua 发资格，Redis Stream 慢慢落库

思路：用户只等"有没有抢到"（Redis 内存级），"把订单写进数据库"交给消费者后台做。

图 5 · 异步秒杀全链路：资格判定在 Lua（快），落库在消费者组（稳），失败的消息躺在 pending 架子上等重试。

为什么是 Redis Stream？——三种"Redis 消息队列"对比（课程选型）

方案机制致命缺陷 / 适用性
ListLPUSH + BRPOP 阻塞取消息被取走就没了：消费到一半宕机 → 消息丢失；且一条消息只能被一个消费者处理
Pub/Sub发布订阅，广播给所有订阅者不持久化：没人订阅或消费者掉线，消息直接蒸发
Stream ✓消费者组 + XREADGROUP + XACK + pending list可持久化、可 ACK、失败可重试、可多消费者分摊——所以被课程选为秒杀异步落库的载体
💬 说人话 Stream 像奶茶店的取号叫号系统：订单小票（消息）落在单架上（持久化）， 柜员（消费者组）按号叫人，办完在票上盖章（XACK）；办砸的票放回"待办架"（pending）， 换个人接着办——而不是像 List 那样"票一撕就没"，也不是 PubSub 那样"喊一嗓子没人听见就作废"。
诚实边界：课程的异步方案里，Redis（库存 + 一人一单 Set）是"唯一真相"—— 消费失败靠 pending 重试兜底，但没有对账、数据库没有唯一索引兜底、Redis 宕机即不可用。学习项目可以接受； 生产要补的正是下一节对照表里本项目做过的事。

面试话术与追问树

"你了解黑马点评的秒杀吗？"——按"演进链"讲，比按"功能"讲高级得多。

🎤 60 秒标准答法

黑马点评的秒杀核心是一条演进链：最早直接查库下单，暴露了超卖和一人多单； 超卖用乐观锁 CAS 解决——把"库存大于 0"写进 UPDATE 条件，检查与扣减就没有缝隙了； 一人多单先靠 synchronized 锁用户（关键是锁要包住整个事务），但集群部署失效， 于是换成分布式锁——课程先手写 SETNX 版，踩了误删、不可重入、超时释放这些坑，最后结论是生产直接用 Redisson。 但锁是串行的，吞吐上不去，所以进一步把"库存判断 + 一人一单 + 扣减"整体搬进 Redis Lua 脚本，一次原子执行， 无效请求连数据库都不碰；最后一步是异步秒杀——Lua 里直接 XADD 到 Redis Stream， 用户秒回"抢购中"，消费者组在后台 XREADGROUP 落库、XACK 确认， 失败的消息留在 pending list 重试。整个优化可以概括成一句话：把"判断资格"放进内存，把"真正下单"异步化。

追问树（面试官往哪挖，答案是什么）

追问要点
为什么用乐观锁不用悲观锁？悲观锁（for update）串行等待，吞吐差；乐观锁失败即返回，秒杀场景"失败"是常态，这样最快
为什么从版本号法改成 stock > 0？版本号下"读到的版本必须没变过"太严格，并发失败率极高；判断"还有库存"只需 stock>0，成功率高得多
synchronized 为什么要锁 intern 后的字符串？为什么锁要包住事务？intern 复用常量池对象（同用户同一把锁）；锁若在事务提交前释放，后来者查不到未提交订单 → 重复下单
为什么释放锁要 Lua？"判断是不是自己的锁 + 删除"必须原子，否则可能删掉别人的锁（超时换主场景）
Redisson 看门狗是什么？未显式指定租期时默认 30s，业务没跑完每 10s 自动续期，防止"业务没完锁先过期"
为什么这个 Lua 脚本能同时防超卖和一人多单？Redis 单线程执行脚本：三个判断和两个修改之间没有任何请求能插入
为什么用 Stream，不用 List / PubSub？List 取走即丢、无法多消费者；PubSub 不持久化；Stream 有消费者组 + ACK + pending，消息不丢可重试
消息一直失败怎么办？（课程未覆盖，展示深度）pending list 可见 + XCLAIM 转让重试；生产还要加死信队列与告警；本项目用"幂等消费 + Scheduler 兜底扫描"
