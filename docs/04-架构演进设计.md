## 2. 服务拆分设计（关键架构决策）

### 2.1 为什么"预约引擎不拆"——刻意的设计，不是偷懒

本平台的核心设计要求是「四个功能**共用一套**资源+时间片+预约模型」+「**跨资源时间冲突检测**」：

- 一次预约写入 = 校验冲突（读用户位图）+ 扣库存（改 slot）+ 写预约（写 reservation）+ 更新位图
  ——**四步必须原子完成**（当前实现见 [docs/03](03-预约核心伪代码.md)，单体本地事务保证）；
- 拆开 = 跨服务分布式事务（需 Seata；本方案明确不引入），复杂度显著上升、收益为零。

**结论**：资源、时间片、预约引擎、用户时间位图、四个业务接口，全部内聚在 `campus-service`，
用**本地事务**保证强一致。这与 12306 的 ticket-service（选座+扣库存+写票同一事务）是同一设计哲学。

### 2.2 拆什么、不拆什么

| 服务 | 职责 | 拆分依据 | 12306 对照 |
|---|---|---|---|
| gateway | JWT 鉴权、路由、限流过滤器 | 横切关注点 | 照搬 gateway-service |
| user-service | 登录（三种方式）、用户信息、配额 | 与预约域低耦合；独立伸缩 | 搬 user-service 结构 |
| campus-service | 资源/时间片/预约引擎/图书馆/场馆/讲座/选课/个人中心 | **核心域，强一致内聚** | 相当于 ticket+order 合体 |
| ~~notification-service~~ | 不拆：通知为模拟站内信，消费者直接写在 campus-service 内 | 数据量小，拆了是过度设计 | — |

### 2.3 单体 → 服务的"接缝地图"（对照当前代码）

当前单体包结构（`backend/src/main/java/com/campus/`）已经按未来服务边界组织，拆分时按包迁移即可：

| 当前包 | 去向 | 说明 |
|---|---|---|
| `framework/user`（JWT/UserContext/过滤器） | gateway + common | JWT 校验迁到网关（照搬 12306 TokenValidateGatewayFilterFactory）；`UserContext` 已用 **TransmittableThreadLocal**（为跨线程/跨服务透传预留，单体期与 ThreadLocal 等价） |
| `auth` + `user` | user-service | 登录三方式（读扩散问题见 §4.4）、用户资料、配额 |
| `resource` + `reservation` + `library` + `venue` + `lecture` + `course` | campus-service | 预约引擎全家（§2.1 不拆的理由） |
| `common`（Result/异常/错误码） | campus-common 模块 | 多模块共享 |
| `stress`（阶段 9） | 不迁移 | 单体期压测演示；演进后以脚本/网关侧压测替代 |
| `config`（拦截器/WebConfig/MyBatis 配置） | gateway / 各服务各自 | 鉴权拦截器退役（网关承担） |

## 3. MQ 场景映射（阶段 13）

| 校园场景 | 12306 对应 | Topic（前缀隔离） | 消息语义 |
|---|---|---|---|
| **预约超时未签到 → 自动取消**（回滚库存 + 释放位图 + 惩罚） | 延时关单（10 分钟未支付 → 关单 + 回滚座位） | `campus_reservation_timeout_topic`（延时消息） | 建预约时投递，delay 到"时段开始后 N 分钟" |
| **预约成功 → 站内信通知** | — | `campus_notification_topic` | 纯演示异步解耦 |
| 幂等消费 | `@MQIdempotent`"消费中/已消费"两态 Lua | 全部消费者 | 照搬 |
| ~~退课 → 候补转正~~ | — | — | **已退役**（2026-10-08：选课不设候补） |

### 3.1 无 MQ 时期的高并发方案（当前单体已具备的对照素材）

单体期的高并发处理并未"等 MQ"——已用提示词范围内工具（Redis + MySQL + @Scheduled）实现：

| 手段 | 有 MQ 的做法 | 当前单体实现 |
|---|---|---|
| 削峰 | 请求进 MQ 排队 | MySQL **原子条件更新**（`WHERE booked<capacity`）——实测 100 并发抢 10 名额 202ms（[docs/06](06-并发压测报告.md)） |
| 解耦 | 事件驱动多消费者 | 单体内部同步调用（够用） |
| 最终一致性 | 事务消息 | 单体单库本地事务（**天然一致**） |
| 延时任务 | 延时消息 | `ReservationScheduler` @Scheduled 每 60 秒（改 MQ 即本文 §3 场景） |
| 防重 | 消费幂等 | 唯一索引 + 用户行锁（压测验证，见 docs/06 §3 的死锁修复） |

### 3.2 与真 MQ 的差距（迁移时必须知道的取舍）

若曾用"轻量队列（Redis List）"过渡方案（规划文档 §8.3 的备选），其与 RocketMQ 的差距：

- **宕机丢消息**（Redis List 无持久化保证；用户可重试，业务可接受）——RocketMQ 持久化 + 重试队列解决；
- **无死信 / 无消费组语义**——RocketMQ 原生支持。

### 3.3 何时该升级到 MQ（判断标准）

升级信号（满足其一即评估）：**跨服务消费** / **可靠投递不能丢** / **多消费组** / **峰值远超单机处理能力**。
12306 的 RocketMQ 用法（延时关单 + 消费幂等）即现成升级样板。

## 4. 分库分表设计（阶段 14）

### 4.1 分片键（阶段 1 建表时已按此预留）

| 表 | 分片键 | 理由 | 12306 对照 |
|---|---|---|---|
| `t_reservation` | `user_id` | "我的预约"单分片命中；写入必带 | 订单表按 user_id（基因法） |
| `t_resource_slot` | `resource_id` | 扣减按 slot→resource 维度路由 | — |
| `t_user_time_occupancy` | `user_id`（主键 `(user_id, occupy_date)` 本身） | **冲突检测永远单分片**——不拆预约引擎之外的第二道分片友好设计 | — |
| `t_resource` / `t_lecture` / `t_course` 等 | 广播表 | 小表、查询频繁 | `t_train` 广播表 |

### 4.2 基因法（照搬 12306 订单号）

`reservation_no` 当前格式：`RES + yyyyMMdd + RediINCR 全局序列`（见 docs/03 §内部方法）。
演进后改为**雪花 ID + user_id % 1000000 拼尾** → 分片算法取尾部 6 位 →
"按单号查"与"按 user_id 查"落**同一分片**（避免广播查询）。

### 4.3 列加密

`t_user.phone / email` 用 ShardingSphere ENCRYPT（AES），配置模式照搬 12306 的 shardingsphere-config。
注意：三方式登录的唯一索引在加密列上仍可工作（密文等值查询）。

### 4.4 多方式登录的"读扩散"问题与解法（12306 实战答案）

**问题**：`t_user` 按 user_id 分片后，"用手机号登录"不知道往哪个分片查（手机号不是分片键）——广播扫描全部分片不可接受。
（当前建表时 `student_no/phone/email` 三个唯一索引即为该问题埋点，见 docs/01 §3.1。）

**12306 解法**：用**索引表** `t_user_phone(user_phone_key, user_id)` / `t_user_mail` 做"读扩散"——
手机号/邮箱登录先查索引表（按手机号分片）拿到 user_id，再按 user_id 查用户分片。
一次额外查询换取"永不广播"。

**本平台落地**：阶段 14 建 `t_user_phone` / `t_user_mail` 两张索引表（本机 12306 项目可直接对照表结构）。

### 4.5 分布式 ID

- 主键：`BIGINT AUTO_INCREMENT` 演示（schema.sql 已注明）→ 演进换**雪花算法**（Redis 生成 workId，照搬 12306 distributedid 模块）；
- 单号：Redis INCR 全局序列 → 雪花 + 基因（§4.2）；
- 现单号序列实现（`RESERVATION_SEQ_KEY` + 库内 MAX(id) 水位）保留为"单体期方案"对照素材。

## 6.5 阶段 12 实施记录（2026-10-08 · ✅ 已落地）

### 模块结构（backend/ 从单模块拆为 5 个 Maven 模块）

```
backend/
├── pom.xml            父 POM（SC 2023.0.3 + SCA 2023.0.1.0 版本管理）
├── campus-common      共享内核：Result/异常/错误码 + JWT/UserContext/BitmapUtil + 全部 DAO
│                      （重依赖 web/redis/mybatis/mysql 全部 optional —— 网关只继承纯工具部分）
├── campus-user        用户服务 :9081（auth + user + 个人中心）
├── campus-service     核心业务服务 :9082（资源/预约引擎/四业务/压测；@EnableScheduling）
└── campus-gateway     网关 :9080（路由 + JWT 鉴权 + Redis 登录态副本校验）
```

**单体 jar 留档**：`resources/legacy/campus-platform-monolith-0.0.1.jar`（阶段 15 对比基线）。

### 关键实现决策（与蓝图的差异说明）

| 项 | 落地方式 |
|---|---|
| 服务内鉴权 | **不改服务代码**：网关做第一道校验（JWT + Redis 副本，40100/40101）；Authorization 原样转发，服务内 UserTransmitFilter/LoginInterceptor 保留作**纵深防御**（直连端口行为与单体期一致，调试方便）；后续可精简 |
| 测试账号重置（跨服务） | user-service 通过 **@LoadBalanced RestClient**（服务名 campus-service）调用 campus-service 内部接口 `POST /api/internal/test-reset/{userId}`（网关不路由 /api/internal/**）——第一处真实的服务间调用 |
| DAO 归属 | 单库期全部 DAO 放 campus-common 共享（分库时按服务切开）；跨模块 DTO（MyReservation/MyCourse/Lecture/LibraryArea）随 DAO 放 common；PenaltyService 亦在 common（双服务共用） |

### 实测证据（curl 实录）

| 验证项 | 结果 |
|---|---|
| Nacos 服务清单 | `campus-gateway / campus-user / campus-service` 全部在册（`v1/ns/service/list`） |
| 网关鉴权 | 无 token → `40100`；伪造 token → `40100`；**登出后同一 token → `40101`**（Redis 副本已删，两级校验生效） |
| 全功能回归（经网关） | 统计/楼层空闲率/预约→取消/选课→退课/讲座/场馆/个人中心/压测 全部通过 |
| 故障隔离 | **停 user-service**：登录域报错，但预约/选课/日程查询经网关照常可用（3/3 成功） |
| 横向扩容 + 故障接管 | campus-service 起双实例（9082+9083）→ Nacos 显示 2 实例 → **杀掉 9082 后请求经 9083 全部成功** |
| 浏览器链路 | 5173（Vite 代理）→ 9080 网关 → 双服务，登录/个人中心全通 |

### 实施中遇到的问题与解决

1. `@LoadBalanced RestClient.Builder` 无默认 Bean（Spring Cloud 只后处理带注解的实例）→ user-service 自声明该 Bean（LoadBalancerConfig）；
2. 拆分后 `GlobalExceptionHandler`（com.campus.common.web）不在服务扫描范围 → 服务启动类 scanBasePackages 补 `com.campus.common`；
3. `PenaltyService` 在共享内核但不在 user-service 扫描范围 → 补 `com.campus.reservation` 扫描（该包在 user 侧 classpath 仅有 dao/dto/PenaltyService，安全）。

## 6.6 阶段 13 实施记录（2026-10-08 · ✅ 已落地）

### 落地内容

| 项 | 实现 |
|---|---|
| **延时消息** | 预约创建成功 → 投递 `campus_reservation_timeout_topic`（延时 = 开始+15min − now）；消费者到点判爽约（释放库存/位图 + 禁约 24h）。`ReservationScheduler`（60s 轮询）**保留为兜底**——消息丢失仍可判罚；两条路径同到只处理一次（状态校验 + 幂等键） |
| **站内信** | 预约/选课成功 → `campus_notification_topic` → 消费者落库 `t_notification` → 顶栏 🔔 铃铛（未读角标 + 抽屉列表 + 已读）——**用户可感知的新功能** |
| **@MQIdempotent** | 消费幂等切面："消费中/已消费"两态 Lua（照搬 12306）；业务异常删标记放行 MQ 重试 |
| **发送策略** | 通知发送失败仅告警不阻断主流程（生产应换事务消息）；延时发送优先 RocketMQ 5.x 自定义延时，异常降级 delayLevel + 消费侧"未到点重投递（hop+1 新幂等键）"链 |
| **演示接口** | `/api/mq/**`（网关已路由）：场景 A 发通知 / 场景 B 同消息双投（幂等）/ 场景 C 真实预约 + 8 秒延时判爽约；配「📨 MQ 演示」页现场可视化 |

### 版本踩坑记录（Boot 3 + RocketMQ）

1. `rocketmq-spring-boot 2.2.3`（12306 同款）在 **Boot 3 下不可用**：自动配置走旧版 `spring.factories`（Boot 3 只认 `AutoConfiguration.imports`）→ `RocketMQTemplate` 不装配；且其消费者代码引用 client 5.x 已迁移的 `MessageModel` 类 → 消费者容器创建失败；
2. 升级 **2.3.1**（官方 Boot 3 适配）后，其传递的 `rocketmq-client 5.1.4` 又缺 `setNamespaceV2` API → 统一钉 **client 家族 5.3.2**（与 broker 5.3.4 同代；acl 在镜像上最高 5.3.2）；
3. 结论：**rocketmq-spring 2.3.1 + client 5.3.2 + broker 5.3.4** 为可用组合（已写入父 pom dependencyManagement）。

## 6.8 阶段 16 实施记录（2026-10-10 · ✅ 已落地）：读缓存化

### 落地内容

| 组件 | 位置 | 职责 |
|---|---|---|
| `CampusCache` / `RedisCampusCache` | `campus-common/framework/cache` | Cache-Aside 门面：`get`（读透）、`safeGet`（**防击穿**：互斥回源 + 双检）、`getDirect`（绕缓存对照）、`evict/evictByPrefix`；**任何 Redis/序列化异常都降级回源** |
| `CampusBloomFilter` | 同上 | Redis 位图布隆过滤器（m/k 由公式算出，双哈希法，位操作走 Lua）；`init/add/addAll/mightContain/stats` |
| `CacheMetrics` | 同上 | 命中率 / 回源 / 防击穿抢锁与抑制 / 空值回填 / 失效 / 最近访问轨迹 |
| `CacheEvictions` | 同上 | `afterCommit` 挂载失效动作，规避"先删缓存后提交"的竞态 |
| `CacheWarmup` / `CacheController` | `campus-service/cache` | 启动预热资源 id 全集（3341 个，批量 Lua，3.5s）；观测接口 |

**接入点**：资源列表、时段可用性（+ 布隆前置拦截）、工作台概览、课程列表、教学班列表（**用户态 `mySelected` 不进缓存**）；
**写后失效**：预约创建/取消/爽约/自动驳回、选课/退课/测试重置。

### 验收证据

- 对照实验（各 30 轮）：概览 **25.63ms → 1.00ms（25.6×）**；时段 1.10ms → 2.30ms（**反例，刻意保留**，见 docs/09 §3.3）
- 布隆探针：不存在的资源 id → "一定不存在"，2ms，**不查库不查缓存**
- 缓存指标：命中率 84.52%（含压测流量）、防击穿抢锁 10 次、抑制 0 次

### 与蓝图的差异

- **未引入 Caffeine 多级缓存**：本地缓存与多实例失效广播的复杂度不划算（热点 key 量级小）
- **未引入 Canal**：用"写后失效 + 短 TTL + 对账"替代（生产化路径见 docs/09 §6）

### 新失败模式

① 缓存对象反序列化要求 DTO 有**无参构造**（`@Builder` 类需补 `@NoArgsConstructor/@AllArgsConstructor`）；
② 列表类缓存必须做"共享数据 vs 用户态"分离，否则跨用户串号；
③ 预热逐条写入会把启动拖慢十几秒（批量 Lua 修复）。

### 验收证据

- **PREDEDUCT 1000 并发**：成功 10 / Redis 拦截 990 / 放行到 DB 10 / 回补 0 / **407ms**，6 项断言全 PASS
- **活跃计数器现场**：教学班 7003 `Redis 136 = DB 136`、若干时间片 `1=1`、`4=4`，**偏差全 0**
- 对账轮次持续累加、纠偏 0 次（说明回补与释放覆盖了全部正常路径）

### 与蓝图的差异（主动决策）

- **不把 Redis 当唯一真相**：镜像 12306 的令牌桶"挡量"能力，但把最终裁决留在 MySQL（对比表见 docs/09 §1）
- **`redundancy-ratio` 默认 0**：演示口径干净；生产建议 0.02~0.05（留冗余避免少卖）
- **对账阈值而非"必须相等"**：吸收"已预扣、未提交"的在途噪音

### 新失败模式

① 冷启动/计数器过期的首个请求潮会出现"计数器不存在"竞争 → 闸门加短暂重试 + 降级直通；
② 压测复跑会被上一轮幂等键污染 → 场景开始前清理 `campus:idem:*`。

## 6.10 阶段 18 实施记录（2026-10-10 · ✅ 已落地）：锁 · 幂等 · 线程池隔离

### 落地内容

| 组件 | 职责 |
|---|---|
| `CampusLock` / `RedisCampusLock` | `SET key token NX PX ttl` + Lua 校验后删除；自旋等待带退避抖动；**Redis 异常时降级放行**（锁只保护"重复执行无害"的动作）；指标含一次即得 / 自旋获得 / 超时 / 持有者快照 |
| `@CampusIdempotent` + `CampusIdempotentAspect` | 两态 Lua（CONSUMING / CONSUMED）；SpEL 业务键（失败退化为入参 MD5）；**业务失败释放标记**允许正当重试 |
| `ThreadPoolBuilder` / `CampusThreadPools` | Builder 模式（队列形态显式三选一：有界 / 无界 / Synchronous）；具名线程工厂；**拒绝计数**；压测池按并发数注册 |
| `LockDemoService` / `ConcurrencyController` | 锁竞争现场实验（含互斥性违例检测）；`/api/concurrency/metrics` |

**应用点**：定时结算（多实例只跑一个）、对账与计数器初始化、选课/预约幂等、压测齐射线程池、缓存防击穿锁。

### 验收证据

- **LOCK 100 线程**：进入临界区 1 次 / 未抢到 99 / **互斥性违例 0** / 18ms
- **IDEMPOTENT 100 并发**：1 成功 / **99 × 40060** / booked=1、记录=1 / 49ms
- 线程池水位：`campus-stress-pool-100`、`campus-stress-pool-1000` 具名可见，拒绝计数 0（无静默丢弃）

### 与蓝图的差异（诚实说明）

**没有引入 Redisson**（原计划写的是"Redisson 分段锁"）：本项目锁的临界区都是短操作，
自研 `SET NX PX + Lua` 已覆盖全部需求，且避免为一处能力引入整套 netty 传递依赖。
`CampusLock` 是接口，**若要换 Redisson 只需替换实现类**（详见 docs/09 §3.1）。

### 新失败模式

① `directHandoff()` 最初误建无界 `LinkedBlockingQueue`（静默排队而非拒绝）——已修为显式 `QueueType`；
② 幂等窗口内的"合法重试"会被拦截：窗口设为 5 秒并把业务失败标记释放，兼顾防连点与可用性。
