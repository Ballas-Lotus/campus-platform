## 3. 服务拆分设计（关键架构决策）

### 3.1 为什么"预约引擎不拆"——这是刻意的设计，不是偷懒

提示词的核心设计要求是"四个功能**共用一套**资源+时间片+预约模型"+"**跨资源时间冲突检测**"。这两个要求意味着：

- 预约写入 = 校验冲突（读用户位图）+ 扣库存（改 slot）+ 写预约（写 reservation）+ 更新位图 —— **四步必须原子完成**（提示词 6.3 明确"必须在同一事务内"）
- 把它拆开 = 跨服务分布式事务（需 Seata，提示词明确不做，且引入会显著增加复杂度）

**结论**：资源、时间片、预约引擎、用户时间位图、四个业务接口，全部内聚在 `campus-service` 一个服务内，用**本地事务**保证强一致。这与 12306 的 ticket-service（购票引擎内聚：选座+扣库存+写票在一个事务）是同一个设计哲学。

### 3.2 拆什么、不拆什么

| 服务 | 职责 | 拆分依据 | 12306 对照 |
|---|---|---|---|
| gateway | JWT 鉴权、路由、限流过滤器 | 横切关注点 | 照搬 gateway-service |
| user-service | 登录（三种方式）、用户信息、配额 | 与预约域低耦合；独立伸缩 | 搬 user-service 结构 |
| campus-service | 资源/时间片/预约引擎/图书馆/场馆/讲座/选课/个人中心 | **核心域，强一致内聚** | 相当于 ticket+order 的合体 |
| ~~notification-service~~ | 不拆：通知为模拟站内信，消费者直接写在 campus-service 内 | 数据量小，拆了是过度设计 | — |

## 4. MQ 场景映射（照搬 12306 模式）

| ~~退课 → 触发候补第一人转正~~ | — | — | **已退役**：2026-10-08 规则——选课不设候补（满员直接拒绝），本场景取消 |

## 5. 分片键设计（阶段 14 实施；阶段 1 建表时就按此预留）

| 表 | 分片键 | 理由 | 12306 对照 |
|---|---|---|---|
| `t_reservation` | `user_id` | "我的预约"单分片命中；写入必带 user_id | 订单表按 user_id（基因法） |
| `t_resource_slot` | `resource_id` | 扣减按 slot→resource 维度路由 | — |
| `t_user_time_occupancy` | `user_id`（主键本身 `(user_id, occupy_date)`） | **冲突检测永远单分片**——这是不拆预约引擎之外的第二道分片友好设计 | — |
| `t_resource`、`t_lecture`、`t_course` 等 | 广播表（小表，全量冗余） | 查询频繁、数据量小 | `t_train` 广播表 |

**基因法（照搬 12306 订单号）**：`reservation_no` 尾部拼接 `user_id % 1000000` → 分片算法取尾部 6 位 → "按单号查"与"按 user_id 查"落**同一分片**。

**列加密（照搬）**：`t_user.phone/email` 用 ShardingSphere ENCRYPT（AES），配置模式照搬 12306 的 shardingsphere-config。

## 8. 演进步骤（阶段 12~15，含验收标准）

### 阶段 12：服务拆分 + Nacos
- backend 从单模块拆为 `campus-gateway / campus-user / campus-common / campus-service`（Maven 多模块 + Spring Cloud 2023.0.3 + SCA 2023.0.1.0）
- 三个服务注册 Nacos；网关路由 + JWT 鉴权（鉴权逻辑从单体 filter 迁移到网关，照搬 12306 的 TokenValidateGatewayFilterFactory）
- **验收**：三服务在 Nacos 控制台可见；通过网关调用登录/预约接口与单体版行为一致（对比贴 curl 结果）

### 阶段 13：MQ 化
- 超时取消 / 通知 两个场景切到 RocketMQ（第 4 节映射；退课→候补转正场景已随候补退役）
- `@MQIdempotent` 幂等消费（照搬 12306）
- **验收**：① 预约不签到 → 延时消息到点自动取消并回滚库存（贴处理前后 SQL 数据）；② 重复投递同一条消息 → 只处理一次

### 阶段 14：分库分表 + Sentinel
- ShardingSphere 按第 5 节落地（2 库 × N 表；基因法；AES 加密）
- Sentinel 对选课接口配置限流规则
- **验收**：① 按 user_id 查询单分片命中（贴 SQL 日志）；② 按 reservation_no 查询落同一分片（基因法验证）；③ 压测触发 Sentinel 限流（贴被限流的统计）

### 阶段 15：演进对比报告
- 单体版 vs 分布式版：阶段 9 的并发数据对照；轻量队列 vs RocketMQ 对照
- 写入 docs/04（演进实录）+ README
- **验收**：报告给出每一项拆分的"收益/代价"结论
