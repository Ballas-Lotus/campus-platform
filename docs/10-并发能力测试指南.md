# 10 · 并发能力测试指南

> 日期：2026-10-10　适用：本项目（校园综合服务平台）本地/同机环境
> 配套工具：`tools/loadtest.py`（零第三方依赖，Python 3.8+）

---

## 0. 先分清你在测什么（两个目标，方法完全不同）

| 目标 | 问题 | 用什么测 | 判定方式 |
|---|---|---|---|
| **正确性** | 并发下数据会不会错（超卖/重复/串号） | 前端「⚡ 并发压测」8 场景、`loadtest.py verify` | **断言**：成功数必须"恰好"等于名额数、0 系统异常 |
| **容量** | 能扛多少 QPS、延迟什么水平 | `loadtest.py read`、JMeter/wrk/k6 | **曲线**：QPS 随并发上升，直到饱和；看 P95/P99 拐点 |

> 两者不能混：容量测试不做"恰好"断言；正确性测试不关心 QPS 绝对值。

## 1. 三条测试路线

### 路线 A · 前端「⚡ 并发压测」（服务内直调，测正确性）

登录 → 菜单「🛠 工程演示」→「⚡ 并发压测」，8 个场景逐一点击：

| 场景 | 测什么 |
|---|---|
| 防超卖 / 防重复 / 位图冲突 / 选课限额 | 四道数据库防线（条件更新/行锁/唯一索引/位图） |
| Sentinel 限流 | 入口限流（40055） |
| 预扣挡量（1000 并发） | Redis 闸门：拦截/放行/DB 写入三组数字 |
| 幂等重复提交 | 接口幂等（40060） |
| 分布式锁 | 锁互斥性（违例必须为 0） |

**口径**：直接调用 Service Bean（不经 HTTP/网关），数字偏乐观，但**含真实事务、行锁、唯一索引**——测正确性最干净。

### 路线 B · `tools/loadtest.py`（走网关全链路，测容量 + 端到端正确性）

```bash
# 容量：3 个内置只读目标 × 并发梯度（默认 50/100/200，每档 10 秒）
python tools/loadtest.py read --concurrency 50,100,200 --duration 10

# 自定义目标
python tools/loadtest.py read --path "/api/resource/10001/slots?date=2026-10-11" --concurrency 200

# 端到端正确性：N 个真实用户（学号 + 123456）经网关并发抢教学班 9999（容量 10）
python tools/loadtest.py verify --users 150
```

**口径**：含网关鉴权/路由 + HTTP 网络 + 序列化，是"用户视角"的数字。

### 路线 C · 外部工具（生产级容量，需要时）

本机没有 JMeter/wrk/k6/ab。若要做到"打满/找极限/分布式压测"，装一个 k6 或 JMeter：
- 目标 URL 直接用 `tools/loadtest.py` 里同样的路径；
- **必须换一台机器当压测端**（同机会互相抢 CPU，测出的是"两者之和的上限"）。

## 2. 实测示例（2026-10-10，同机，本机 16 核）

### 2.1 读容量（走网关，命中缓存；每档 8 秒）

| 目标 | 并发 50 | 并发 100 | 并发 200 |
|---|---|---|---|
| 时段查询（热点 key，缓存命中） | 1955 QPS / P50 22ms | 3442 QPS / P50 27ms | **3529 QPS** / P50 51ms |
| 工作台概览（缓存命中） | 3890 QPS / P50 12ms | 4069 QPS / P50 22ms | **4132 QPS** / P50 43ms |
| 资源列表（缓存命中） | 3674 QPS | 3616 QPS | 3672 QPS / P50 49ms |

**读法**：100→200 并发 QPS 基本不再涨、延迟翻倍 → **已在 ~3.5k~4.1k QPS 饱和**。
饱和点是"单个 JVM + 网关 + Python 压测端挤在同一台机器"的结果，换机器打会更高。

### 2.2 端到端写竞争（`verify`，经网关）

| 条件 | 并发 | 结果 | 耗时 |
|---|---|---|---|
| 默认配置（Sentinel QPS=20） | 151 人 | 成功 **10**（=名额数）· 40055 限流 131 · 40052 名额满 10 · 系统异常 **0** | 408ms |
| **临时放开限流**（`-Dcampus.sentinel.course-select-qps=100000`） | 151 人 | 成功 **10** · 40052 141 · 系统异常 **0** | 1322ms |

**读法**：第一行说明**入口限流先挡住了大部分人**；第二行才是"纯并发路径"的真实防超卖证明——
151 个真实用户、真实 token、真实网关，最终**恰好 10 人成功**。

### 2.3 与前端压测页数据的关系

| 口径 | 同样 100 并发抢 10 个名额 | 差异原因 |
|---|---|---|
| 前端压测页（服务内直调） | ~250 ms | 不含 HTTP/网关/序列化 |
| `loadtest.py verify`（全链路） | ~1300 ms | 含 151 次登录 + HTTP 往返 + 网关鉴权 |

## 3. 十个口径陷阱（读数字前先过一遍）

1. **同机压测**：压测端与被测端抢同一台 CPU → 数字是下限；生产容量必须换机器打。
2. **链路层级**：服务内直调 ≠ 走网关 ≠ 公网入口，三层数字依次变差，报数字时必须注明口径。
3. **热点 vs 分散**：1000 人抢 1 个资源（同一行/同一分片串行）与 1000 人各抢各的，差几个数量级。
4. **限流会先挡人**：选课接口有 Sentinel（默认 QPS 20）——测容量前要么调阈值，要么把结果标注为"限流后"。
5. **幂等窗口**：同一用户 5 秒内重复请求会被 40060 挡（这是特性不是 bug）；压测脚本要清 `campus:idem:*` 或换用户。
6. **夹具要干净**：压测班 `selected` 必须为 0，且**预扣计数器要一起重置**——
   手工清库后调一次 `POST /api/prededuct/reconcile`（或丢弃计数器 `POST /api/prededuct/drop?classId=`）。
7. **计数器会"记仇"**：预扣计数器 TTL 600 秒，清库不清计数器会让下一轮全被误拦（40052 看似"满员"）。
8. **连接池是天花板**：写路径的容量由"单分片峰值并发 × 连接数"决定（外层 128 + 内层 2×128 + MySQL 500），
   不是由并发线程数决定。
9. **读有多快取决于缓存命中**：命中率 84% 与 0% 是两个世界；压测时要先"生成读流量"（缓存页有按钮）。
10. **JVM 预热**：第一轮数字普遍偏差（JIT 未编译），每档先预热 2 秒，或跑两轮取第二轮。

## 5. 测试过程中发现并修复的问题（本轮）

| # | 问题 | 怎么暴露的 | 修复 |
|---|---|---|---|
| 1 | **预扣计数器"重启后无人认领"**：手工清库后计数器残留 0 → 闸门持续误拦（最长到 TTL 600 秒） | `loadtest.py verify` 在"清库 + 重启"后出现 **151 个请求全被 40052 拒绝** | 计数器元信息随写 Redis（`campus:prededuct:meta`）+ **启动即对账**认领并纠偏（受控实验：清库后计数器 0 → 重启 → 自动回到 10） |
| 2 | **IDE 编译产物污染**：语言服务器把带编译错误的 class 写进 `target/classes`，被增量打包进 jar → 接口 50000 | `verify` 读教学班接口报 50000，日志是 `Unresolved compilation problem` | 改用 `mvn clean package`（先清 target 再全量编译），并核对接口冒烟 |

> 这两条正是"测试的价值"：**容量测试工具顺便把运维路径上的真问题挖了出来**。
> 第 1 条的完整证据链见 [docs/09 §5](09-高并发改造设计与验收.md)。

## 6. 阶段 19 新增：读模型 / 合并 Lua / 批量消费怎么测（2026-10-10 增补）

> 设计背景见 [docs/13](13-读模型与快路径升级（阶段 19）.md)。五项都可以在前端点按完成，命令行等价操作附后。

### 6.1 读模型 A/B（「🚀 缓存 → 对照实验」切到 class_stock）

- **看什么**：A 组（写后整键失效）每次读都回源、B 组（写后增量）**回源 0 次**且延迟更低；
  "写后可见"样本显示 增量 -1 后读到的 available 当场变化。
- **参考数字**（同机）：A ≈ 20ms/40 次回源 vs B ≈ 3ms/0 次回源（20 轮）。
- **陷阱**：先跑 A 组会顺带清掉余量 Hash，B 组开头自带一次预热——这是脚本内的公平起点，不是作弊。

### 6.2 毒化自愈（「🧩 教学班读模型 → 🧪 毒化一格」）

- **三步**：毒化（缓存余量被改成"真值+5"）→ 刷新状态看 **偏差 +5**、去课程列表页看**显示错值** →
  点「🧮 立即对账」立刻恢复；**不点也行——30 秒周期内的自动对账会在 ~25 秒时纠偏**（可现场掐表）。
- **口径**：这是**展示读模型**的偏差，选课的正确性由闸门 + MySQL 条件更新保证（毒化期间照样不会超卖）。

### 6.3 合并 Lua 对照（「🔒 并发控制 → ⚡ 合并 Lua」）

- **看什么**：旧路径 4 次 Redis 往返 vs 快路径 2 次，µs 级 avg/P50/P95 与倍率（本机 ≈ 1.85×）。
- **看闸门真实占比**：`GET /api/prededuct/state` 的 `fastPathSingleLua / fastPathSlow`。
- **陷阱**：压测夹具每轮会**先删计数器**再齐射 → 整波请求走"慢路径"（正确的冷启动语义），
  `fastPathSlow` 大不代表退化；想验证快路径，对**未清理的真实课程**连续 select/drop 两次看 `fastPathSingleLua` 增长。

### 6.4 批量消费（「📨 MQ 演示 → 📦 批量消费」）

- **看什么**：点「发送 50 条（一次调用）」→ 1~2 秒后刷新：**批次数明显小于消息数**（实测 4 批、avg 10.2、max 20），
  落库=50、幂等跳过 0。
- **陷阱**：必须用**突发投递**（批量接口）——逐条发时消费者实时追平，批大小恒为 1；
  低流量下批大小退化为 1 属正常（与逐条等价）。

### 6.5 窗口预热（「🧩 → 🔥 预热该课程」）

- 预热后立即读教学班列表：`pipeline 合并读` 指标增长而 `回源/重建` 不增长（数据已在 Redis）。
- 启动时会自动预热热门课程前 20（日志：`抢课窗口预热完成`）。

### 6.7 阶段 19 的三个新口径陷阱（叠加在 §3 的十条之上）

1. **余量 Hash TTL 120 秒**：服务刚重启或某课程长时间无人读时，第一次读会触发一次重建回源（一次性，正常）；
   压测"纯命中"前先读一次预热。
2. **毒化后的偏差窗口 ≤30 秒**：要现场演示"人工对账"就掐在自动对账之前点；演示"自动自愈"就等 25~30 秒。
3. **写后增量的可见性依赖 Hash 存在**：夹具把库清零后若同时清了 Hash（如压测清理），
   先发生的写只会记一条 `stockSkips`（跳过），下一次读按真值整体重建——这在压测计数里是预期行为，不是丢更新。

## 7. 万人同抢一课：怎么观察（2026-10-10 实测）

> 场景：**10,000 个不同学生、经网关、同一瞬间抢同一个教学班（容量 10）**——热点写的极限形状。
> 前置事实：种子库里正好有 **10,000 个常规学生账号**（2023~2026 级各 2,500 名，学号 `{年份}{4位序号}`），
> `tools/loadtest.py` 的账号生成规律与之一一对应。

### 7.1 三步准备

```bash
# ① 清夹具（压测班 selected 归零 + 丢弃预扣计数器 + 失效余量 Hash）
#    前端「⚡ 并发压测」跑任一选课场景即可（自带清理），或 POST /api/stress/run {"scenario":"COURSE_OVERSELL"}

# ② 放开选课限流（默认 20 QPS 会先把人挡光，看不到预扣闸门真实挡量）——阶段 19 新增热调接口，无需重启
curl -s -X POST "http://127.0.0.1:9080/api/stress/sentinel?qps=100000" -H "Authorization: $TOKEN"

# ③ 万人齐射（批量登录约 1 分钟 + 齐射几秒；工具自带"服务端观测台"，
#    跑完自动生成单文件 HTML 战报 → tools/reports/verify-report-<时间戳>.html）
python tools/loadtest.py verify --users 10000 --workers 1200
```

演示结束后恢复：`POST /api/stress/sentinel?qps=20` + 清理夹具。

### 7.2 观察什么（工具输出的「服务端观测」+ 三个前端页面）

| 观测量 | 在哪看 | 万人齐射的预期形状 |
|---|---|---|
| **成功数 = 容量** | 工具输出 + 教学班列表显示 | 恰好 **10**（多一个少一个都是事故） |
| **闸门挡量** | 工具输出 `闸门·Redis拦截/放行` | 拦截 + 放行 **= 全部到达数**（算术必须闭合） |
| 慢路径占比 | 工具输出 `闸门·慢路径` | 只有冷启动第一波（实测 +17），其余全走合并快路径 |
| 回补 / 降级 | 工具输出 `闸门·回补 / 降级直通` | **0 / 0**（说明没走到"少卖"与"Redis 故障"路径） |
| 缓存余量增量 | 工具输出 `缓存·余量增量` | **= 成功数**（10 个成功者各 -1） |
| 限流拦截 | 工具输出 `限流·累计拦截` | 放开阈值后应为 **0**（由闸门挡，而不是限流挡） |
| 现场计数器 | 前端「🔥 预扣闸门」 | Redis 预计数 = DB 真值（drift 0）、拦截率 ~99.9% |
| 日志 | `tail -f /d/tmp/campus-logs/service.log` | 每笔拦截一行 40052；**这正是日志量被压的时刻**（万人 ≈ 1 万行，生产需采样） |

### 7.3 实测结果与一个真实发现（连接风暴）

| | 第一轮（1200 连接与请求同瞬间开火） | 第二轮（**先预建连接、再齐射**） |
|---|---|---|
| 成功 / 挡回 | 10 / 9734 | 10 / **9890** |
| 系统异常 | **157 个 CONN_ERR**（1.6% 请求根本没到达业务层） | **0** |
| 延迟 P95 / P99 | 2038ms / 3294ms | **588ms / 698ms** |
| 结论 | FAIL（入口丢连接） | **PASS**（恰好 10、0 超卖、0 异常） |

> **发现**：1 万个请求里丢的 157 个，不是闸门问题也不是数据库问题——**连接建立风暴**本身是独立的一层
> （算数验证：`拦截 + 放行 = 9744 = 9900 − 157`，丢的请求从未到达业务层；日志里也没有任何对应异常）。
> 把"连接建立"与"请求齐射"分开后，连接错误归零、尾延迟下降 ~5 倍。
> 真实系统里这一层靠 **LB（LVS/Nginx）+ 多实例 + 连接预建/长连接** 消化——单机 Tomcat 直扛万人连接
> 本来就是超配，这正是"向 10w/100w 演进"要解决的入口问题。

### 7.4 万人场景的口径纪律（叠加在 §6.7 之上）

1. **"同时"的物理上限**：同机单进程做不到严格齐射，工具输出里的「发起窗口」（实测 ~3s）就是全部请求的到达跨度——
   服务端要观察的东西（精确挡量 / 恰好成交 / 零超卖）与窗口宽度无关；
2. **登录阶段约 1 分钟**：1 万次真实登录（含 BCrypt 校验）是压测的固定成本，不是被测目标；
   登录失败率 ~1%（9900/10000）属正常（并发下的超时重试），不影响断言；
3. **Windows 客户端端口**：批量登录会留下 ~1 万个 TIME_WAIT，密集复跑（几分钟内）可能造成客户端端口紧张——
   两轮万人测试之间建议间隔 2 分钟以上，或降低 `--workers`；
4. **夹具必须先清**：上一轮 10 个成功者不清掉，下一轮"成功数 = 容量"的断言必然失败（这是测试污染，不是 bug）。
