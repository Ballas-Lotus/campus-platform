# 06 · 并发压测报告（阶段 9）

> 日期：2026-10-08　场景：防超卖 / 防重复 / 位图冲突 / 选课限额（4 个）
> 入口：前端「⚡ 并发压测」页（`/stress`）或 `POST /api/stress/run`

## 1. 方法

- **服务端线程池齐射**：`CountDownLatch` 栅栏对齐后同时发起 N 个**真实事务请求**
  （调用与 HTTP 接口相同的 Service Bean，事务/行锁/唯一索引全部真实生效）。
- **真实数据库**：MySQL 8（InnoDB），连接池 20 —— 并发事务直接竞争行锁与唯一索引。
- **时延口径**：服务层一次调用（含事务提交）的耗时，非 HTTP RTT。
- **自动清理**：每轮压测结束后删除本轮写入（预约/选课/位图/配额），**不污染业务数据**；
  压测夹具独立（见 §5）。
- **断言式验收**：每个场景内置数据核对断言（成功数、booked/selected 计数、总账自洽、
  无系统异常），全部通过 = PASS。

## 2. 四大场景与结果（修复后复测）

| # | 场景 | 并发 | 预期 | 实测结果 | 时延 |
|---|---|---|---|---|---|
| 1 | **防超卖** OVERSELL：100 个不同用户并发抢专用场地 10 个名额 | 100 | 恰好 10 成功 | ✅ 成功 **10**，失败 90 × `40024` 名额已满；booked=10=有效预约数 | **202ms** / P50 153ms / P95 195ms |
| 2 | **防重复** DUPLICATE：同一预约并发提交 50 次 | 50 | 恰好 1 成功 | ✅ 成功 **1**，失败 49 × `40023` 时间冲突；booked=1，记录=1 | **97ms** / P50 58ms / P95 93ms |
| 3 | **位图冲突** BITMAP：同一用户并发抢 50 个座位的同一时段 | 50 | 恰好 1 成功 | ✅ 成功 **1**，失败 49 × `40023`；当日位图 = 该时段 bits（无丢更新） | **84ms** / P50 52ms / P95 80ms |
| 4 | **选课限额** COURSE_OVERSELL：100 人抢压测班 10 个课额 | 100 | 恰好 10 成功 | ✅ 成功 **10**，失败 90 × `40052` 课额已满；selected=10=选课记录数 | **159ms** / P50 111ms / P95 149ms |

> 热点行（同一片/同一教学班）的串行化由 InnoDB 行锁排队，单事务尾部仅数毫秒。

## 3. 压测发现并修复的缺陷：同一用户"当日首约"并发死锁

### 3.1 现象（修复前实测）

DUPLICATE / BITMAP 场景的失败分布中混入**大量非业务异常**：

| 场景 | 修复前失败分布 | 修复后 |
|---|---|---|
| DUPLICATE | `40023` × 33 + **`DeadlockLoserDataAccessException` × 16** | `40023` × 49（全干净） |
| BITMAP | `40023` × 6 + `40024` × 5 + **`DeadlockLoser` × 38** | `40023` × 49（全干净） |

用户视角：并发双击"预约"时，一个成功、另一个（排后面的）可能返回
**"系统繁忙，请稍后重试"**（50000），而不是友好的"该时段与你的已有安排冲突"。

### 3.2 根因

`t_user_time_occupancy` 的位图行用 `SELECT ... FOR UPDATE` 做"读-改-写"防丢更新——
但**对"当日尚无位图行"的用户，不存在的行锁不住**（InnoDB RR 下只加间隙锁）：

1. 并发请求 A、B 同时 `selectForUpdate` → 都读不到行 → **都通过冲突检测**；
2. A、B 互相持有同一间隙的 gap 锁，各自要执行 INSERT（插入意向锁）→
   **插入意向锁 vs 间隙锁互斥 → 死锁** → MySQL 随机回滚一方（DeadlockLoser）。

结果正确性侥幸被"死锁回滚"兜住（实测未发生双订），但错误面（系统繁忙）与吞吐
（重试/回滚）都不可接受；且这是**未被单线程正确性测试覆盖的隐患**。

### 3.3 修复

`ReservationService.create()` 在位图操作前增加 **t_user 行锁**
（`SELECT id FROM t_user WHERE id=? FOR UPDATE`，与选课 `CourseService` 同款）：

- 同一用户的预约/取消/选课操作**全部串行化** → 间隙锁互撞与死锁从根上消失；
- 后续请求在锁释放后读到已提交的位图行，得到**干净的 `40023` 业务拒绝**；
- 不同用户之间无任何竞争（锁的是各自用户行），吞吐不受影响。

### 3.4 修复后复测

死锁清零（`EX:` 计 0），全部失败均为业务拒绝；断言"无系统异常（失败均为业务拒绝）"
由 FAIL 转 PASS；DUPLICATE 场景总耗时 153ms → 115ms。

### 3.5 第二个缺陷（浏览器实测发现）：压测执行器"栅栏空等 10 秒"

**现象**：curl 直连全部 PASS，但**浏览器里防超卖/选课限额"经常失败"**（防重复/位图冲突正常）。

**根因链**：

1. 压测执行器线程池上限 64，而这两个场景要发 100 个任务——后 36 个任务**没有线程可用**，
   迟迟无法"就位"（countDown 栅栏）；
2. 栅栏 `ready.await(10s)` 等不齐 → **每次空等到 10 秒超时才开闸**，服务端总耗时被拉长到 ~10.2s；
3. **前端 axios 全局超时恰好 10 秒** → 浏览器在服务端返回前掐断请求 → 页面显示失败。

**修复**（两层）：

- 服务端：线程池大小 ≥ 并发数（上限 128，100 并发即 100 线程），栅栏瞬时对齐；
  总耗时改为从"齐射开闸"起算。修复后真实执行仅 **202ms / 159ms**（此前 98% 是空等）；
- 前端：压测接口单独放宽超时到 60 秒（全局默认 10 秒对长事务场景不适用）。

**实测对比**：OVERSELL 10,227ms → **202ms**；COURSE_OVERSELL 10,190ms → **159ms**；
浏览器端 4 场景全部即时返回 PASS。

## 6. 复现方式

```bash
# 登录拿 token（accessToken 自带 "Bearer " 前缀，直接作为 Authorization 头）
TOKEN=$(curl -s -X POST http://127.0.0.1:8081/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"account":"test","password":"123456"}' | sed -E 's/.*"accessToken":"([^"]+)".*/\1/')

# 四个场景（也可在前端「⚡ 并发压测」页一键执行）
for S in OVERSELL DUPLICATE BITMAP COURSE_OVERSELL; do
  curl -s -X POST http://127.0.0.1:8081/api/stress/run \
    -H "Authorization: $TOKEN" -H "Content-Type: application/json" \
    -d "{\"scenario\":\"$S\"}"
done
```

## 7. 局限说明（诚实口径）

- 本压测为**单进程线程池并发**（验证正确性/锁行为），非跨机分布式压测（JMeter 集群）；
- 时延含连接池排队（20 连接 × 100 并发），是"竞争下的时延上界"，非空载基准；
- 未覆盖场景：跨用户抢同一**图书馆座位片**的超卖（与场景 1 同一防线，机理相同，抽样验证从略）。

## 8. 阶段 14 复测：分库分表后（2026-10-08）

同一套场景在**分片形态**（2 库 × 4 片 = 8 分片 + ShardingSphere-JDBC）下复测，
并与**单体留档 jar**（`resources/legacy/`，:8081，连 `campus_platform`）同机对照（各 2 轮取最好）：

| 场景 | 单体（best） | 分片（best） | 倍数 | 断言 |
|---|---|---|---|---|
| OVERSELL | 184 ms | 371 ms | 2.0× | 两侧均 PASS（10/10、booked=10、账实一致） |
| DUPLICATE | 82 ms | 129 ms | 1.6× | 两侧均 PASS（1/50） |
| BITMAP | 82 ms | 122 ms | 1.5× | 两侧均 PASS（1/50） |
| COURSE_OVERSELL | 168 ms | 348 ms | 2.1× | 两侧均 PASS（10/10） |
| **RATE_LIMIT（新增）** | — | 172 ms | — | **PASS**：120 并发 → 99 限流（40055）/ 10 抢到 / 0 系统异常 |

> 复跑入口：前端「📈 演进对比」页一键双侧对照（各侧多轮取最好）。

**结论**：分片后**正确性断言零妥协**；延迟代价 +50%~90%（解析/路由 + 连接放大 + 热点分片串行 + 跨库双写）。

**复测暴露的新失败模式**（详见 [docs/07 §3](07-架构演进对比报告.md)）：
① 热点分片连接放大——100 并发抢同一资源 → 全部路由同一分片，双池 20/10 直接打爆
（先 `CannotCreateTransactionException` 后 `Hikari time out`）；解法：外层 128 + 内层 2×128 + MySQL `max-connections=500`，
容量规划按**单分片峰值并发**而非总并发；
② 分片列禁 UPDATE（`updateById` 带 `user_id`/`reservation_no` → `Can not update sharding value`）；
③ 合并结果集缺 `java.time` 转换；④ snakeyaml 2.x 冲突（补丁类，见 docs/04 §6.7）。

## 9. 阶段 16~18 复测：读缓存化 + 预扣闸门 + 并发控制（2026-10-10）

改造设计见 [docs/09](09-高并发改造设计与验收.md)。本轮新增 3 个场景，并在同机复跑全部老场景。

### 9.1 新增场景

| 场景 | 并发 | 预期 | 实测 | 时延 |
|---|---|---|---|---|
| **PREDEDUCT 预扣挡量** | **1000** | 只有等于名额数的请求进数据库 | ✅ **Redis 拦截 990 / 放行 10 / DB 只写 10 行**（290 也被幂等前置拦截的场景见 §9.3） | **407 ms**（p50 345 / p95 367） |
| **IDEMPOTENT 幂等重复提交** | 100 | 同一请求只生效一次 | ✅ 成功 **1**，**99 × `40060`**（幂等拦截），booked=1、记录=1 | **49 ms**（p50 8ms） |
| **LOCK 分布式锁** | 100 | 同一时刻只有一个进入者 | ✅ 进入临界区 **1**、未抢到 99、**互斥性违例 0** | **18 ms** |

> PREDEDUCT 的现场口径：`Redis 拦截` 由闸门指标累加差值得到（不是失败码统计），
> 断言"拦截 = 请求数 − 名额数"与"放行 = 名额数"同时成立，才算闸门真的在做精确挡量。

### 9.2 老场景复跑（各 2~3 轮取最好）

| 场景 | 阶段 14（分片后） | 阶段 18（本次） | 变化 |
|---|---|---|---|
| OVERSELL | 371 ms | 416 ms | +12%（写路径多了缓存失效/预扣归还的 Redis 往返，属噪声区间） |
| DUPLICATE | 129 ms | 147 ms | +14%（同上） |
| BITMAP | 122 ms | 131 ms | +7% |
| COURSE_OVERSELL | 348 ms | **244 ms** | **−30%**：预扣闸门把 90 个必败请求挡在数据库之前 |
| RATE_LIMIT | 172 ms | 239 ms | 120 并发 → 95 × `40055` 限流 / 10 成功 / 0 系统异常 |

### 9.3 缓存对照实验（各 30 轮）

```
工作台概览（6 次聚合）：无缓存 avg 25.63ms / p95 35ms → 有缓存 avg 1.00ms / p95 0ms    （25.6×）
单资源时段（单分片）：  无缓存 avg  1.10ms / p95  2ms → 有缓存 avg  2.30ms / p95 4ms    （反例：更慢）
```

> **反例是刻意保留的**：缓存往返 + 反序列化的开销（约 2ms）可能超过一次极廉价的回源（1.1ms）。
> 时段查询保留缓存的理由不是单请求更快，而是**高并发下把数据库连接占用从 N 次降到 1 次**。
> 判断依据见 [docs/09 §3.3](09-高并发改造设计与验收.md)。

### 9.4 结论

1. **正确性零妥协**：8 个场景断言全 PASS，回归 46 项全绿，服务日志 0 ERROR；
2. **写热点吞吐未退化**，选课限额场景反而**快 30%**（前置挡量的直接收益）；
3. **新增的挡量能力是量级提升**：改造前 1000 并发会全部打到数据库（连接池 128 先爆），
   现在 99% 在 Redis 一层被拒（拒绝成本 μs 级）；
4. 复跑期间发现并修复 4 个真实缺陷（线程池队列形态、凌晨演示时段、压测幂等残留、布隆预热耗时），
   见 [docs/09 §5](09-高并发改造设计与验收.md)。
