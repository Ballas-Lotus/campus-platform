# 09 · 高并发改造设计与验收（阶段 16 ~ 18）

> 日期：2026-10-10　目标：**把架构做到 12306 那样"读缓存化 + 写前置挡量"的高并发设计**，
> 同时不牺牲已有正确性（数据库唯一索引 + 原子条件更新始终是最终真相）。
>
> 入口：前端三张新页面「🚀 缓存」（/cache）「🔥 预扣闸门」(/prededuct)「🔒 并发控制」(/concurrency)，
> 以及「⚡ 并发压测」页新增的 3 个场景。

---

## 1. 先定目标：为什么不是照抄 12306

12306 的高并发由两根柱子撑起：**读路径全内存组装**、**写路径 Redis 令牌桶前置挡量**。
本项目对齐这两根柱子，但在"Redis 扮演什么角色"上做了一个**更保守的选择**：

| 维度 | 12306 令牌桶 | 本项目预扣闸门 |
|---|---|---|
| Redis 角色 | **唯一真相**（数据库无唯一索引兜底，靠"删桶重建"自愈） | **预计数**（真相始终在 MySQL：唯一索引 + 条件更新） |
| Redis 不可用 | 取不到令牌 → **购票不可用** | 自动**降级直通数据库**（只损失性能，不损失正确性） |
| 状态漂移 | 删桶全量重建 | 30 秒**对账纠偏**（只把计数器拉回真值，不打断在途请求） |
| 跨段扣减 | 区间扣减（跨站全成或全败） | 跨时间片 all-or-nothing（同一 Lua 模式） |

> 结论：**能挡的量一样（都在 Redis 之前拒绝），但正确性不再押在 Redis 上**。
> 这是本项目相对 12306 那个学习版实现的**加分项**，也是面试时最值得讲的一句。

## 3. 关键技术决策（连同理由与实测）

### 3.1 分布式锁：自研而不是 Redisson（诚实说明）

用 `SET key token NX PX ttl` + Lua"校验 token 后删除"自研实现，**未引入 Redisson**，理由：

1. 本项目锁的临界区都极短（缓存防击穿回源 / 定时结算防重 / 计数器初始化），不需要可重入、看门狗续期、公平锁；
2. 不新增重量级传递依赖（Redisson 会带入 netty 一整套），减少与 RocketMQ/Sentinel 现有 netty 版本的冲突面；
3. `SET NX PX + Lua 释放`本身就是 Redis 官方推荐的锁写法，语义透明、可压测。

> **想换 Redisson 也很容易**：`CampusLock` 是接口，`RedisCampusLock` 是唯一实现，换实现类即可
> （`RLock`/`RBloomFilter` 语义与本项目自研版一一对应）。**若简历上要写 Redisson，改这一处即可。**

### 3.2 布隆过滤器：参数是算出来的，不是拍的

- 公式：`m = -n·ln p /(ln2)²`、`k = (m/n)·ln2`，取 `n = 20,000`（资源 id 全集余量 6×）、`p = 1%`
- 实算：**m = 191,702 位（≈24 KB）、k = 7**；位操作走 Lua，一次往返完成 7 次 `SETBIT`/`GETBIT`
- 实测：插入 3,341 个资源 id，位图填充率 **11.49%**，按填充率反推误判率 ≈ 0
- 语义边界：布隆说"不存在"**一定**不存在（可直接拒绝，不查库不查缓存）；说"可能存在"仍需回源确认

### 3.3 缓存对象的选择：回源成本必须大于缓存往返成本（**这条有实测反例**）

| 读路径 | 无缓存 | 有缓存 | 结论 |
|---|---|---|---|
| 工作台概览（6 次 count 聚合，跨广播表/分片表） | **25.63 ms**（p95 35ms） | **1.0 ms**（p95 0ms） | ✅ 缓存 **25×**，非常划算 |
| 单资源时段（单分片、走索引、14 行） | 1.1 ms | 2.3 ms | ❌ **缓存反而慢 1ms**：往返 + 反序列化开销 > 回源开销 |

> **诚实的结论**：缓存不是免费的午餐。时段查询保留缓存**不是因为单请求更快，而是因为它是最热的读路径**
> ——1000 个并发读同一资源时，缓存把数据库连接占用从 1000 次降到 1 次（连接池才是稀缺资源）。
> 这条"看回源成本、看并发压力、不看直觉"的判断，比"我加了缓存"本身更值钱。

### 3.4 写后失效的时序：挂在事务提交之后

`CacheEvictions.afterCommit(...)`（`TransactionSynchronization`）——避免经典竞态：

```
T1 更新数据库（未提交） → T1 删缓存 → T2 回源读到旧值写回缓存 → T1 提交
→ 缓存里长期是旧值（直到 TTL 到期）
```

### 3.5 用户态不进缓存（课程列表的 `mySelected` 分离）

教学班余量是共享数据（进缓存），"我是否已选"是用户态（**每次实时查**）。
若两者一起缓存，A 用户会看到 B 用户的"已选"标记——这是列表类缓存最容易踩的坑。

### 3.6 预扣的三条防线与参数（`campus.prededuct.*`）

| 防线 | 机制 | 为什么 |
|---|---|---|
| **预扣** | Lua 内"先全部校验、再逐个扣减" | 多时间片预约天然**全成或全败**，不会出现"扣了 1 片、另 1 片没扣" |
| **回补** | 数据库拒绝（冲突/真满）时 `INCRBY` 归还 | 不回补就会**少卖**（Redis 扣了、库里其实空着） |
| **对账自愈** | 每 30 秒比对 Redis 与 DB 真值，偏差超阈值即纠偏 | 兜住进程崩溃导致的漏回补；多实例下用分布式锁只跑一个 |

参数选择：`redundancy-ratio = 0`（演示口径干净；**生产建议 0.02~0.05**，留冗余避免"少卖"）、
`drift-threshold = 5`（**吸收"已预扣、未提交"的在途噪音**，否则对账会误纠在途请求）、
TTL 600 秒（过期后按 DB 真值懒加载重建）、Redis 异常自动降级直通。

### 3.7 闸门必须放在事务之外（连接池才是瓶颈）

Spring 的 `@Transactional` 在方法进入时就占一条数据库连接。1000 个并发若都先开事务再判定，
连接池（128）会先被打爆——预扣放在事务之前，**990 个被拒请求根本不向连接池借连接**。
这也是"闸门类"（`CourseSelectGate` / `ReservationGate`）独立于 Service 存在的原因。

## 4. 实测数据（2026-10-10，本机同环境）

### 4.1 缓存对照实验（各 30 轮）

```
工作台概览：无缓存 avg 25.63ms / p95 35ms  →  有缓存 avg 1.00ms / p95 0ms   （25.6×）
单资源时段：无缓存 avg  1.10ms / p95  2ms  →  有缓存 avg 2.30ms / p95 4ms   （反例，见 §3.3）
缓存运行指标：命中 71 / 未命中 13 / 命中率 84.52% / 回源 13 / 防击穿抢锁 10 / 写后失效 260
```

### 4.2 预扣闸门（新增场景 PREDEDUCT）

| 并发 | 成功 | Redis 拦截 | 放行到数据库 | 回补 | 总耗时 | 断言 |
|---|---|---|---|---|---|---|
| **1000** | 10 | **990** | **10** | 0 | **281 ~ 550 ms**（多轮波动，含 1000 线程创建） | 6 项全 PASS |

> 对照改造前：这 1000 个请求会**全部打到数据库**（连接池 128 先被打爆）。
> 现在 99% 的请求在 Redis 一层就被拒绝，且拒绝成本是内存往返（μs 级）。

### 4.3 接口幂等（IDEMPOTENT）与分布式锁（LOCK）

| 场景 | 请求 | 结果 | 耗时 |
|---|---|---|---|
| 幂等：同一用户并发提交同一预约 100 次 | 100 | **1 成功 / 99 × 40060**，booked=1、记录=1 | 48 ms（p50 8ms） |
| 锁：100 线程同抢一把锁 | 100 | **进入临界区 1 次 / 未抢到 99 / 互斥性违例 0** | 10 ~ 38 ms |

> 8 个场景在最终构建上一次性复跑的结果：全部 PASS（OVERSELL 557 / DUPLICATE 164 / BITMAP 144 /
> COURSE_OVERSELL 249 / RATE_LIMIT 228 / PREDEDUCT 281 / IDEMPOTENT 48 / LOCK 10 ms）。

## 5. 本次改造中发现并修复的真实缺陷（4 个）

| # | 缺陷 | 现象 | 修复 |
|---|---|---|---|
| 1 | 线程池 Builder 的 `directHandoff()` **实际建的是无界 `LinkedBlockingQueue`** | 压测池"不排队"变成"静默排队到 OOM 才暴露"，拒绝计数永远 0 | 显式引入 `QueueType`（BOUNDED / UNBOUNDED / SYNCHRONOUS） |
| 2 | MQ 超时演示在**凌晨 0~8 点**找不到时段 | `nextWholeHourAtLeast5MinLater` 只夹取了"≥22 点顺延"，漏了 `<8 点`，凌晨演示报"找不到可用的演示时段" | 两侧都夹取到开放时段 08:00~22:00 |
| 3 | 压测**复跑被上一轮幂等键污染** | 上一轮的 `CONSUMED` 把本轮首笔也挡掉，PREDEDUCT 的"拦截 = 请求 − 名额"断言偏移 | 每轮场景开始前清理 `campus:idem:*` |
| 4 | 布隆预热**逐条写入**（3000+ 次双往返） | 启动多花 **12.1 秒** | 批量 `addAll`（分块 Lua）→ **3.5 秒** |
| 5 | **预扣计数器"重启后无人认领"**（2026-10-10 由并发测试工具发现） | 手工清库 + 重启后，计数器残留 0 不在注册表里 → 对账不管它 → **151 个并发请求全部被误拦**（40052），最长持续到 TTL 600 秒 | 元信息随计数器写 Redis（`campus:prededuct:meta`）+ **启动即对账**（`ApplicationReadyEvent`）认领并纠偏——受控实验：清库后计数器 0 → 重启 → **自动回到真值 10** |
| 6 | **IDE 编译产物污染**（2026-10-10 由并发测试工具发现） | 语言服务器把带编译错误的 class 写进 `target/classes`，被增量打包 → 接口 50000（日志：`Unresolved compilation problem`） | 构建固定用 `mvn clean package`（先清 target 再全量编译）；接口冒烟作为验收第一步 |

（另有 2 个集成期问题：`CacheMetrics` 未注册为 Bean 导致启动失败；预扣计数器冷启动竞争 → 闸门加"短暂重试 + 降级直通"。）

## 6. 与 12306 的距离还剩多少（诚实版）

**已对齐**：读缓存化（safeGet 防击穿 / 布隆防穿透 / 空值回填）、Lua 原子预扣、跨段全成或全败、
延迟消息、消费幂等、分布式 ID 基因法、分库分表、列加密、读扩散索引表、限流、定时任务防重。

**仍缺（生产化清单）**：

| 缺口 | 12306 的做法 | 本项目的现状与生产路径 |
|---|---|---|
| 缓存与 DB 增量同步 | Canal → RocketMQ → 增量刷新 | 用"写后失效 + 短 TTL + 对账"，够用但峰值下有窗口 |
| 动态线程池 | Hippo4j（Nacos 配置中心动态调参） | 自研 Builder + 注册表 + 水位观测（无动态调参） |
| 分片规模 | 2×32 = 64 片/表 | 2×4 = 8 片（基因法已验证 1000000 % 64 == 0，扩容无缝） |
| 读写分离 / Redis 集群 | 主从 + 哨兵 | 单机（文档已给生产路径） |
| MQ 死信与积压预案 | 重试 Topic + 死信 + 告警 | 消费端幂等 + Scheduler 兜底，未做死信队列 |
| 压测工具 | JMeter（仓库内无脚本） | 内置断言式压测页（**可复跑、有报告**，这一点本项目更强） |

**性能口径**：写热点落库吞吐两者同一量级（都受"最终裁决点"约束）；读路径在缓存化之后已拉平到同一量级
（对比推算见 `docs/07`）。
