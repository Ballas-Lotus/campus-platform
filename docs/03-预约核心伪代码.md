## 0. 总览：一次预约要穿过五道闸门

```
                用户维度                      资源维度
       ┌───────────────────────┐    ┌──────────────────────────┐
       │  ① 位图冲突检测        │    │  ② 逐片原子扣减（防超卖）  │
       │  (96 格 × 15 分钟)     │    │  UPDATE ... WHERE booked  │
       │  SELECT ... FOR UPDATE │    │         < capacity        │
       └───────────┬───────────┘    └────────────┬─────────────┘
                   │  同一事务（任一步失败 → 全部回滚）        │
   ③ 写预约主表（uk 兜底）→ ④ 合并位图 → ⑤ 配额 ±1

   注：进入 ① 之前先取 t_user 行锁（阶段 9 压测修复——消除"当日首约"的间隙锁死锁，见 §1.5）
```

## 1. 创建预约（区间独占 / 容量计数通用）

```java
@Transactional(rollbackFor = Exception.class)
create(resourceId, slotDate, startTime, endTime):
    userId ← UserContext.getUserId()

    ── 闸门 0：静态校验（无锁，快速失败）──────────────
    资源 ← 查 t_resource；必须存在 && status=1 && 类型 ∈ {LIBRARY_SEAT, VENUE, LECTURE}
    时段：整点 && 图书馆 1~4 小时 / 体育馆 1~3 小时 && 08:00~22:00 内
    日期：仅"当天与明天"（图书馆/体育馆）；讲座报名为"开始前 7 天"窗口，由讲座入口另行把关

    ── 闸门 1：配额（图书馆不限次；体育馆每周 4 次）────
    仅体育馆：行 ← 查 t_user_quota(user, 'VENUE_WEEKLY', 本周一)
    若 行.used ≥ 4 → 拒绝 40025（"本周体育馆预约次数已达上限"）
    # 行不存在时：本事务末尾新建（并发冲突时改为重读 +1）；取消回退次数，爽约不回退

    ── 闸门 1.5：t_user 行锁（串行化"同一用户"；2026-10-08 阶段 9 压测修复）──
    SELECT id FROM t_user WHERE id=? FOR UPDATE
    # 位图行 FOR UPDATE 对"当日尚无位图行"的用户锁不住（不存在的行只加间隙锁），
    # 同一用户并发首约时事务间"插入意向锁 vs 间隙锁"互撞死锁（DeadlockLoser → 系统繁忙）。
    # 先锁用户行 → 该用户的**并发预约创建**全部串行化，死锁与丢更新从根上消除（与选课同款）。

    ── 闸门 2：位图冲突检测（用户维度，行级悲观锁）────
    newBits ← BitmapUtil.toBitmap(startTime, endTime)   # 96 bit：bit i = 第 i 个 15 分钟格
    占用行 ← SELECT * FROM t_user_time_occupancy
             WHERE user_id=? AND occupy_date=? FOR UPDATE     # ← 锁行，防并发丢更新
    若 占用行 ≠ null 且 (占用行.bitmap AND newBits) ≠ 0 → 拒绝 40023（与已有安排冲突）

    ── 闸门 3：逐片原子扣减（资源维度，数据库原子性防超卖）──
    片集 ← 查 t_resource_slot(resource_id, slot_date)     # 命中 uk 唯一索引前缀
    目标片 ← 片集.filter( startTime ≤ 片.startTime < endTime )
    断言 目标片数量 = 小时数（讲座为"整场一格"，恒等于 1）
    for 片 in 目标片:
        rows ← UPDATE t_resource_slot
               SET booked = booked + 1, version = version + 1
               WHERE id = 片.id AND booked < 片.capacity      # ← 唯一的超卖防线
        if rows = 0: 抛 40024（手慢了）
        # 已扣的片由事务回滚自动恢复 —— "全部成功或全部失败"

    ── 闸门 4：写预约主表（唯一索引兜底）─────────────
    单号 ← nextReservationNo()      # 阶段 14 起：RES + 雪花ID + 6 位基因（user_id % 1000000，见 docs/04 §4.2）
                                    #（单体期方案：Redis 全局 INCR + 库内 MAX(id) 水位，保留为对照素材）
    INSERT t_reservation(..., slot_id=目标片[0].id, time_bitmap=newBits,
                         status = APPROVED)
        # 2026-10-08 起无人工审批：规则校验全过即生效（机器自动处理）
    若 DuplicateKeyException → 40026
        # uk_reservation_no：业务单号幂等（防重复提交）
        # uk_reserved(slot_id, user_id, active_key)：同片同用户最多一条"有效"预约

    ── 闸门 5：更新位图 + 配额 ────────────────────
    if 占用行 = null:  INSERT t_user_time_occupancy(user, date, bitmap=newBits, version=1)
    else:              UPDATE ... SET bitmap = 占用行.bitmap OR newBits, version = version + 1
    assert 影响行数 = 1
    仅体育馆：配额行.used + 1（或新建）

    return 预约详情
```

### 1.1 两个关键设计

| 设计 | 为什么 |
|---|---|
| **FOR UPDATE 锁位图行** | 同一用户并发提交两笔不冲突时段的预约：不加锁会"读-改-写"丢更新（两个事务都读到旧位图，后写覆盖先写）。悲观锁是最直观的正确解 |
| **`WHERE booked < capacity` 而非先查后改** | 先 `SELECT` 判断再 `UPDATE` 在并发下必超卖（检查与更新之间有窗口）。让**数据库行锁 + 条件更新**做唯一裁判 |

### 1.2 位图为什么用 BigInteger

96 格 > 64 bit，`long` 放不下；`BigInteger` 天然支持任意精度位运算：

```
14:00~16:00 → bit 56..63 → hex "00000000ff00000000000000"（24 字符，与种子数据同格式）
冲突判断: (a AND b) != 0       取消释放: occupancy AND NOT bits
```

## 2. 取消预约（创建的反向操作，同一事务）

```java
@Transactional(rollbackFor = Exception.class)
cancel(reservationId):
    预约 ← 查 t_reservation；不存在 → 40027
    assert 预约.userId = 当前用户      → 否则 40028
    assert 状态 ∈ {PENDING, APPROVED}  → 否则 40027（已完成/已取消/爽约不可再取消）
    assert 预约开始时刻 > now         → 否则 40027（已开始的时段不可取消）

    for 片 in 覆盖的片:
        UPDATE t_resource_slot SET booked = booked - 1, version = version + 1
        WHERE id=? AND booked > 0           # 防负库存

    占用行 ← SELECT ... FOR UPDATE
    UPDATE t_user_time_occupancy SET bitmap = 占用行.bitmap AND NOT 预约位图

    UPDATE t_reservation SET status='CANCELLED', remark='用户取消'
        # 不物理删除：生命周期由 status 表达（docs/01 §2）
        # active_key 生成列随之变为 NULL → uk_reserved 释放 → 该片可再约

    仅体育馆：配额 -1（不为负；取消回退，爽约不回退）
```

> **"取消 → 再约 → 再取消"为什么合法**：uk_reserved 的第三列是**生成列** active_key，
> 仅 PENDING/APPROVED 为 `'Y'`、终结态为 NULL，MySQL 唯一索引允许多个 NULL——
> 历史记录随便躺，有效预约每用户每片至多一条（见 docs/01 §3.5）。

## 3. 跨资源时间冲突检测（核心亮点）

任何一笔预约（座位/场馆/讲座/课程）都写同一张 `t_user_time_occupancy` 并读它做检测，
因此四种业务天然互斥：

```
上午预约了「图书馆座位」→ 同一时段无法再约「羽毛球场」（位图 AND ≠ 0 → 40023）
```

该反解能力已交付（阶段 10 · 个人中心）：`GET /api/user/schedule?date=` 把当日位图解码成连续占用段，
逐段匹配预约明细，并与当日课程合并为一条时间轴（见 docs/02 §13.2）。

## 4. 并发正确性推演（阶段 9 压测的实测结果）

| 场景 | 防线 | 实测结果（2026-10-08，[docs/06](06-并发压测报告.md)） |
|---|---|---|
| 100 用户并发抢容量 10 的场馆片 | `UPDATE ... WHERE booked < capacity` 行锁串行化 | **成功恰 10**，90 个 40024；booked = 10 = 有效预约数；总耗时 202ms |
| 同一预约并发提交 50 次 | 用户行锁 + 位图 + `uk_reserved` 唯一索引 | **成功恰 1**，49 个 40023；97ms |
| 同一用户并发抢 50 个座位的同一时段 | 用户行锁串行化 + 位图冲突检测 | **成功恰 1**，49 个 40023；位图无丢更新；84ms |
| 100 用户并发抢 10 个课额（选课） | 用户行锁 + `WHERE selected < capacity` | **成功恰 10**，90 个 40052；159ms |

> 压测同时发现并修复"**当日首约**"间隙锁死锁缺陷（用户行锁即修复产物）——根因与前后对比见 docs/06 §3。

## 4.5 签到与违约惩罚（2026-10-08 业务规则）

> 规则：签到窗口 = 开始前 30 分钟 ~ 开始后 15 分钟；未签到 → 禁约 24 小时（"次日无法预约"）；
> 临近取消（<30 分钟）→ **仅体育馆/讲座**禁约 5 分钟（图书馆取消无任何惩罚）。
> 图书馆不限预约次数；体育馆每周 4 次（取消回退，爽约不回退）。

```java
// ① 签到（ReservationService.checkin）
checkin(id):
    assert 本人 && status=APPROVED && 未签到
    assert now ∈ [start - 30min, start + 15min]     → 否则 40030
    UPDATE t_reservation SET checkin_time = now

// ② 定时结算（ReservationScheduler，每 60 秒；查询命中 idx_status_slotdate）
settle():
    for 单 in (status=APPROVED && slot_date ≥ 今天-1):
        if 已签到 && end < now:        → markCompleted（COMPLETED）
        if 未签到 && now > start+15min: → markNoShow

// ③ 判爽约（事务）——"没来的人把座位让出来"
markNoShow(id):
    status ← NO_SHOW（remark=未签到）
    releaseResources(单)      # 片 booked-1 + 位图清位（与取消共用）
    penalty.apply(user, 24h, "预约未签到")

// ④ 惩罚载体（PenaltyService，Redis 天然过期）
key   campus:penalty:{userId}
value "{解禁时间}|{原因}"     TTL = 惩罚时长
预约入口检查：now < 解禁时间 → 40029（提示带解禁时间，如"解禁时间 2026-10-09 01:44"）

// ⑤ 临近取消（cancel 内；仅体育馆与讲座触发，图书馆无惩罚）
if 业务 ∈ {VENUE, LECTURE} && (start - now) < 30min:
    penalty.apply(user, 5min, "临近开始取消预约")
```

**为什么用 Redis 承载惩罚**：TTL 与"禁约截止时间"同构——到期自动解除，不需要定时清理；
惩罚检查在预约入口读一次（O(1)），不引入新的表与索引。

## 5. 已知简化点（生产改进方向）

| 简化 | 生产方案 |
|---|---|
| 配额行"并发首建"用 catch 重试 | 定时预热/分段合流（INCR-only Redis 计数 + 落库对账） |
| 位图用悲观锁 | 乐观锁 version + 重试，或 Redis Lua 原子合并 |
| 单号用 Redis INCR 全局序列 | 雪花算法（阶段 14 起用基因法拼接 user_id 后段，见 [docs/04](04-架构演进设计.md) §4.2） |
| 同一用户请求用 t_user 行锁串行化（吞吐换正确性） | 用户级 actor / 按用户分区队列（Redis Stream）；当前每用户独立行锁，横向量级下冲突可控 |
| 取消不校验"开始前 N 小时"规则 | 业务规则参数化（如"开始前 30 分钟不可取消"） |
