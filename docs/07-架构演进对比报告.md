## 1. 量化对照

### 1.1 并发压测：单体 vs 分片（同机同场景，各跑 2 轮取最好）

| 场景 | 单体 | 分片（8 分片） | 倍数 | 断言（两侧均 PASS） |
|---|---|---|---|---|
| 防超卖（100 并发抢 10 名额） | **184 ms** | 371 ms | 2.0× | 恰好 10 成功，片 booked=10 |
| 防重复（同一预约并发 50 次） | **82 ms** | 129 ms | 1.6× | 恰好 1 成功（唯一索引兜底） |
| 位图冲突（50 个座位同一时段） | **82 ms** | 122 ms | 1.5× | 恰好 1 成功，位图无丢更新 |
| 选课限额（100 并发抢 10 课额） | **168 ms** | 348 ms | 2.1× | 恰好 10 选中，selected=10 |

> 口径：各侧多轮取最好（冷启动首轮偏慢主要来自连接池按需扩容，见 §3.1——
> 修复前首轮曾达 6000+ ms 且伴随连接超时失败）。
> **本表可在前端「📈 演进对比」页一键复跑**（双侧同屏对照 + 断言逐条展示）。

**结论**：分片后**四条不变量的断言全部继续成立**（成功数严丝合缝、账实一致、零系统异常）——
正确性零妥协；代价是**同等工作量延迟约 +50%~+90%**，来源可逐项归因：

| 延迟来源 | 说明 |
|---|---|
| SQL 解析 + 路由 | 每条逻辑 SQL 经 ANTLR 解析、计算路由目标（实测日志可见 Logic → Actual 两次打印） |
| 连接放大 | 一条事务每触及一个库占一条物理连接；热点分片（压测场地固定在一个分片）把 100 个事务挤向同一池 |
| 跨库双写事务 | 预约事务同时写"用户分片 + 资源分片"，提交变两次 |
| 无收益的差异 | 广播表（课程/资源）读放大不明显（小表） |

### 1.2 数据规模与查询定位

| 维度 | 单体 | 分片后 |
|---|---|---|
| `t_reservation` 单表行数 | 957,994（单表） | 最大分片 **121,091**（≈ 单表的 1/8） |
| "我的预约"（按 user_id） | 单表索引（`idx_user_status`） | **单分片**命中：`ds_1 ::: ... FROM t_reservation_1 WHERE user_id=?` |
| "按单号查" | 单表唯一索引 | **基因路由**单分片：`ds_0 ::: ... FROM t_reservation_1 WHERE reservation_no=?`（尾 6 位基因 `000001` → 与 user_id=1 同分片） |
| 三方式登录 | 1 次查询（t_user 三个唯一索引） | 2 次查询：索引表（单分片）+ 按 id 回查（单分片）——**永不广播 8 分片** |
| 无分片键查询（定时结算扫描 / 压测清理） | 1 张表扫 | 8 分片全路由后归并（语义不变，仅慢） |

> **基因法恒等证明**（可验证）：`gene = user_id % 1,000,000`，`1,000,000 = 8 × 125,000`，
> 故 `gene % 8 ≡ user_id % 8`——按单号路由与按 user_id 路由必然同一分片（迁移脚本已将
> 全部历史单号重写为该格式，逐行校验零违例）。
> 对照点：12306 同款算法用 `String.hashCode` 参与单号路由，与其 user_id 侧（数值取模）**并不严格一致**；
> 本实现两侧统一数值取模，数学上可证。

### 1.3 违约判定：@Scheduled 轮询 vs RocketMQ 延时消息（阶段 13）

| 维度 | Scheduler（单体期方案） | 延时消息（现方案） | 兜底关系 |
|---|---|---|---|
| 判定时效 | 0~60 秒（平均 30 秒；轮询周期固定） | **精确到点**：实测"8 秒延时消息 → 8 秒后判定 NO_SHOW、库存回滚、施加禁约" | Scheduler 保留，每 60 秒兜底扫一遍 |
| 数据库压力 | 每 60 秒全量扫描一次（分片后 ×8 路由） | **0 轮询**（消息驱动，按需触达单行） | 双路径同到 → 状态校验 + 幂等键保证不双罚 |
| 可靠投递 | 进程内，重启窗口丢判定 | 持久化 + 重试 + 死信；未到点自动按剩余时长重投递 | |
| 复杂度代价 | 简单（一个 @Scheduled） | 消息模型 + 消费幂等切面（@MQIdempotent 两态 Lua）+ 版本兼容工程量 | |

**结论**：时效敏感（预约超时、订单关单）→ 延时消息；低频兜底 → 保留轮询。
本项目"两条腿"并存且互不冲突，代价仅一份幂等切面。

### 1.4 服务拆分（阶段 12）对照

| 维度 | 单体 | 拆分后 | 实测 |
|---|---|---|---|
| 部署单元 | 1 | 3（网关 + 双服务） | Nacos 三服务在册 |
| 故障隔离 | 全挂 | 停 user-service：登录域报错，**预约/选课/日程经网关照常** | 3/3 成功 |
| 横向扩容 | 整机复制 | campus-service 起双实例，杀一存一 | 9082+9083 → 杀 9082 后请求全部成功 |
| 配置成本 | 1 份 | 分片配置 ×2 服务（手工同步！）、JWT 密钥 ×3 | 见 §3 教训 |
| 调用链 | 进程内方法调用 | 服务间 HTTP（测试重置经 @LoadBalanced RestClient） | 一次额外网络往返 |

### 1.5 Sentinel 限流（阶段 14 · 选课接口）

实测（120 并发抢课，QPS 阈值 20）：

| 指标 | 值 |
|---|---|
| 被限流快速失败（40055） | **99** |
| 放行并通过防超卖闸门 | 21（其中 10 抢到名额，11 被"名额已满"业务拒绝） |
| 系统异常 | **0** |
| 整批完成耗时 | 172 ms（快速失败，无 DB 动作） |

**结论**：限流是**入口保护**（保系统），与防超卖（保数据）互补；代价是阈值按实例数折算——
多实例部署时单机阈值 × 实例数 = 集群总入口量，或改用统一限流（网关集群限流/Sentinel 集群模式）。

### 1.6 列加密与读扩散索引表（阶段 14）

| 项 | 实测 |
|---|---|
| AES 列加密 | t_user.phone/email 落库为密文；登录/资料读取透明解密；UPDATE 日志可见密文参数 |
| 加密等价性 | ShardingSphere 的 AES（ECB/PKCS5 + SHA1(密钥)[0:16] + Base64）与 MySQL `AES_ENCRYPT` 表达式**逐字节一致**（用于迁移脚本，已实测） |
| 索引表 | t_user_phone / t_user_mail / t_user_student_no 各 10,005 行；登录路径 = 索引表单分片点查 → 按 id 回查（2 次单分片查询） |
| 代价 | ① 加密列不能范围/模糊查询（本项目登录已改走索引表，无影响）；② 密文更长（phone 20→64、email 128→256 列宽）；③ 索引表需与用户表同步维护（本项目无注册/改手机号流程，迁移一次性灌入即恒定） |

## 2. 逐项「收益 / 代价」结论（验收要求）

| 拆分项 | 收益 | 代价 | 结论 |
|---|---|---|---|
| **服务拆分**（12） | 故障隔离、独立扩容（实测杀实例不宕）、边界清晰 | 配置重复、调用链变长、分布式调试 | ✅ 值得：当模块有**独立伸缩/故障域**诉求时；小团队演示亦可显著提升可运维性 |
| **MQ 化**（13） | 判定精确到点、零轮询、可靠投递 | 消息模型复杂度、版本兼容坑 | ✅ 值得：时效敏感 + 需要可靠触达；低频场景继续用轮询 |
| **分库分表**（14） | 单表行数 1/8、单分片查询、可水平扩 | 延迟 +50~90%、跨库事务、无分片键查询全路由、连接放大 | ⚠️ 条件值得：单表 > 千万级 / 写入热点 / 需分片扩容时；本项目规模（96 万）是**教学预演**，收益主要为架构能力而非性能 |
| **雪花 + 基因单号**（14） | 分片后 ID 全局唯一 + 单号可直接路由（免广播） | 单号变长、依赖机器号分配 | ✅ 值得：与分片强绑定，属必选项 |
| **列加密**（14） | 敏感列落库不可读（合规） | 不可范围/模糊查、列宽膨胀、迁移必须走加密层 | ✅ 值得：有合规要求时；代价可用索引表/预计算化解 |
| **读扩散索引表**（14） | 三方式登录**永不广播** 8 分片 | 多一次查询、需同步维护 | ✅ 值得：登录是最高频入口，一次额外点查换掉广播扫描 |
| **Sentinel 限流**（14） | 抢课高峰快速失败保 DB、错误可读（40055） | 阈值需按实例数折算、规则需治理 | ✅ 值得：有突发流量的写接口标配 |

## 3. 分片后的新失败模式与解法（实战记录）

### 3.1 连接放大：热点分片打爆连接池 ★

分片后**每条事务在每个触及的库各占一条物理连接**；压测"100 人抢同一个场地"时，
100 个事务全部路由到该场地的**同一个分片**（`ds_0`），排队等行锁期间各自持连接不放——
`ds_0` 池需要 ≈ 并发数容量，20（默认）直接打爆：
先报 `CannotCreateTransactionException`（外层池 20），放大外层后转为
`HikariPool-3 time out`（内层池 10）。

**解法**：外层 128 + 内层 2×128 + MySQL `max-connections=500`（docker-compose 已固化）。
**通用结论**：分片系统容量规划要看"**单分片**峰值并发"，不是总并发。

### 3.2 ShardingSphere 5.3.2 × Spring Boot 3.2：snakeyaml 冲突

5.3.2 的 YAML 序列化用 snakeyaml 1.x 的 `Representer()` 无参构造（Boot 3.2 自带 2.2 已删除）→
首次建连即 `NoSuchMethodError`；官方 **5.4.1 仍未修、5.5.3 才修**（构造器改传 DumperOptions）。
**解法**：保留与 12306 同版 5.3.2 + 两个服务模块内置补丁类
`org.apache.shardingsphere.infra.util.yaml.representer.ShardingSphereYamlRepresenter`
（源码 = 5.3.2 官方源码 + 5.5.3 的构造器修法；BOOT-INF/classes 覆盖 lib 内同名类）。

### 3.3 合并结果集缺 java.time 转换

多分片归并的结果集里，MyBatis 以 `getObject(col, LocalTime.class)` 读取时，
5.3.2 的 `ResultSetUtil.convertDateValue` 不支持 `java.sql.Time/Date/Timestamp → java.time.*`，
任何**全路由查询**（图书馆楼层统计、定时扫描）直接抛 `UnsupportedDataTypeConversionException`。
**解法**：同法内置 `ResultSetUtil` 补丁类（官方源码 + 四个 java.time 分支，两服务各一份）。

### 3.4 分片列禁止 UPDATE

`UPDATE ... SET user_id=?`（MyBatis-Plus `updateById` 会带上全部非空字段）被
ShardingSphere 拒绝：`Can not update sharding value`。
**解法**：分片键字段一律 `@TableField(updateStrategy = FieldStrategy.NEVER)`
（`reservation_no` 作为复合分片键成员同理——单号创建后不可变）。

### 3.5 跨库事务的 LOCAL 语义（已知边界）

预约事务跨"用户分片 + 资源分片"两库，ShardingSphere 默认 LOCAL 事务：
**提交阶段两次独立提交**——同 MySQL 实例内部分失败窗口极小，但架构上无全局原子性。
业务侧的补偿：所有核心不变量由**单条语句原子性**（条件更新）+ **唯一索引**（分片内）保证，
最坏情况是"库存已扣、预约记录缺失"，可由对账/定时任务清理。跨实例部署时应升级 XA/Seata。

### 3.6 唯一索引降级为「分片内唯一」

分片后 `uk_reservation_no` 仅在单分片内唯一——全局唯一由**雪花 ID + 基因**在设计上保证
（与 12306 的订单号方案同理）；`uk_reserved`（同用户防重）天然同分片，语义不变。

## 4. 什么时候**不该**拆（反面结论）

- 数据 < 千万行、单实例撑得住时：分库分表带来 ~2× 延迟、双层连接池、跨库事务、
  配置双份维护——**收益为 0**。本项目 96 万行属于"教学规模"，分片是**能力预演**，
  真正的收益点应从 **单表 > 2000 万 / 单库写入瓶颈 / 需要在线扩容** 时开始计算。
- 无用户量压力时 MQ 化的收益主要是**可靠性语义**，不是吞吐。
- 服务拆分的收益在**故障隔离与独立伸缩**（本平台已实测），不在"更快"。

**一句话结论**：演进的价值 = 把"能演示正确性"的系统，变成"在规模与故障下仍然正确"的系统；
每一层拆分都用可复现的对照数据标注了它的票价。
