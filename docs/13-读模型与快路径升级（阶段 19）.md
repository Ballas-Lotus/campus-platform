# 13 · 读模型升级与快路径合并（阶段 19）

> 日期：2026-10-10　目标：**吸纳 12306 的读模型思路与黑马点评的"一步原子"思路，
> 让抢课系统"读写都更进一步"**——读路径静态/动态分离 + 写路径增量维护 + 写入口往返减半。

> 入口：前端「🚀 缓存」页新增「🧩 教学班读模型」与 A/B 对照、「🔒 并发控制」页新增「⚡ 合并 Lua」、

## 1. 为什么是这两刀（与三份参考的谱系关系）

抢课的业务形状 = **读写同峰 + 强结果 + 高正确性**（见 docs/12 §谱系），所以：

| 来源 | 学什么 | 落在哪 |
|---|---|---|
| **12306**（读模型） | 余票查询的"独立读模型 + 写路径同步增量维护（hincrby ±1）"，而不是"写后整键失效" | §3.1 静态信息/动态余量拆分 + HINCRBY；§3.2 pipeline 合并读；§3.3 开窗前预热 |
| **黑马点评**（一步原子） | 判定 + 占位 + 入队全塞进一个 Lua（一次往返） | §3.5 幂等 + 预扣合并脚本 |
| **延续既有结构** | 对账自愈（阶段 17 用在预扣计数器上）扩到读模型；批量消费补齐 MQ 一课 | §3.4 / §3.6 |

**没有抄的**（见 docs/12 已论证）：全异步落库（强结果不适合）、公平锁串行（Lua 原子已消灭业务锁）、
给热门课做库存分桶（教学班天然分桶，1000 并发对 Redis 是毛毛雨）。

## 3. 关键技术决策（连同理由与实测）

### 3.1 静态/动态分离：把"会变的余量"从缓存主体里拆出去

**问题**（阶段 16 的结构性代价）：整个教学班 DTO（名称/教师/时间/余量）挤在一个 key（TTL 30s），
每次写都要整键失效 → 下一次读全程回源；余量显示最长滞后 30 秒。

**拆法**（与阶段 16 "用户态不进缓存"同款原则的推广——"**高频变化字段不进静态缓存**"）：

| 对象 | key | TTL | 写路径怎么维护 |
|---|---|---|---|
| 静态信息（名称/教师/时间/容量） | `campus:cache:classes:{courseId}` | **600s** | **不动**（选课/退课不再失效它） |
| 动态余量（field=classId → 剩余名额） | `campus:cache:class_stock:{courseId}`（Hash） | **120s** | 提交后 `HINCRBY -1/+1`（Lua"存在才加"） |

**"存在才加"的 Lua 是防坑关键**：写路径到达时若 Hash 已过期，直接 HINCRBY 会创建一个"只含一个 delta 字段"
的残缺 Hash（后续读数全是错的）。脚本改为 `EXISTS 才 HINCRBY`，不存在则跳过（记 `STOCK_SKIP`）——
下一次读按 DB 真值整体重建，**宁可重建，不可残缺**。

**写路径顺带卸掉一个 SCAN**：原实现每次选课 `evictByPrefix(courseListPrefix())`（SCAN + 批量删）——
写热点上做 SCAN 是明显的反模式。现在课程列表的聚合值随 60s TTL 自然刷新（展示可旧），
**写路径零扫描**。

### 3.2 pipeline 合并读（阶段 19 版"V2 管道"）

`ClassStockCache#read` 用 `executePipelined` 一次往返取回 `GET classes:{id}` + `HGETALL class_stock:{id}`；
任一 miss 再走各自的回源路径（静态信息走 `safeGet` 防击穿语义不变；余量走 `rebuild`）。
pipeline 结果做了 String/byte[]/Map 归一化（不同序列化路径的兼容），失败自动回退逐条读。

### 3.3 抢课窗口预热

窗口打开前的"温桶"：启动时 + 手动触发，把**热门课程**（`GROUP BY course_id ORDER BY SUM(capacity) DESC LIMIT N`，
可配 `campus.cache.warmup.hot-course-ids` 显式指定）的静态信息与余量 Hash 灌进 Redis。
开抢第一波读全部命中、零回源；余量 Hash 随后由写路径增量维护、对账兜底。

### 3.4 对账扩到读模型（与预扣对账同构）

`ClassStockReconciler`：30 秒周期 + **启动即对账**（`ApplicationReadyEvent`，认领重启前遗留的 Hash），
分布式锁保证多实例只跑一个（`campus:lock:cache:stock:reconcile`）。逐字段比对 DB 真值：
缺失/漂移 → HSET 拉回；DB 中不存在的字段（幽灵班级）→ HDEL；整课无班级 → 删 key；单轮最多检查 50 个 Hash。

> **诚实边界**：增量更新（提交后 HINCRBY）与对账（HSET 绝对值）并发交错时，最坏引入 **±1 的显示偏差**——
> 下一轮对账或 TTL 到期重建即收敛；**闸门判定与 MySQL 真相不受影响**（余量 Hash 是展示读模型）。
> 彻底消除需版本 CAS，教学项目从简。

### 3.5 合并 Lua：把"幂等 + 预扣"焊成一次原子

```
旧（阶段 18 成功路径）：ensureInitialized(hasKey) → 幂等两态 Lua → 预扣 Lua → 置已消费   = 4 次往返
新（阶段 19 快路径）：  合并脚本（幂等判定 + 预扣一次原子）→ 置已消费                     = 2 次往返
```

脚本内顺序**刻意与阶段 18 一致**：先判幂等（重复提交应得 40060），再判余量（不足得 40052），
通过才 `SET CONSUMING` + `DECRBY`。返回码：`1 放行 / -1 满 / -2 未初始化 / -3 已成功重复 / -4 处理中重复`。

**三层结构保证语义不变**：

| 层 | 触发条件 | 行为 |
|---|---|---|
| 快路径 | 正常流量（99%） | 合并脚本一次原子；业务失败 → 回补预扣 + 释放幂等标记 |
| 慢路径 | 计数器未初始化（冷启动/过期第一波，返回 -2） | 保留阶段 18 完整链路：两态幂等 → `ensureThenDeduct` → 业务 |
| 降级 | Redis 异常 | 幂等放行 + 不预扣，直通数据库（与阶段 18 切面降级一致） |

**工程细节**：Lua 与 key 规则抽到 `IdempotentSupport`（切面与快路径共用同一份状态语义）；
key 命名空间不变（`campus:idem:course-select:{userId}:{classId}`），压测清理脚本零改动；
预留 `fastPathSingleLua / fastPathSlow` 指标可观测两层占比。

### 3.6 消费者批量消费——以及一条真实发现

**发现**：本项目的 `rocketmq-spring-boot 2.2.3` **不支持消费端批量**——`@RocketMQMessageListener`
没有 `consumeMessageBatchMaxSize` 属性，容器类只声明 `handleMessage(MessageExt)`（逐条）。
（已用 `javap` 反编译核实，见 §5 缺陷 3。）

**做法**：站内信消费者绕过 spring 封装，用底层 `DefaultMQPushConsumer` 注册
`MessageListenerConcurrently` 并显式 `setConsumeMessageBatchMaxSize(20)`——协议与幂等语义
（`campus:mq:idem:notification:{messageKey}` 两态 Lua）与逐条版完全一致；整批成功统一 ACK，
任一条失败整批 `RECONSUME_LATER`（已成功条目由幂等跳过）。MQ 不可用时消费者启动失败**不阻断服务启动**。

## 4. 实测数据（2026-10-10，本机同环境）

### 4.1 读模型 A/B：「写后整键失效（阶段 16） vs 写后增量（阶段 19）」

```
A · 写后整键失效：avg 21.4 ms · 回源查库 40 次（20 轮 × 信息+余量各一次）
B · 写后增量维护：avg  3.05 ms · 回源查库  0 次
写后立即可见：Hash 162 → 增量 -1 后读到的 available = 161（不失效、不回源，显示当场变化）
```

### 4.2 合并 Lua 对照（500 轮，同一计数器）

```
旧路径（hasKey + 幂等 + 预扣 + 置已消费）：avg 2981 µs · P50 2900+ · 4 次 Redis 往返
快路径（合并脚本 + 置已消费）：          avg 1608 µs · P50 1600+ · 2 次 Redis 往返（快 1.85×）
（本地 loopback µs 级；跨网络部署时"省 2 次 RTT"会按 RTT 放大）
```

### 4.3 对账自愈（两种触发）

| 触发 | 操作 | 结果 |
|---|---|---|
| 手动「立即对账」 | 毒化 7001 余量 0 → **+5** | `scanned=21 / fixed=1`，drift 归零；列表显示从 5 回到 0 |
| **自动对账（无人工干预）** | 同样毒化后等待 | **第 25 秒自动纠偏**（30s 周期内），drift → 0 |

### 4.4 批量消费

```
一次调用批量投递 50 条 → 消费 4 批（maxBatchSize=20，avg 10.2）· 落库 50 · 幂等跳过 0 · 失败 0
（对照：逐条 syncSend 时消费者实时追平，批大小恒为 1——"批"只在突发投递下出现）
```

### 4.5 回归与容量（确认"更进一步"没有代价）

| 项目 | 数字 |
|---|---|
| 8 个压测场景复跑 | **全 PASS**（PREDEDUCT 1000 → 990 拦 / 10 放行 / 0 回补 / 502ms；COURSE_OVERSELL 263ms；IDEMPOTENT 99×40060；LOCK 违例 0） |
| 端到端写竞争（151 真实用户走网关） | **恰好 10 成功 · 0 系统异常 · 294ms**（较阶段 18 的 408ms 更快：合并脚本少一趟 + 限流先挡） |
| 读容量（走网关，同机） | 时段 3549 / 概览 4197 / 列表 3615 QPS —— **与阶段 18 基线持平**（时段 3529 / 概览 4132 / 列表 3672） |
| 全链路回归 | **48 项 PASS / 0 FAIL**；三服务日志 0 ERROR |

## 5. 本阶段发现并修复的问题（4 个）

| # | 问题 | 怎么暴露的 | 修复 |
|---|---|---|---|
| 1 | 毒化演示在余量 Hash 过期（TTL 120s）后报"Hash 不存在" | 冒烟脚本隔了几分钟再点毒化 | 毒化前若 Hash 缺失先按真值重建（"随时可毒化"） |
| 2 | 逐条 `syncSend` 演示不出批量消费（批大小恒为 1） | 冒烟：50 条 → 50 批 | 演示端点改"一次调用批量投递"（`RocketMQTemplate.syncSend(destination, Collection)`） |
| 3 | **rocketmq-spring 2.2.3 不支持消费端批量** | `javap` 核实注解无批量属性、容器只处理单条 | 原生 `DefaultMQPushConsumer` + `MessageListenerConcurrently` + `setConsumeMessageBatchMaxSize(20)` |
| 4 | A/B 的"写后可见"样本选中余量 0 的班（-1 被钳到 0，看不出变化） | 冒烟输出 `sample: 0 → 0` | 样本改选"有余量的教学班"（162 → 161 可见） |
