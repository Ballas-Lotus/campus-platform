总览：高并发就是"漏斗"，六道关层层筛

请求像过安检：每一层用更便宜的手段，把请求处理掉、或礼貌地劝返。

💬 说人话 高并发不是"让每个请求都跑得飞快"，而是漏斗：在请求到达数据库之前，用一层层更便宜的关卡把它处理掉或拒绝掉。 越靠前越便宜——浏览器 > 网关（纯内存判断）> Redis（内存往返，微秒~毫秒）> MySQL（磁盘 + 锁，毫秒~几十毫秒）。 优化的本质 = 把请求挡在更便宜的一层。
图 1 · 一条写请求的六道关：每层都在"更便宜的地方"解决问题。读请求走 1→2→3→④读侧→5。
拒绝也是一种服务：990 个抢不到名额的同学，在 Redis 一层（微秒级内存判定）就被告知"手慢了"， 而不是排 30 秒队后超时——快速失败，比让用户干等更善良，也把数据库保护得死死的。
3

读路径：四步把请求挡在数据库之外

🧭 小林路线 · Redis 篇 → 缓存三兄弟 + 缓存一致性。读请求占大多数，也最好优化。

图 2 · 读路径四步：布隆挡穿透 → 缓存挡回源 → 锁挡击穿 → 最后才轮到数据库。写路径反向通知：提交后删缓存。
💬 说人话 缓存 = 前台放一箱常用资料，找资料先翻前台；布隆 = 门口保安，记性极好——他说"没这本书"就一定没有（防穿透）； 防击穿 = 资料被撕掉的瞬间，只放一个人进档案室去取，其他人在门口等 40ms； 空值回填 = 查不到的也贴一张"查无此页"的条，省得人人跑一趟档案室； 写后失效 = 档案改了就把前台那页撕掉——而且是等档案改完（事务提交）再撕。
阶段 19 增补（读模型升级）：教学班列表这一层又往前走了一步——拆成 静态信息（名称/教师/时间，TTL 600s，选课退课不再失效它）+ 动态余量 Hash（field=classId → 剩余名额，TTL 120s，写路径提交后 HINCRBY 增量维护、不再整键失效）， 读列表用一次 pipeline 合并两者；Hash 过期/漂移由"读回源重建 + 30 秒对账"自愈。 对照实测：写后失效 21.4ms / 40 次回源 → 写后增量 3.05ms / 0 次回源， 且余量变化写后立即可见（162 → 161 不经过回源）。开抢前还可「窗口预热」热门课程。 详见 [docs/13](13-读模型与快路径升级（阶段 19）.md)。

缓存一致性（小林：Cache Aside，先更新库、再删缓存）

本项目把"删缓存"挂在 TransactionSynchronization.afterCommit 上，堵死这个经典竞态： 

// 若"先删缓存、后提交"，会出现：
T1 更新数据库(未提交) → T1 删缓存 → T2 回源读到旧值并写回缓存 → T1 提交
// 结果：缓存里长期是旧值（直到 TTL 到期）。挂到提交之后即可消除。
反例（本节课最值钱的一条）：单资源时段查询——无缓存 1.10ms → 有缓存 2.30ms，反而慢了 1ms （缓存往返 + 反序列化的开销 > 一次走索引回源的开销）。为什么还保留缓存？因为它是最热的 key： 1000 个并发读同一资源时，缓存把数据库连接占用从 1000 次降到 1 次——连接池才是稀缺资源。
口诀：回源成本必须大于缓存往返成本；看回源成本、看并发压力，不看直觉。
小林怎么说

Redis 为什么快？

纯内存操作、单线程避免锁竞争、IO 多路复用；再加上 Lua 脚本原子执行——一段脚本里的多条命令不会被其他请求插队。

➜
本项目怎么做

把"判断 + 扣减"压成一次原子执行

预扣、幂等、布隆探针、锁释放……全部写成 Lua 一次往返：不是把收银员变多，而是把"结账动作"打包成一步做完，不给你插队的机会。

4

写路径：预扣闸门，99% 的无效请求进不了数据库

🧭 对标 12306 令牌桶；写请求受"唯一真相的串行点"约束，挡量比提速更重要。

图 3 · 写路径：前两层快速失败 → 闸门在 Redis 内存里挡掉 99% → 只有拿到"号牌"的请求进事务碰数据库。
💬 说人话 预扣闸门 = 教室门口发号牌：1000 个人来抢 10 个座，990 个人在门口就被劝回（Redis 内存级判定，微秒）； 只有 10 个拿着号牌进教室（数据库）。回补 = 号牌发错了要收回来（数据库说"其实满了"，就把预扣的还回去）； 对账 = 每天晚上核对账本，Redis 是草稿纸、数据库是账本。

预扣闸门的三条防线（campus.prededuct.*）

① 预扣
Lua 内"先全部校验、再逐个扣减"——多时间片预约天然全成或全败，不会扣一半卡住
② 回补
数据库拒绝时 INCRBY 归还——不回补就会"少卖"（Redis 扣了、库里其实空着）
③ 对账自愈
每 30 秒比对 Redis 与 DB 真值，偏差超阈值（max(5, 真值×20%)）即纠偏；多实例用分布式锁只跑一个

与 12306 令牌桶的对照（诚实版）

维度12306 令牌桶（学习版实现）本项目预扣闸门
Redis 角色唯一真相（靠"删桶重建"自愈）预计数——真相始终在 MySQL（唯一索引 + 条件更新）
Redis 不可用取不到令牌 → 购票不可用自动降级直通数据库：只损失性能，不损失正确性

能挡的量一样（都在 Redis 之前拒绝），但正确性不再押在 Redis 上——这是本项目相对 12306 学习版实现的加分项，也是面试最值得讲的一句。
阶段 19 增补（快路径合并）：选课入口把"② 幂等"和"③ 预扣"合并成一个 Lua 脚本 （判定与扣减一次原子完成，吸收黑马点评"一步原子"思路）——成功路径的 Redis 往返 从 4 次压到 2 次（实测 1.85×）。冷启动第一波走"慢路径"（先初始化再判定）， Redis 故障仍走降级直通——三层语义完全一致（40052 满员 / 40060 重复 / 恰好扣 1 个名额）。 详见 [docs/13 §3.5](13-读模型与快路径升级（阶段 19）.md)。

并发控制三件套：锁 · 幂等 · 线程池

🧭 小林路线 · Redis 篇 → 分布式锁（SET NX + 为什么释放锁要 Lua）。

图 5 · 幂等两态：抢到标记的人才执行业务；"处理中"和"已完成"对重复请求都回 40060，业务失败则删标记允许重试。
💬 说人话 分布式锁 = 厕所门上的"有人"牌子：谁挂的谁摘（释放时校验 token，防误摘别人的）； 幂等 = 快递运单号：同一个单号，仓库只会发一次货； 线程池 = 银行窗口就这么几个：人满了就明确拒绝取号（并计数报警），而不是让队伍无限排下去直到 OOM。

小林怎么说

为什么释放锁要用 Lua？

"先 GET 判断是不是自己的锁、再 DEL"——这两步不是原子的，可能在判断后被别人抢走，删掉别人的锁。所以要用 Lua 把"校验 + 删除"写成一步。

➜
本项目怎么做

SET NX PX + Lua 校验删除

官方推荐写法，语义透明、可压测。诚实说明：未引入 Redisson——临界区极短（缓存回源/定时结算/计数器初始化），不需要可重入与看门狗；CampusLock 是接口，想换 Redisson 只改一个实现类。

MQ：削峰 · 延时 · 幂等消费

🧭 小林路线 · 《消息队列面试题》：削峰填谷、重复消费、延时消息、消息丢失。

图 6 · MQ 一条线：同步先回结果 → 延时消息到点判爽约 → 消费端幂等 → Scheduler 兜底防消息丢失。
💬 说人话 削峰 = 奶茶店取号：高峰期先收单给号，不让所有人挤在柜台前； 幂等消费 = 同一张订单即使被派送两次，仓库也只发一次货（发 2 条 → 落 1 条）； 延时消息 = 定个 8 秒的闹钟，到点自动检查"这人来没来"，没来就判爽约、释放名额。
诚实缺口（写进 docs/09 §6）：MQ 死信队列与积压告警预案未做——目前的兜底是"消费端幂等 + Scheduler 定期扫描"，生产化路径已在文档中列出。

60 秒面试话术（说人话版）

把上面的六道关，压成一段能一口气讲完的话。

🎤 "你这个项目的高并发是怎么做的？"

我把它设计成一条漏斗：请求先过网关鉴权和限流，再走接口幂等，然后到缓存和预扣闸门这层—— 这是最核心的一层。读路径用布隆过滤器防穿透、互斥回源防击穿、写后失效保一致， 实测工作台概览从 25.6 毫秒降到 1 毫秒；写路径用 Redis Lua 原子预扣名额， 1000 人并发抢 10 个名额，990 个在内存层就被挡回，只有 10 个进数据库， 而且被挡的请求根本不占用数据库连接——因为闸门放在事务之外。 最后一道是数据库：条件更新加唯一索引，保证"恰好"，这也是唯一不可绕过的真相层。

有个我觉得最值得讲的取舍：Redis 在我这里只是"预计数"，MySQL 才是真相—— Redis 挂了就自动降级直通数据库，只损失性能、不丢正确性；计数器漂移了，30 秒对账自己纠回来。 这套设计是跟着小林 coding 的路线走的：缓存三兄弟、分布式锁、MQ 幂等，一个个知识点在项目里都有落点、有实测数字。 前面还有锁、幂等、线程池三件套兜住并发控制，MQ 做削峰和延时判爽约。

进一步追问的方向（都有文档支撑）：为什么缓存有时反而更慢（§3 反例）？为什么闸门不能放在事务里（§4）？ 为什么释放锁要用 Lua（§6）？Redis 当唯一真相 vs 当预计数的取舍（§4 对照 12306）？ 想继续往 10 万 / 100 万 QPS 走，要动的是多实例 + 负载均衡 + Redis 集群 + 读写分离——那是换架构维度，不是调参。
