1高并发预扣减设计（Redis + Lua 闸门）

业务场景：选课开放的那一秒，几千名学生同时点"确认选课"；图书馆座位/体育馆/讲座报名走的是同一套闸门。 一个教学班只剩 10 个名额，但瞬时到达 9,000+ 个请求——系统必须快速告诉 8,990 个人"手慢了"，同时保证恰好 10 人成功。

图 1 · 预扣闸门：一次选课请求的四条出口（拒绝 / 放行 / 降级 / 回补）

怎么做到的

  • 校验与扣减必须原子：写成一条 Lua（FAST_PATH_SCRIPT），先 GET 幂等键与计数器做全校验，全部通过才 DECRBY——单线程执行、没有中间态，天然免疫并发穿插。
  • 跨资源 all-or-nothing：预约要占用多个连续时段，脚本接收 KEYS[] 数组：任一 GET 返回 false（计数器未初始化）或不足，整体返回失败，一个都不扣。
  • 闸门刻意放在事务之外：CourseSelectGate.select() 先做 Redis 预扣，再把通过的请求交给 CourseService.select()。Spring 的 @Transactional 在方法进入时就占用连接，若先开事务再判定，连接池会先被打爆。
  • 失败要回补，不能"少卖"：数据库拒绝（冲突/真满）时执行 RELEASE_SCRIPT（INCRBY 回补）并释放幂等标记，让用户能换班重试；退课走 drop()：先落库再 release(+1)，保证 Redis 计数与数据库同步。
  • Redis 故障降级直通：捕获异常后记降级、不预扣、直接进事务——正确性由数据库唯一索引/条件更新兜底，代价只是这期间的数据库压力上升。

面试追问

Q：为什么不用数据库行锁直接挡，非要加 Redis？
A：行锁挡得住超卖，但挡不住连接数——每个请求都要借连接、开事务。"手慢了"这类无效请求占比 >99%，让它们连数据库都不进，才是把压力挡在门外。
Q：Redis 扣减成功但数据库失败，不就少卖了吗？
A：所以有回补——runBusiness 捕获异常后 INCRBY 还原并把幂等标记释放；即使回补本身也失败（进程被杀），还有定时对账以数据库真值为准纠偏。
Q：Redis 挂了会超卖吗？
A：不会。降级路径不做预扣，全部请求进事务，最终仍由 WHERE selected < capacity（条件更新）和唯一索引保证不超卖——Redis 只是"预计数"，从来不是真相。
诚实边界：闸门依赖计数器与数据库真值的一致性；两者短暂不一致（回补失败/进程被杀的极端情况）由对账器在下一个周期收敛，代价是这段时间内可能出现"显示还有名额但实际抢不到"的极小概率。

2核心链路原子化（幂等与预扣合并为一条脚本）

业务场景：学生在页面上连点两下"确认选课"，或网络超时后自动重试——系统既要拦重复，又要在同一秒内把名额扣掉。 改造前，这一串动作要跟 Redis 来回 4 次；每次往返都是一次网络等待，在高并发下被放大成延迟。

图 2 · 合并前后对照：4 次往返 → 2 次，且判定顺序被固化进脚本

怎么做到的

  • 把顺序写死在脚本里：幂等判定必须排在余量校验之前。否则"用户重复提交时名额恰好被别人抢完"这一瞬间，会得到 40052（名额满）而不是 40060（重复提交）——语义错误会误导用户去换班。
  • 两态幂等：CONSUMING（处理中，防并发重入）与 CONSUMED（已成功，防重复提交）CONSUMING 带 5 秒 TTL，避免进程崩溃后标记永久卡死。
  • 失败不污染幂等：-1/-2 都不写幂等标记——"没抢到"不是"提交过"，用户换一个班应当能继续抢。
  • 与旧切面共用同一套状态语义：IdempotentSupport 统一 key 构造（campus:idem:course-select:{userId}:{classId}）与两态语义，慢路径/降级路径行为与阶段 18 完全一致，历史数据与清理脚本无需改动。
  • 只有 1 次脚本 + 1 次收尾：成功后 markConsumed 把 CONSUMING 改成 CONSUMED（第 2 次往返）；失败路径则释放标记。

面试追问

Q：合并成一条脚本，为什么不是 1 次往返而是 2 次？
A：脚本内只能有一个"入口状态"——放行时先置 CONSUMING（防并发重入），业务真正落库成功后才置 CONSUMED。这一步必须在业务成功之后，所以必然多一次往返；换来的是"并发重入"与"已成功"两种语义的精确区分。
Q：合并后语义怎么保证和慢路径一致？
A：三条对齐——顺序（幂等先于余量）、状态机（CONSUMING/CONSUMED 两态 + TTL）、key 命名空间（同一前缀、同一构造）。所以"走快路径还是慢路径"对用户不可见。
诚实边界：1.85× 是两条路径的对照微基准（同一台机器、各 500 轮）。真实收益取决于网络 RTT 与请求量级，不宣称等于线上提升。

3热点缓存模型重构（静态/动态双层拆分 + 写后增量）

业务场景：选课页要展示"每个教学班还剩几个名额"。开抢时学生疯狂刷新——余量每成交一单就变一次； 如果它和"课程名称/教师/上课时间"这类几乎不变的信息存在同一个缓存键里，任何一次成交都会让整页数据失效、全体回源。

图 3 · 读模型：读走一次 pipeline、写走增量、错由对账纠

怎么做到的

  • 拆分依据是"变化频率"：班级名/教师/时间几乎不变（TTL 600s）；余量每成交一单就变（TTL 120s）。拆开后，余量变化不再牵连静态信息。
  • 合并读：ClassStockCache.read() 用一次 pipeline 同时取静态信息与余量 Hash，避免两次往返；返回前做归一化（余量夹取到 [0, 容量]）。
  • 增量而非失效：applyDelta 用 Lua "EXISTS 才 HINCRBY"，选课 -1、退课 +1；失败（key 已过期）自动退化为"下次读重建"，绝不会写出残缺 Hash。
  • 重建以 DB 为锚：rebuild() 分布式锁 + 双检，一次 DB 查询同时用于比对与回填；班级集合变化也触发。
  • 对账自愈：reconcile() 每 30 秒抽样比对，纠偏偏差、清理幽灵字段、删除空 key；多实例由分布式锁保证只有一个在执行。

面试追问

Q：为什么不直接删缓存让它自己重建？
A：删整键 → 下一个请求全部回源，而在开抢场景下"下一个请求"有成千上万个，回源瞬间打满数据库。增量维护把"一次写"的成本固定成一次 HINCRBY。
Q：增量维护和缓存不一致怎么办？
A：两重保障——① key 过期时增量自动跳过，交给重建；② 30 秒对账以 DB 真值纠偏。诚实说：增量与对账并发交叉的极小窗口内，展示层余量最坏 ±1，下一轮即收敛；它只影响"显示"，闸门判定与落库都以 MySQL 为准。
Q：余量为什么要 TTL 120 秒？
A：TTL 是"自愈上界"——即使增量与对账都出问题，120 秒后整份数据也会按数据库真值重建。TTL 越长省得越多，但偏差存活时间越长，120s 是这里的折中。

4多维度数据一致性兜底（数据库防线 + 缓存防线）

业务场景：预约一条更有"人间烟火"的链路——同一名学生不能在同一时段既约图书馆又约体育馆（时间冲突）； 一个时段只有 50 个位子（不能超卖）；预约成功后要能查、能签到、能取消。

图 4 · 一致性兜底：事务内四步防线 + 缓存三件套 + 两条自愈闭环

怎么做到的

  • 防线分层，各管一件事：位图管"时间冲突"（同一人），条件更新管"不超卖"（同一资源），唯一索引管"防重"（幂等与同人同资源），行锁管"并发串行"。任一层失效都还有下一层，因此不依赖任何单点技巧。
  • 条件更新是"防超卖"的底线：UPDATE ... WHERE id = ? AND booked < capacity，影响行数为 0 即回滚——这条 SQL 在数据库内原子执行，任何并发交错都不可能超过容量。
  • 缓存与数据库的失效顺序：先提交事务、再失效缓存（afterCommit）。反过来会出现"缓存已删、事务未提交"期间旧值被读回来再写进缓存。
  • 余量展示与库存判定分开：页面上的"剩 3 个"来自缓存（允许 ±1），真正决定能否预约的是 Redis 闸门 + 数据库条件更新。
  • 取消/超时也走同一套一致性：释放库存、清位图、状态流转在同一事务；Redis 预扣计数器同步 +1，防止"退了但名额回不来"。

面试追问

Q：条件更新和悲观锁/乐观锁是什么关系？
A：条件更新本质是"带上限校验的乐观更新"——不显式加锁，靠 WHERE 条件与行锁在数据库内完成"检查+更新"的原子性；冲突时不是重试而是直接失败（名额本来就有限，重试无意义）。行锁用在"同一用户"维度，保证同一人的多笔提交串行。
Q：位图为什么用在这里（而不是 Redis 的 bitmap）？
A：这里的位图是"用户 × 时段"的占用关系，需要与预约记录同事务、可回滚、可重算（取消时按剩余预约 OR 重算），所以放在数据库里；Redis 位图适合"超大基数 + 只判存在性"的场合（如签到），两者解决的不是同一个问题。
诚实边界：本项目的"分布式锁"是单 Redis 实例的 SET NX PX + Lua 校验删除，不是 Redisson 看门狗；单实例 Redis 故障时锁会整体失效——这也是降级路径必须存在的原因。

5分库分表与异步解耦

业务场景：一学期几十万条预约、选课记录；学生登录可能用学号、手机号或邮箱（登录时还不知道分片键）。 同时，选课成功的站内信通知、以及"预约超时未签到"的释放，都不该拖慢主流程。

图 5 · 分片路由 + 基因法单号 + 读扩散索引表 + MQ 异步与批量消费

怎么做到的

  • 分片键的选择标准是"查询形态"：预约永远"查我的预约"→ 按 user_id；时段库存永远"查某资源的时段"→ 按 resource_id。让最常见的查询走单分片，避免广播查询。
  • 基因法解决"两种查法"：单号尾部的 6 位基因与 user_id 对 8 取模同余，因此"按用户查"与"按单号查"落到同一分片——不需要二级索引表，也不需要广播。
  • 读扩散用映射表收敛：t_user_phone / t_user_mail / t_user_student_no 各自按自身列分片，登录先点查映射表拿到用户主键，再按主键查用户表——两次单分片点查，替代一次全库扫描。
  • 敏感列加密：ShardingSphere AES 加密器自动改写真 SQL，密钥走配置项；应用代码里看到的始终是明文，落库是密文。
  • 异步分层：站内信与超时释放都是"可延迟、可重试"的动作，走 MQ；主流程只在提交后发一条消息，发送失败仅记日志，不改变业务结果。

面试追问

Q：分片后跨分片的分页/统计怎么办？
A：不做跨分片聚合——"我的预约"天然单分片；全局统计类需求走异步汇总（离线表），而不是让在线请求去广播查询。
Q：批量消费的幂等怎么做？
A：逐条用业务唯一键（消息 key）做两态幂等：处理前占位、成功后置"已消费"、异常释放。整批重投递时，已成功的条目会被幂等直接跳过，保证"至少一次投递 + 恰好一次生效"。
诚实边界：本项目是单机中间件、单实例服务，验证的是"分片路由正确性"和"异步链路正确性"，没有做多机房/多副本与故障切换演练；批量消费的收益随批大小与网络 RTT 变化，不宣称固定倍数。
