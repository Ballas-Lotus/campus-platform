## 4. 新增依赖决策点（需确认）

提示词第 2 节技术栈"严格遵守"，以下是从 12306 资产引入时**必须新增**的依赖，逐项标注理由：

| # | 依赖 | 用途 | 理由与替代方案 |
|---|---|---|---|
| 1 | 🔴 **Redisson**（如 3.21.3+） | 分布式锁（`RLock`）、布隆过滤器、Lua 执行封装 | cache/idempotent/distributedid 三个模块的基座；定时任务分布式锁（防多实例重复结算）的最顺解法。**替代**：纯 spring-data-redis + 手写 Lua 锁（工作量大，不推荐） |
| 2 | 🟡 Hutool（如 5.8.x） | 工具类（StrUtil/BitUtil 等） | BitUtil 对位图编解码有直接帮助；**替代**：JDK 原生 `BitSet` + 手写（可行） |
| 3 | 🟡 Caffeine | 热点资源本地缓存 | 可选，提示词未要求，可不引入 |
| 4 | ⚪ Dozer | ~~Bean 映射~~ | **不引入**：12306 用它属历史包袱，本项目用轻量替代 |

> 另外确认：**Jackson**（Spring Boot 默认）作为唯一 JSON 库（12306 用 fastjson2，不迁移）。

## 6. "分布式高并发特点"保留方案（三层）

与提示词"不做微服务/Nacos/MQ/分库分表"不冲突的落地方式：

**第一层 · 单体内核（写代码）**
- Redis 缓存（safeGet 防击穿）+ Lua 原子预扣 + 限流（提示词第 2 节）
- 防重三板斧 + 乐观锁 + 唯一索引（6.1/6.2）
- 阶段 9 三大并发场景压测 + 热点资源限流压测（超额完成阶段 9 的验收标准）

**第二层 · 分布式武器单体化（移植资产）**
- @Idempotent、safeGet、布隆过滤器、雪花+Redis workId、悲观/公平锁 —— 全部来自 12306，在单体里同样真实工作

**第三层 · 演进蓝图（写文档，docs/04）**
- 用 12306 的实战经验写透：服务拆分路线、分库分表（分片键选择、基因法、读扩散解法、平滑上线与回滚）
- 这是提示词本就要求的内容，12306 项目即是最好的"答案库"

## 8. 无 MQ 的高并发方案（对第 2.8 节判定的补充说明）

> 背景：校园场景存在真实高并发（选课开放瞬间抢名额、热门讲座/座位预约开放），但提示词明确本版本不做 MQ。**高并发 ≠ 必须 MQ**——本节说明如何用提示词范围内的工具（Redis + MySQL + @Scheduled）做出完整的高并发处理方案。

### 8.1 高并发三板斧与 MQ 的关系

| 手段 | 有 MQ 的做法 | 本项目的无 MQ 实现 |
|---|---|---|
| 削峰 | 请求进 MQ 排队，消费者匀速落库 | **Redis Lua 原子预扣**（挡量）+ Redis List 轻量队列（8.3，可选） |
| 解耦 | 事件驱动多消费者 | 单体内部：同步调用 / Spring 事件（够用） |
| 最终一致性 | 事务消息 / 可靠消息 | 单体单库本地事务（**天然一致**） |
| 延时任务 | 延时消息 | `@Scheduled`（提示词 6.4 已定） |

**关键认知**：预约类高并发的瓶颈是"库存争抢"，最有效的解法是 Redis 原子预扣（12306 令牌桶同款：校验+扣减在一条 Lua 内原子完成）——它本身就是秒杀方案的核心，多数场景下不需要 MQ 排队。

### 8.2 三道闸门（建议实现顺序）

1. **闸门一 · Redis Lua 原子预扣**：请求先到 Redis，`校验名额 + 扣减` 原子完成；失败直接返回"已满"——1000 并发只放行 100 到数据库
2. **闸门二 · 限流**（可选）：用户/资源维度的 Redis 计数器限流，挡刷单
3. **闸门三 · 落库**：扣减成功后落 MySQL（校园规模直接同步落库即可；需更平滑时用 8.3）
- **兜底**：MySQL 乐观锁（version）+ 唯一索引——Redis 失效时的最后防线（防重三板斧）

### 8.3 轻量队列（可选增强：用 Redis 实现"没有 MQ 的 MQ"）

- 提交请求 `LPUSH campus:queue:reservation` 入队 → 立即返回"排队中"
- 消费者：应用内线程池 或 `@Scheduled` 批量 `BRPOP` → **批量落库**
- **复用 12306 资产**：`@MQIdempotent` 的"消费中/已消费"两态 Lua 幂等（见修正后的 2.8 判定），用于队列消费者防重复处理
- 与真 MQ 的差距（写入 docs/04 说明）：宕机丢消息（可接受，用户可重试）、无死信/重试队列

### 8.4 阶段 9 建议增加的压测场景

- **场景 D：1000 线程抢 1 门容量 100 的课** → 期望结果：Redis 预扣挡下 900、DB 只产生 100 条落库；贴出"Redis 拦截率 / DB 实际写入量 / 耗时"
- 这个数字就是"无 MQ 也能扛"的量化证据，也是面试时的亮点素材

### 8.5 何时该升级到 MQ（写进 docs/04 的判断标准）

升级信号：需要跨服务消费 / 需要可靠投递不丢消息 / 需要多消费组 / 峰值远超单机处理能力。
12306 项目的 RocketMQ 用法（延时关单 + 消费幂等）即现成的升级样板，可对照引用。

### 8.6 可选扩展（不进主线验收，由你决定）

若希望简历上补充"MQ 实战"：阶段 9 之后可加做 **MQ 对比版**——本机已具备 RocketMQ 5.3.4 环境（DOVideo 容器），将 8.3 的轻量队列替换为 RocketMQ 版本做同场景对比压测，成果写入 docs 附录。
