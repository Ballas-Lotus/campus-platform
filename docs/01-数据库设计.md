## 1. 表清单与关系

| 模块 | 表 | 说明 |
|---|---|---|
| 用户 | `t_user` / `t_user_quota` | 三种登录方式（学号/手机/邮箱）；用户维度配额 |
| 统一资源 | `t_resource` / `t_resource_slot` | **四业务共用**：资源目录 + 时间片库存 |
| 预约 | `t_reservation` / `t_user_time_occupancy` | 预约主表（四业务共用）+ 用户时间位图（跨资源冲突检测） |
| 业务扩展 | `t_lecture` / `t_library_area` / `t_venue` / `t_course` / `t_course_class` / `t_course_selection` | 各业务元数据与专属表 |

**核心关系（逻辑外键，无物理外键）**：

```
t_lecture.id ──► t_resource(parent_id)         讲座席位资源
t_course_class.id ──► t_resource(parent_id)    课程名额资源
t_resource.id ──► t_resource_slot.resource_id  资源的时间片库存
t_resource_slot.id ──► t_reservation.slot_id   预约占用时间片
t_user.id + t_reservation.time_bitmap ──► t_user_time_occupancy.bitmap（冗余快照，冲突检测用）
```

## 2. 通用设计约定（含防坑决策）

| 约定 | 选择 | 理由 |
|---|---|---|
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | 演示用；生产换分布式 ID（docs/04 演进说明） |
| 外键 | **不使用物理外键** | 约束交给应用层——为分库分表预留（跨库外键不可行） |
| 时间类型 | "时刻"用 `DATETIME`、"时段"用 `TIME`+日期字段、周期用 `DATE` | 时段天然无日期（与 slot_date 组合）；防坑 3"不假设固定时长" |
| **逻辑删除（防坑 2 的明确选择）** | 生命周期由 status 表达的表**不用 deleted**：`t_reservation`、`t_resource_slot`、`t_user_time_occupancy`、`t_course_selection`；其余管理表用 `deleted` | 预约取消/退课本身就是状态；避免"逻辑删除 + 唯一索引"互相打架 |
| 唯一索引与 deleted | 管理表唯一索引**不含 deleted**（学号/手机/邮箱不放号，注销不释放） | 一句话业务规则，避免生成列复杂化；预约表的"取消-再约"则用生成列解决（见 3.3） |
| 枚举 | 业务状态用 `VARCHAR` 存字符串枚举，启停用 `TINYINT` | 可读性优先（学习/演示项目） |
| 位图 | `VARCHAR(64)` 存 24 个 hex 字符（96 格 × 15 分钟） | 防坑 4：便于调试；Java 用 `BitSet` 编解码（阶段 5 实现时配单元测试） |

## 3. 逐表说明与索引理由

### 3.1 t_user（用户）

字段要点：`student_no/phone/email` 三种登录方式，均为唯一索引（为演示"多方式登录读扩散"问题埋点，见 docs/04）。

| 索引 | 类型 | 服务哪条查询 |
|---|---|---|
| `uk_student_no` | UNIQUE | "学号登录"；唯一约束 |
| `uk_phone` | UNIQUE | "手机号登录"；唯一约束 |
| `uk_email` | UNIQUE | "邮箱登录"；唯一约束 |

### 3.2 t_user_quota（配额）

| 索引 | 类型 | 服务哪条查询 |
|---|---|---|
| `uk_user_type_period` | UNIQUE | "扣减/查询某用户某类型某周期的配额"（唯一性防重复行） |
| `idx_user_type` | 普通 | "我的当前配额"（按用户+类型查） |

### 3.3 t_resource（统一资源）

| 索引 | 类型 | 服务哪条查询 |
|---|---|---|
| `idx_type_campus` | 普通 | "按类型/校区筛选资源列表"（资源浏览页） |
| `idx_parent` | 普通 | "查某讲座/教学班下的席位/名额资源"（parent_id 反查） |

### 3.4 t_resource_slot（时间片+库存，高频大表 ~59.8 万行）

| 索引 | 类型 | 服务哪条查询 |
|---|---|---|
| `uk_resource_slot` (`resource_id`,`slot_date`,`start_time`) | UNIQUE | ①"查某资源某天某时段还有没有位置"（预约前置校验，唯一前缀命中）；②防重复生成时间片 |
| `idx_date_status` (`slot_date`,`status`) | 普通 | "按天统计/批处理"（运营报表、过期片处理） |

> **大表约束（防坑 5）**：本表所有列表查询必须走上述索引 + **游标式分页**（`id > last_id`），禁止 `LIMIT` 大偏移。

### 3.5 t_reservation（预约，核心）

**防重复预订的完整设计**（本表最重要的设计）：

- 生成列 `active_key`：`status IN ('PENDING','APPROVED')` 时为 `'Y'`，其余（CANCELLED/COMPLETED/NO_SHOW）为 `NULL`
- 唯一索引 `uk_reserved(slot_id, user_id, active_key)`——MySQL 唯一索引**允许多个 NULL**，于是：
  - 同一用户对同一时间片**最多一条有效预约**（防重）✓
  - "取消 → 再约 → 再取消 → 三约"：历史记录任意多条 `active_key=NULL`，互不冲突 ✓（若不用生成列，`uk(slot_id,user_id,status)` 在第二次取消时就会被唯一索引误伤）
- 重叠时段（14:00-16:00 与 15:00-17:00）不由索引防——由**位图冲突检测**兜住（位图是时段级的，见 3.6）
- `slot_id` 语义：指向 `t_resource_slot` 的起始片。库存片按"未来 14 天滚动窗口"生成（图书馆/场馆），历史片到期归档清理 → **历史预约 slot_id 为 NULL**；讲座片按场次生成（未来 30 天），不受 14 天窗口限制

| 索引 | 类型 | 服务哪条查询 |
|---|---|---|
| `uk_reservation_no` | UNIQUE | "按业务单号查预约"；幂等（防重复提交） |
| `uk_reserved` | UNIQUE | 防重复预订（见上） |
| `idx_user_status` | 普通 | "我的预约列表"（按状态筛） |
| `idx_resource_date` | 普通 | "某资源某天的预约情况"（管理/统计） |

### 3.6 t_user_time_occupancy（用户时间位图，跨资源冲突核心）

| 索引 | 类型 | 服务哪条查询 |
|---|---|---|
| `PRIMARY (user_id, occupy_date)` | 组合主键 | 冲突检测的**唯一入口**："取某用户某天位图"；**组合主键先 user_id → 分片友好**（永不跨片） |

### 3.7 业务扩展表

| 表 | 索引 | 服务哪条查询 |
|---|---|---|
| `t_lecture` | `idx_status_start(status,start_time)` | "讲座列表：已发布 + 按时间排序" |
| `t_venue` | `idx_type_campus(venue_type,campus)` | "按类型/校区筛选场馆" |
| `t_course` | `uk_course_code`；`idx_college_type(college,course_type)` | 课程代码唯一；"按学院/类型筛选课程" |
| `t_course_class` | `idx_course(course_id)`；`idx_schedule(semester,week_day,start_section)` | "课程→教学班列表"；"某学期某天某节次有哪些课"（排课冲突检测） |
| `t_course_selection` | `uk_user_class_semester`；`idx_class_semester(class_id,semester)` | 防重复选课（"选-退-选"为同行状态变迁不新增行）；"教学班选课名单" |

> 注：`t_course_waitlist`（候补队列）已于 **2026-10-08 退役**（阶段 8 规则：选课不设候补，
> 人数限额制满员直接拒绝）；迁移脚本见 `resources/database/migrate-drop-waitlist.sql`。

## 4. 分片键选择说明（阶段 14 已落地：2 库 × 4 表 = 8 分片）

| 表 | 分片键 | 理由 | 落地形态 |
|---|---|---|---|
| `t_reservation` | `user_id`（+ `reservation_no` 基因） | "我的预约"是最高频查询；写入必带 user_id；`reservation_no` 尾部拼接 `user_id % 1000000` **基因法**，使"按单号查"与"按用户查"同分片 | `campus_{0,1}.t_reservation_{0..3}` |
| `t_resource_slot` | `resource_id` | 预约扣减天然按资源维度定位；查询"某资源某天"单分片命中 | `t_resource_slot_{0..3}` |
| `t_user_time_occupancy` | `user_id`（组合主键首列） | 冲突检测**永远单分片**——"预约引擎不拆微服务"之外的第二道分片友好设计 | `t_user_time_occupancy_{0..3}` |
| `t_user_quota` / `t_course_selection` / `t_notification` | `user_id` | 用户维度读写（周配额/我的课表/站内信）全部单分片 | 各 `_{0..3}` |
| `t_user` | `id`（= user_id 同值域） | 同一用户的数据（用户行/预约/位图/配额/选课/站内信）**全部同库同表** | `t_user_{0..3}` |
| `t_user_phone` / `t_user_mail` / `t_user_student_no` | 自身（`CRC32(标识) % 8`） | 登录标识 → user_id 的**读扩散**索引表：单分片点查，换"永不广播" | 每库 1 张（库级分片） |
| `t_resource` / `t_lecture` / `t_venue` / `t_library_area` / `t_course` / `t_course_class` | 广播表 | 数据量小、查询频繁，两库全量同构副本 | 每库整表一份 |

**分片公式**（`shard = MOD(分片键, 8)`；库 = `shard / 4`，表 = `shard % 4`）与 Java 算法类
（`campus-common/.../framework/sharding/`）及迁移脚本（[migrate-sharding.sql](../resources/database/migrate-sharding.sql)）
**三处严格一致**。基因法恒等：`1,000,000 = 8 × 125,000 ⇒ 基因 % 8 ≡ user_id % 8`。

**阶段 14 物理侧变化（相对 schema.sql）**：

| 变化 | 说明 |
|---|---|
| 主键策略 | 分片表（预约/选课/站内信/配额/时间片）由 `AUTO_INCREMENT` 改**雪花**（`ASSIGN_ID` + 自定义发生器，机器号 Redis 分配）——AUTO 在 8 个物理分片间会撞号；历史数据保留原 id |
| 单号格式 | `RES + yyyyMMdd + 12 位序列` → **`RES + 雪花ID + 6 位基因`**（迁移时全量重写，旧格式不含基因无法路由） |
| `t_user.phone / email` | 存 **AES 密文**（ShardingSphere ENCRYPT，ECB/PKCS5+Base64）；物理列宽扩为 `VARCHAR(64) / VARCHAR(256)`；唯一索引保留（密文等值） |
| 唯一索引语义 | 分片后为"分片内唯一"；全局唯一由雪花+基因保证（`uk_reserved` 同用户天然同分片，语义不变） |
| 新增 3 张索引表 | `t_user_phone / t_user_mail / t_user_student_no`（明文标识 + user_id） |

> 单体库 `campus_platform` **原地保留**（阶段 15 对比基线与回滚路径）；运行期业务只连 `campus_0 / campus_1`。

| 1. 时区 | JDBC `serverTimezone=Asia/Shanghai`（阶段 4 配数据源时）；Jackson 统一定义 `yyyy-MM-dd HH:mm:ss` | 已在阶段 0 完成 Jackson 配置 |
