W1 · 台账状态机缺 CAS → 补偿与消费竞态，会双倍加名额 部分成立风险 中

问题补偿与消费是两个独立执行者，作用于同一份台账；清单给出 T0~T4 时序：消费成功与补偿同时发生 → 名额虚高。钳 ≤ 容量可能掩盖错账。
证据CourseStockAcceptService.java:176-181（补偿以 HEXISTS 为原子闸门）；CourseSelectConsumer.java:178-195（先查台账 → 落库 → 再清账，查与清非同一原子步骤）；CourseStockReconciler.java:98-110（30s 对账，pending 口径 + 版本 CAS）
修改意见评估需调整：台账 value 目前无状态位，需先加状态；消费端的状态迁移应发生在事务开始之前（认领 CONSUMING→PROCESSING），而不是“提交前 CAS DONE”；业务拒绝分支允许 PROCESSING→COMPENSATING；超时裁决覆盖 PROCESSING。改动集中在 ACCEPT/COMPENSATE 脚本与消费端 process() 的 ① 与 ③ 之间。
🗣️ 说人话：前台给你留了座、在小本本上记了一行“待登记”；后台拿着小票去名册写名字。有个极窄的时间缝：后台刚写完名字、还没来得及在小本本上划掉那行，前台因为“等回音超时”就判定“没办成”，于是把座位加回去——结果你选上了，座位数也多还了一个，等于凭空多出 1 个名额。正常网络碰不到（发小票是毫秒级），只有“网络打嗝、系统以为没送到但实际送到了”的故障瞬间才可能撞上。撞上也不是永久错账：每 30 秒一次的“对账”会发现账不对并改回来。修法就是给小本本上的每条记录加一个状态：谁先动这条记录，另一个就放弃——一张单子只能盖一个章。

W2 · opId 服务端生成 → 重试不幂等？ 部分成立风险 低

问题opId 在服务端生成；网络重试可能“又受理一次、又扣一次”（清单假设 5 秒幂等窗口过后无保护）。
证据CourseSelectGate.java:100（服务端生成 opId）；CourseStockAcceptService.java:113-140（ACCEPT 脚本内幂等两态 + SISMEMBER 已选检查）
修改意见评估需调整：重试不会二次扣减（两道路障），建议保留但降为体验优化；实现不必 hash，直接把客户端 requestId 当 opId；回放要明确是“裁决码”而非 remain 数字（数字可能已被后续操作改变）。
🗣️ 说人话：你担心“我点了一次、响应丢了、再点一次，会不会选上两次、扣两个座”。不会：系统有两道挡板——第一道是 5 秒内的“防连点”标记，重复提交直接告诉你“别重复点”；第二道是“已选名单”，5 秒后再点，系统一看名单里有你，就回“你已经选过啦”，根本不会再扣座。真正的小问题是：重试时它不会把第一次办理的结果再念给你听，你可能得刷新确认；而且如果第一次还在落库途中，那句“已选过”可能比最终结果先到（万一随后发现时间冲突，你会先被告知“已选过”、再收到“没办成”）。数据不会错，只是话说得不够准。

W3 · 冷启动恢复没有单飞保护？ 部分成立风险 中

问题“各至多一次”只防单请求死循环，不防并发：1 万请求同时 -6/-2 → 同时按 DB 初始化 → DB 被打爆；且 Lua 里不可能查 MySQL。
证据CourseStockAcceptService.java:260-278（集合初始化：锁 + 双检）；CourseStockService.java:257-262（结构重建：锁 + 双检）；CourseSelectGate.java:105-126（-6/-2 恢复在 Java 侧读 DB 后重跑 Lua，符合“Lua 查不了库”的约束）
修改意见评估可直接落地（针对“等锁者也各查一次库”）：受理恢复改为只触发重建、忽略返回值，或给 rebuild 加无兜底变体；“等待者快速失败 + 前端退避”需新增错误码，属产品取舍。
🗣️ 说人话：担心“Redis 刚重启、一万人同时点选课，会不会所有人同时查库把数据库压垮”。分两半：好的那一半——“重新建立公告板”有锁，同一门课只派一个人去做；重建是 Java 去查库（脚本里连不了数据库），符合约束。不够好的那一半——没抢到锁的人不是安静等，而是各自去数据库抄一份数字再离开；人特别多时数据库会挨一波“每人抄一次”。再加上重建失败会退回老流程、老流程第一步也查库，高峰瞬间数据库确实比平时忙。这不是错账问题，是“高峰 + 刚重启”时的性能问题，修法就是让来晚的人别各自抄库。

W4 · 降级链路自相矛盾？ 不成立风险 低

问题“Redis 异常 → 同步老链路”，但老链路第一步也是 Redis 预扣 → 没有不依赖 Redis 的路。
证据CourseSelectGate.java:226-230（tryFastPath 异常 → courseService.select 直通数据库）；CourseSelectGate.java:262-267（慢路径同样处理）
修改意见评估不适用（无需新增第三级）；可选增强：给纯 DB 层加独立并发闸（目前依赖 Sentinel 阈值与 DB 条件更新）。
🗣️ 说人话：你的推理是“老办法第一步就要用 Redis，所以 Redis 坏了老办法也跑不通，等于没退路”。推理没错，但代码在老办法内部还有一层保险：一旦发现 Redis 连不上，会连“预扣”都跳过，直接冲进数据库，让数据库自己的规则（名额没满才能加一、同一个人不能重复）做最终判定。实际有三档：①新办法 → ②老办法 → ③完全不碰 Redis 的纯数据库。Redis 彻底挂掉时你会落在第③档：能选、结果也对，只是慢，压力全在数据库上。第③档的保护目前靠入口限流，觉得不够可以再加一层“同时最多放多少人进数据库”的闸。

W5 · “置消费（5s 等零）”阻塞请求线程？ 不成立风险 无

问题清单怀疑“置消费（5s 等零）”是请求线程阻塞等待 5 秒。
证据CourseSelectGate.java:190-193（markConsumed(idemKey, 5s)）
修改意见评估不适用（非阻塞）；设计图措辞有歧义，代码语义明确。
🗣️ 说人话：“5 秒”是系统在 Redis 里放的一个小标签：“这个同学刚提交过，5 秒内别再受理”，5 秒后标签自动消失——用来防手抖连点。请求线程只是“写一下标签”就立刻返回了，全程几十毫秒，没有任何人等 5 秒。设计图里“置消费（5s 等零）”写得像“等 5 秒”，是图误导了你。

W6 · 回退切换时没有排空在途请求 部分成立风险 低

问题回退时若有“已受理、未落库”的在途单（最长 5 分钟），老链路读 DB 看不到 → 允许再选 → 异步随后落库 → 同一用户选上两次。
证据CourseSelectGate.java:78-79（@Value 开关，重启生效）；同步链路不查台账（CourseService.java:168-169）；重复由唯一索引兜底、消费端业务拒绝分支补偿（CourseSelectConsumer.java:196-218）
修改意见评估可直接落地（只出不进 + 排空），但对数据正确性非必需；最低成本：切换脚本先摘流量、等台账归零再切换；或同步链路入口检查本人未决台账。
🗣️ 说人话：担心“切回老办法的那一刻，有人新办法已受理、名册还没写，老办法看到他没选上就让他再选一次，结果选上两门一样的课”。这条链被两道东西挡住：①名册有“同一学期同一教学班只能有一行”的硬规矩，第二次写入会被直接拒绝；②后台那条迟到的登记如果发现“已经选过了”，会自动退座，把多扣的名额加回来。所以最终数字是平的。小瑕疵在观感：切换那几秒里，同一个人可能先看到“成功”、又收到更早那单的“没办成”，一会儿说成了一回说没成。修法很朴素：切换时先暂停新请求、等“待办”清空再切。

W7 · 补偿消息本身不幂等？ 不成立风险 无

问题清单假设补偿也由消息触发，MQ 至少一次投递 → 同一消息投两次 → 名额 +2。
证据补偿无独立 topic；调用点仅三处：CourseSelectGate.java:176-183、CourseSelectConsumer.java:205、CourseStockReconciler.java:157；均走 CourseStockAcceptService.java:176-181 的 HEXISTS 原子闸门
修改意见评估不适用（补偿不由消息驱动，且已幂等）；若做 W1 的台账状态位改造，可顺带把状态带上，但非必需。
🗣️ 说人话：你担心“补偿如果靠消息触发，消息重复投递两次，会不会退两次座”。首先，补偿根本不是消息触发的——系统里没有“补偿消息”这种东西，补偿是三个地方在需要时直接调用同一段代码：前台发不出小票时当场退座、后台发现你不符合条件时退座、每 5 分钟巡检发现拖太久的单子时退座。其次，这段“退座”代码自带原子锁：先去小本本找那一行，找到就“删掉这行并加一个座”，找不到就什么都不做。所以同一笔单子无论被触发多少次，座位最多加一次。你提的“用 opId 去重”就是这个机制本身。

W8 · 读写联动三处定义 8a 不成立8b 部分成立8c 不成立

问题8a 发起者是否等 SSE；8b settled 与 stock 的渲染优先级；8c 库存粒度 course vs class。

修改意见评估8a 不适用；8b 可直接落地（settled 携带 remain/ver）；8c 不适用（澄清即可）。
🗣️ 说人话：8a：你自己点选课，返回结果里就带着“最新还剩几个位、第几版”，页面立刻用它更新自己；广播是给别的同学看的。8b：“我有没有选上”和“这门课还剩几个位”是两件独立的事，代码分开存，不会互相冲掉；小瑕疵是失败回滚时，“已选取消”的提示可能比“座位加回来”早到几十毫秒（广播要等 50 毫秒合并），数字随后自动补齐——最稳的改法是把最新余量直接塞进“没办成”那条通知里。8c：名额是按“教学班”点的，不是按课程；课程页上的总数是前端把各班加起来给你看的，代码里定义非常明确。

W+ · 补充：40056「假失败」——说没受理，其实选上了 补充发现风险 中

问题发送超时但消息已投递并消费成功 → 补偿空转 → 仍回 40056；settled(ok=true) 到达但前端无对应“待处理”上下文，被忽略。
证据CourseSelectGate.java:176-183（补偿后仍抛 40056）；CourseSelectConsumer.java:178-180（台账已清则跳过）；CourseView.vue:490-505（无 _pending 时 ok=true 不处理）
修改意见评估可直接落地：改文案 + 前端对“矛盾的成功回执”主动刷新；不动数据结构。
🗣️ 说人话：有一种隐蔽情况：你点选课，系统发“登记单”时网络超时，但后台其实收到了并办成了。前台按规矩执行退座，却发现小本本那行已被划掉（说明办成了），于是什么也没退——但还是按“没办成”回了你一句“未被受理，请重试”。你屏幕上写着失败，实际已经选上了；“办成了”的通知其实也发给你了，但你的页面当时没有“等待中的单子”这个概念，收到就直接忽略了。数据没错，但你得刷新才知道真相。建议把这句话改成“结果未知，请刷新确认”。

👀 读链路（8 条 + 1 条补充）

总评：1 条成立（R8）· 4 条部分成立（R3、R5、R6、R7）· 3 条不成立（R1、R2、R4）

R1 · L1 的 version 语义自相矛盾？ 不成立风险 低

问题L1 同时写着“键含版本”与“信号即失效”——两种互斥缓存语义混用；version 参数含义不定。
证据StockL1Cache.java:44-53（键=courseId；命中用 cver == clientVersion）；CourseStockService.java:187-203（未命中走 L2/L3，忽略客户端 version）
修改意见评估不适用（无需调整语义）；若要改，只改设计图措辞。TTL 2s 是刻意的“漏信号陈旧上界”，不建议放宽到 30–60s。
🗣️ 说人话：缓存像一张贴在眼前的便签，记着“这门课还剩几个位、第几版”。你每次来问，它先看你手里记的版本号：一致就把便签上的数给你（省得再跑一趟）；不一致就去公告板重新抄一份最新的。关键点：不一致只会导致“多跑一趟拿最新”，绝不会导致“拿不到新数据”——最新数据永远服务端说了算，版本号只用来省这趟腿。所以这两套语义在代码里并不冲突，是设计图那句“键含版本”写得不准确。

R2 · L3 重建缺少 selected 的数据源？ 不成立风险 低

问题“真值 = cap − selected − Σpending”，但“查询不碰 MySQL”——selected 从哪来？
证据CourseStockService.java:329-341（dbTruth 读 t_course_class 的 capacity/selected）；CourseStockService.java:257-296（仅 L3 重建与降级快照读库）
修改意见评估不适用（selected 来源即 MySQL，只在重建时读取；“Redis 另存 selected 计数”是可选优化）。
🗣️ 说人话：你问“不碰数据库的话，'已经选了多少人'这个数从哪来？”——答案是：真到了需要重新点人数时，它就是去数据库数的（名册上写着每班容量多少、已选多少）。平时九成九的查询只看便签和公告板，不打扰数据库；只有“便签和公告板都过期”这种少见情况，才派一个人去数据库数一遍再更新回来。设计图那句话漏了“除了重新数的时候”这个括号，不是链路断了。

R3 · ∑pending 是遍历求和，而非增量计数 部分成立风险 低

问题∑ 意味着遍历求和；热点课 pending 上千，求和在锁内 → 重建本身成热点；建议维护 pendingCount 增量计数。
证据CourseStockService.java:413-447（pendingEntries 读整个 Hash 后循环计数；重建锁内与对账器里调用）
修改意见评估不适用（代价大于收益）：台账条目 = 在办请求，天然 ≤ 名额数；几百条 HGETALL 是微秒级；增量计数器会新增三处写路径并引入漂移风险。
🗣️ 说人话：算“还有多少人在办”确实是挨个看小本本，不是提前攒一个总数。但别急——小本本上记的是“已经占到座、但还没登记完”的单子，这种单子最多只等于这个班的名额数（比如 120 个），而且通常半秒内就被划掉了，所以本子上通常只有几条到几十条。挨个数这几十条是眨眼都不到的功夫。反过来，专门维护一个“进行中总数”，就要在受理、退座、登记完三处都加减它，任何一处出错数字就永久偏了——反而更危险。所以这里“挨个数”是更稳的选择。

R4 · version 缺乏持久单调 → 前端「只升不降」会永久卡死？ 不成立（已修复）风险 低

问题Redis 重启/evict 后 ver 可能变小；前端“只升不降”永久丢弃 → 界面停在旧数字，直到手动刷新。
证据stores/stock.js:214-230（“服务端查询 = 权威快照：数值永远采纳；版本只升高（高水位），不降低”）
修改意见评估不适用（已以更强形式修复：数值直接以查询为准）；清单的“时间戳版本/持久序列”方案不再需要。
🗣️ 说人话：你担心的场景是：服务器重启后版本号从头数（比如从 15 变回 1），页面记着“我见过第 15 版”，于是把后面所有“第 1 版、第 2 版”都当旧消息扔掉——页面永远停在旧数字。这个隐患确实存在过（上一版代码），已经修好了：现在页面的规则是“从服务器查回来的数字永远信、版本号只记最高的那个”。即使版本号变小，数字照样更新；即使实时消息全丢了，最多 60 秒一次的对账核对也会把数字拉回来。

R5 · 没有任何容量与扇出估算？ 部分成立风险 低

问题设计里没有 QPS/订阅数/扇出量/帧大小；50ms 合并只压频率、压不住人数；建议补容量表、单次序列化、连接硬上限。
证据application.yml:105-110（连接/用户/班级上限、寿命、心跳）；StockSseRegistry.java:52-54（池 4/8、队列 1000）；StockSignalBus.java:141-143（一帧构造一次、多连接复用）
修改意见评估部分适用：硬上限与单次序列化已满足；建议补一张量级测算表（纯文档）。
🗣️ 说人话：你担心“一万人盯同一门课，服务器推得过来吗”。代码里的保险丝其实都在：一台机器最多 5000 条实时连接、每账号 3 条、每条最多盯 200 个班、推送线程池多大、队列多长，都配好了。推送也是“把一条消息准备好、给每个连接各发一份”，不存在每连接重新生成内容的浪费。真正缺的是一张“多少人 × 每秒变几次 × 每条多大 = 每秒多少数据”的测算表——这是文档没写，不是代码没有。按每条约 0.1KB 粗算，5000 人盯一门课、每秒最多 20 次，也就是每秒几兆，单机扛得住；到五万人盯一门课才需要多实例分流。

R6 · 服务端 → Redis 的订阅断连没有覆盖 部分成立风险 低

问题Pub/Sub 无 ACK；实例与 Redis 的订阅断开后，本实例用户静默错过所有信号，浏览器端不触发轮询。
证据StockSignalBus.java:82-96（只注册监听器，无断连回调/健康标记）；stores/stock.js:22-23,246-253（连接正常也 60s 校准；断开 15s）
修改意见评估可直接落地（容器状态监听 → 标记 degraded / 推校准帧），属增强；当前已有“≤60s 陈旧”的兜底。
🗣️ 说人话：这里有两段连接：一段是“浏览器 ↔ 服务器”（断了前端知道），另一段是“服务器 ↔ Redis 的广播接收器”（断了服务器不会吭声）。你担心的第二种：服务器耳朵聋了，浏览器还傻等实时消息，页面永远不动。一半是真的——代码里确实没有“接收器断了我喊一声”的机制；另一半不成立——页面不是只靠实时消息：就算一切正常，它也会每 60 秒主动核对一次数字；浏览器自己的连接断了，就改 15 秒一次。所以最坏是“数字旧最多一分钟”，随后自动恢复，不会永远不动。建议的“断了就通知页面进入兜底模式”可以做，属于锦上添花。

R7 · 异常路径的返回语义未定义（两半分开判定） 降级语义：不成立线程池溢出：成立风险 中

问题degraded 没写返什么；线程池溢出没写丢旧帧还是新帧。
证据a：CourseStockService.java:261 → 366-367（降级返回 DB 真值快照）；CourseStockController.java:39-56（degraded 字段在响应里）。b：StockSseRegistry.java:52-54（AbortPolicy）、134/154（execute 无捕获）、StockSignalBus.java:135-145（flush 无 try）、100（scheduleAtFixedRate）
修改意见评估a 不适用（语义已定义且比建议更强）；b 可直接落地：flush 包 try/catch + DiscardOldestPolicy，或独立队列。
🗣️ 说人话：分两半。第一半：你担心降级时返回“上一版旧数字却不加标记”。实际不是——所谓降级，是“便签和公告板都没了，当场派人去名册数一遍再回答你”，返回的是当场最新的真数字，还带“我是兜底查的”标记（只是页面没显示这个标记）。第二半是真问题，而且是这份清单里最该修的：这台服务器靠一个“每 50 毫秒检查、有变化就群发”的定时器干活，任务丢进容量 1000 的队列。队列一满，代码会抛异常，而定时任务有个脾气：抛过一次异常就再也不跑了。结果是从此不再推任何实时消息，还一行日志都不留——页面靠 60 秒轮询还能更新，但“实时”没了，没人知道它停了。修法很小：把“检查并群发”包一层“出错也别死”，队列满了丢最旧的消息（实时消息本来就是新的覆盖旧的，丢旧无害）。

R8 · stock 与 settled 共用一条连接，无优先级 成立风险 中

问题settled（低频高价值）与 stock（高频低价值）同一条 SSE、同一队列，无优先级；stock 拥塞会延迟确权。
证据StockSseRegistry.java:122-139（pushToUser）与 142-159（fanout）都提交同一个 fanoutPool 的同一 FIFO 队列
修改意见评估可直接落地：settled 独立小队列/线程或消费线程直发；至少捕获推送异常并回落站内信。
🗣️ 说人话：系统要往你浏览器推两种消息：一种是“这门课又少了一个位”（频繁、可丢，后面还有新的）；另一种是“你刚才那单办好了/没办成”（很少、但对你最重要）。现在这两种消息排同一个队、用同一条通道，没有“重要消息插队”的机制。像食堂把普通窗口和“叫号取餐”排在同一条队——人一多，你最着急的“我到底点上没有”就排在几百个“某某桌撤了一个菜”后面。平时没事（队伍很短），高峰时会让你在“我到底选上没有”的不确定里多待一会儿；最坏还会和上一条联动：队列满时这条重要通知直接被拒掉。修法：给这种“只发给一个人”的通知单开一条小通道，或由办理的人直接送达。

R+ · 补充：Redis 全挂时 /stock 返回 500（回源兜底被锁挡住） 补充发现风险 中

问题Redis 全挂时读服务是否还活着：L3 的 dbSnapshot 兜底被“领锁”挡住。
证据CourseStockService.java:257-258（lock.tryAcquire 在 try 之外）；205 行起（readL2 捕获异常返回 null）
修改意见评估可直接落地：tryAcquire 移入 try（异常时直接 dbSnapshot），或给锁增加“降级直通”变体。
🗣️ 说人话：查余量的打算是：先看便签 → 再看公告板 → 都没有就“派人去名册数一遍”。但“派人”之前要先领一把锁（防止一百个人同时去数），而领锁本身也要访问 Redis——Redis 挂了，领锁直接报错，整条路就断了，接口返回 500。只有“2 秒内刚看过的便签”还能用。也就是说，“数据库兜底”这一步设计上有，但被“领锁”挡在门外。修法：把领锁也包进保护里——领不到（或报错）就干脆跳过锁直接去数；最坏情况是几个人同时去数，结果也是对的，只是多几次数据库查询。
