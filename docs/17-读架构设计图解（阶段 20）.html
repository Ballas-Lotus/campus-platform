读架构图解：三层缓存漏斗 + 一条信号推送线

同一条读，分成两件事：看得见变化（展示层：L1/L2/信号/乐观渲染，允许毫秒级滞后）与 算不算得数（判定层：闸门 Lua + 数据库条件更新，唯一裁决）。本文四张流程图把两条线讲透，并给出 人话 ↔ 术语逐项对照。

变更感知延迟 1ms（落库→客户端收帧） L1 命中率 99.9%（39,857 / 32） /stock 容量 ~4.2k QPS 信号风暴 12 → 1 合并

1读架构全景：两条线、四层

人话：查询走"漏斗"（能不进厨房就不进厨房）；变化走"广播"（后厨一出菜就喊一声，各服务员只通知自己照看的客人）。 术语：Cache-Aside 多级缓存 + 服务端推送（signal-and-pull）；多实例经 Redis Pub/Sub 扇出，无粘性会话。

图 1 · 读架构全景：① 查询走漏斗（蓝线）② 订阅走长连接（绿线）③ 写后信号经 Pub/Sub 广播（紫线）

2查询三层漏斗：每一步拦住多少

人话：先看口袋小抄 → 再看共享保温箱 → 都没有才现做，而且只放一个人进厨房。 术语：L1 进程内不可变快照（版本键）→ L2 分布式缓存原子快照 → L3 互斥回源（锁 + 双检 + 超时兜底）。

图 2 · 查询漏斗：L1 直返（0 网络）→ L2 一次 HGETALL → L3 锁+双检（超时兜底）

3写后信号传播：从落库到"你屏幕上数字变了"

人话：后厨一出菜就喊一嗓子（只喊"变了 + 新数字"），各服务员听到后只通知自己照看的客人；客人先动手改数字，再抽空去核对。 术语：afterCommit 发布 → Redis Pub/Sub 扇出 → 实例内合并 → SSE 推送 → 客户端乐观渲染 + 防抖校准（signal-and-pull）。

图 3 · 时间轴：t=0 提交 → 1ms 收帧 → ~17ms 可见 → 150ms 开始校准 → ≤500ms 权威值回填

4前端响应管线：信号与降级轮询共用同一条流水线

人话：听到喊声有三步规矩（先动手 → 攒一攒 → 去核对），旧版本信息一律扔掉；电梯（SSE）坏了就走楼梯（轮询），修好后先把状态对齐再继续。 术语：乐观渲染 → 防抖合并 + 最大等待 → 带版本校准；单调版本去重（乱序丢弃）；fallback polling；resync-on-reconnect。

图 4 · 前端管线：三步规矩 + 三条旁路（降级 / 重连拉齐 / 多标签共享），及"旧版本一律丢弃"的硬规则

6设计原则与诚实边界

六条原则

#原则（人话 → 术语）
1看板可以旧、裁决必须新 → 展示层允许毫秒级滞后；判定层（闸门 Lua + DB 条件更新/唯一索引）唯一裁决
2只喊"变了"不端饭 → signal-and-pull；避免 N 倍广播放大
3版本号是通行证 → 单调版本做去重 / 防乱序 / 缓存键；不依赖时钟
4每一层都要能输 → 逐层降级（L1 没了走 L2，信号丢了走轮询，SSE 断了走重连+轮询）；只有真相层不可绕过
5重建只在"知道真相"时进行 → 同步写模型下 DB 真值即真相，按真值重建/对账永远安全（无需在途台账）
6让最贵的东西最少被碰 → 数据库连接与写路径；查询不回源、推送仅 20 字节、写路径零改动

边界（如实说明）

① L1 最坏陈旧 ≤2s（Pub/Sub 尽力而为，靠 TTL 封顶 + 轮询收敛）；
② 课程列表聚合列只在该课程"打开过抽屉"后享受实时补丁，不承诺全列表实时；
③ SSE 上限：单实例 5000 连接 / 单用户 3 条 / 单连接 200 个教学班，超限自动降级轮询；
④ "我的预约 / 我的已选"永远实时查库——这是共享度决定的特性，不是缺陷；
⑤ 多实例扇出结构就绪，本机按单实例验证（起第二个实例即可复验广播）。
